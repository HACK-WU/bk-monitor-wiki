# Wiki增量更新Skill 需求挖掘报告

## 1. 原始需求描述

> 现在想创建一个skill，可以用于指导AI，如何根据metadata.json中的数据，以及用户指定的提交，去更新json数据，同时更新wiki呢？并且更新的wiki需要符合当前已有的wiki的风格和格式？

## 2. 需求澄清

### 2.1 需求形态
**真实需求** - 创建一个增量更新skill，用于保持wiki与源代码同步

### 2.2 功能本质
解决wiki与源代码脱节的问题，提供半自动化的wiki更新能力，确保文档与代码保持一致

### 2.3 使用场景与角色

| 场景 | 描述 |
|------|------|
| 场景1 | 开发者提交了代码变更（如新增功能、修改接口），需要更新wiki反映最新实现 |
| 场景2 | 用户指定一个commit，AI自动检测变化的源文件，更新受影响的wiki页面 |
| 场景3 | 更新后的wiki保持与现有wiki一致的风格格式（引用格式、目录结构、架构图风格等） |

**场景关联性**：场景1和2是同一流程的不同表述，场景3是质量约束

### 2.4 用户角色
- **AI助手**：执行增量更新的主体
- **开发者/维护者**：指定commit、审核更新结果
- **读者**：使用wiki的用户，期望文档始终是最新的

### 2.5 核心痛点
- 当前wiki是基于特定commit一次性生成的，无法自动跟进代码变更
- 手动更新wiki工作量大，且容易遗漏
- 如果完全重新生成，会丢失之前手动编辑或优化的内容

### 2.6 期望体验
- 指定一个commit hash → AI自动分析变化 → 更新受影响的wiki → 保持格式一致
- **最爽的一点**：文档与代码自动同步，无需手动维护

### 2.7 深层动机
- 减少文档维护成本
- 确保文档的准确性和时效性
- 提高团队协作效率（文档不会过时）

### 2.8 非功能性需求
- **性能**：增量更新应比全量重建快50%以上
- **格式一致性**：更新后的wiki必须保持与现有wiki一致的格式规范
- **可追溯性**：记录每次更新对应的commit

### 2.9 关键假设与验证建议

| 假设 ID | 假设内容 | 验证难度 | 验证建议 |
|---------|----------|----------|----------|
| H-01 | 用户希望保留手动编辑的内容，只更新受影响的部分 | 低 | 确认用户是否接受完全重新生成 ✓已确认 |
| H-02 | wiki中的 `<cite>` 引用关系是增量更新的关键依赖 | 中 | 检查metadata.json是否记录了wiki与源文件的映射关系 ✓已确认：需要建立双向索引 |
| H-03 | 需要维护wiki的格式规范（引用、目录、图表风格） | 低 | 已通过现有wiki验证格式特点 ✓已确认 |

## 3. 根本性分析

### 3.1 核心问题
如何建立和维护wiki页面与源代码文件的映射关系，以便在源代码变更时能够精准定位受影响的wiki页面并进行增量更新？

### 3.2 根因链
1. wiki是基于特定commit一次性生成的
2. 生成时建立了wiki内容与源代码的引用关系（通过 `<cite>` 标签记录实际引用的文件）
3. **但这个引用关系没有被持久化到metadata.json中**
4. 因此在源代码变更时，无法自动定位受影响的wiki页面

### 3.3 方案评估
**判断**：**情况 A - 方案对症**

**理由**：
- 该方案直接解决"wiki与源代码脱节"的核心问题
- 通过建立映射关系，实现精准的增量更新
- 保留手动编辑内容，只更新受影响的部分
- 维护wiki格式规范，确保一致性

### 3.4 预期效果分析
- **核心场景覆盖度**：高 - 能覆盖大部分增量更新场景
- **痛点解决程度**：高 - 从"手动维护"变为"半自动化更新"
- **用户体验提升**：指定commit → 自动分析 → 更新wiki → 格式一致
- **潜在副作用**：
  - 首次建立映射关系需要扫描所有wiki文件
  - 如果源文件变化较大，可能需要人工审核更新结果

### 3.5 建议
- **短期**：创建增量更新skill，支持基本的增量更新流程
- **长期/根本**：在metadata.json中维护完整的wiki-源文件映射关系，支持更精准的增量更新

## 5. metadata.json 结构设计

### 5.1 双向索引结构

```json
{
  "wiki_path": "bk-monitor-wiki/wiki",
  "source": { "repo": "...", "branch": "master", "commit_id": "..." },
  "excluded_paths": ["bklog/", "bkmonitor/webpack/"],
  "stats": { ... },
  "wiki_catalogs": [ ... ],
  
  "source_to_wiki": {
    "bkmonitor/alarm_backends/README.md": [
      "告警系统设计/告警系统设计.md",
      "故障排查/常见问题诊断.md"
    ]
  },
  "wiki_to_source": {
    "告警系统设计/告警系统设计.md": [
      "ai-docs/bk-monitor/docs/告警后台(alarm_backends)/告警数据流.md",
      "bkmonitor/alarm_backends/README.md"
    ]
  }
}
```

### 5.2 解析规则

| 来源标记 | 格式 | 提取方式 |
|---------|------|---------|
| `<cite>` 标签 | `[名称](file://相对路径)` | regex 匹配 `<cite>...</cite>` 块内所有 `file://` 链接 |
| **章节来源** | `**章节来源**\n- [名称](file://相对路径)` | 按段落匹配，归属到最近的 `##` 章节 |
| **图表来源** | `**图表来源**\n- [名称](file://相对路径)` | 按段落匹配，归属到最近的 mermaid 代码块 |

**路径规范**：
- 提取 `file://` 后的路径，去掉行号部分（`#L1-L71`）
- 所有路径使用相对路径，不含 `file://` 前缀

## 6. 增量更新流程

### 6.1 完整流程

```
用户指定 commit hash
        ↓
git diff --name-only <old_commit>..<new_commit>
        ↓
过滤：排除 excluded_paths 中的文件
        ↓
查 source_to_wiki 索引 → 得到受影响 wiki 列表
        ↓
对每个受影响 wiki：
  ├── 读取当前 wiki 内容（含 <cite>、章节来源）
  ├── 读取新版本源文件（git show <commit>:<path>）
  ├── AI 对比变更，生成更新后的 wiki 内容
  └── 更新 <cite> 和章节来源中的文件列表
        ↓
更新 metadata.json：
  ├── source.commit_id = <new_commit>
  ├── 重新扫描受影响 wiki 的引用关系
  └── 更新 source_to_wiki / wiki_to_source
        ↓
输出变更摘要，等待用户确认
```

### 6.2 变更影响分类

| 变更类型 | 对 wiki 的影响 | 处理方式 |
|---------|---------------|---------|
| 源文件内容修改 | 对应章节可能需要更新 | AI 对比 diff，重新生成受影响的章节 |
| 源文件新增 | 可能需要新增 wiki 章节 | AI 判断是否需要新增 |
| 源文件删除 | wiki 中引用失效 | 标记或删除相关引用 |
| 源文件重命名 | 引用路径需要更新 | 自动更新路径 |

## 7. wiki 格式规范

### 7.1 格式模板

```markdown
# 标题

<cite>
**本文引用的文件**
- [文件名](file://相对路径)
- [文件名](file://相对路径#L1-L71)
</cite>

## 目录
1. [简介](#简介)
...

## 简介
[内容]

## 章节标题
[内容]

```mermaid
[图表]
```

**图表来源**
- [文件名](file://相对路径)

**章节来源**
- [文件名](file://相对路径)
```

### 7.2 格式校验规则

| 规则 | 说明 |
|------|------|
| R1 | 文件开头必须有 `<cite>` 标签 |
| R2 | `<cite>` 中的路径必须是相对路径，不含 `file://` |
| R3 | 每个 `##` 章节末尾必须有 `**章节来源**` |
| R4 | 每个 mermaid 图表后必须有 `**图表来源**` |
| R5 | 所有路径引用格式为 `[名称](file://相对路径)` |
| R6 | 目录结构必须与实际章节对应 |

## 8. 潜在风险与注意事项

1. **源代码变化较大时，wiki更新质量可能下降**
   - 建议：对大幅变更标记需要人工审核

2. **新增源文件可能不在任何现有 wiki 中**
   - 建议：AI 判断是否需要新建 wiki 页面

3. **索引构建的首次成本**
   - 一次性扫描 132 个 wiki 文件，耗时约 2-3 秒
