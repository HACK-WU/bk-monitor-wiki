## 简介

## 任务结构

```go
type Task struct {
	Kind    string   // 任务类型标识，如 "async:collect_es_task"
	Payload []byte   // 任务参数（JSON 序列化后的字节）
	Options []Option // 可选行为配置
}

type SerializerTask struct {
	Kind    string
	Payload []byte
	Options Options // 已合成的确定值（非 Option 列表）
}
```

- `Task` 是**生产者侧**的构造形态：`NewTask(kind, payload, opts...)` 接收 `Option` 列表。
- `SerializerTask` 是**传输/落盘形态**：`NewSerializerTask(t)` 通过 `ComposeOptions` 将 `Option` 列表合成为确定的 `Options`（见下节），便于序列化进 Redis。
- `TaskMessage`：broker 在 Redis 中存储的消息体（含 `ID/Queue/Retry/Retried/ErrorMsg/Timeout/Deadline/UniqueKey/Retention/CompletedAt` 等字段）。
- `TaskInfo`：向 API/管理端展示的任务详情（`NewTaskInfo(msg, state, nextProcessAt, result)` 由 `TaskMessage` + 状态合成）。
- `TaskMetadata`：内部携带 `id/maxRetry/retryCount/qname`，供 processor 注入 context（`AddTaskMetadata2Context`）。

```go
func NewTask(kind string, payload []byte, opts ...Option) *Task {
	return &Task{Kind: kind, Payload: payload, Options: opts}
}
```

## 选项系统（Option）

`Option` 是一个接口（`String()/Type()/Value()`），通过一组具名构造函数表达任务行为；`ComposeOptions` 将其合成为 `Options` 结构体。

支持的选项（含默认值）：

| Option 构造函数 | Options 字段 | 默认 | 说明 |
|----------------|--------------|------|------|
| `MaxRetry(n)` | `Retry` | `DefaultMaxRetry`=5 | 最大重试次数（负数按 0） |
| `Queue(name)` | `Queue` | `DefaultQueueName`="default" | 队列名（需通过 `ValidateQueueName`） |
| `TaskID(id)` | `TaskID` | `uuid.NewString()` | 任务 ID（不可空） |
| `Timeout(d)` | `Timeout` | 0 | 运行超时 |
| `Deadline(t)` | `Deadline` | 零值 | 截止时间 |
| `Unique(ttl)` | `UniqueTTL` | 0 | 唯一去重 TTL（<1s 报错） |
| `ProcessAt(t)` | `ProcessAt` | `time.Now()` | 指定执行时刻 |
| `ProcessInterval(d)` | `ProcessAt` | — | 相对当前时间偏移（`ProcessAt` 后到则覆盖） |
| `Retention(d)` | `Retention` | 0 | 完成后保留时长（>0 才进 completed ZSet） |

`ComposeOptions` 以默认值初始化后逐个应用，遇到非法（空 TaskID、Unique TTL<1s、非法队列名）返回 error。

```go
func ComposeOptions(opts ...Option) (Options, error) {
	res := Options{
		Retry:     common.DefaultMaxRetry,
		Queue:     common.DefaultQueueName,
		TaskID:    uuid.NewString(),
		ProcessAt: time.Now(),
	}
	for _, opt := range opts { /* 按类型 switch 覆盖 */ }
	return res, nil
}
```

## 任务状态机（TaskState）

`TaskState` 是一组从 1 开始的连续枚举（`iota+1`），灵感来自 asynq/machinery：

```go
const (
	TaskStateActive    TaskState = iota + 1 // 1 执行中
	TaskStatePending                       // 2 等待中
	TaskStateScheduled                     // 3 已调度（延迟）
	TaskStateRetry                         // 4 重试中
	TaskStateArchived                      // 5 已归档（最终失败）
	TaskStateCompleted                     // 6 已完成
)
```

`String()` 返回小写英文（`active/pending/scheduled/retry/archived/completed`），未知状态 `panic`。状态转换由 broker 在 Redis 中通过移动不同 key 下的任务完成：

- `pending` →（Forwarder 到期）→ `active`；
- `active` →（成功）→ `completed`/`done`，（失败可重试）→ `retry`，（超限）→ `archived`；
- `scheduled`/`retry` →（ForwardIfReady/Retry 到期）→ `pending`。

`NewTaskInfo` 根据 `TaskState` 设置 `TaskInfo.State`，默认分支 `panic("unknown state")`。

## 序列化与注册

- `NewSerializerTask(t Task)` 将 `Task` 的选项合成为 `Options`，得到可序列化结构；常驻任务/周期任务均以 `SerializerTask` 形式写入 Redis（`DaemonTaskKey` 集合、`DaemonBindingWorker` Hash 等）。
- 任务与处理函数的绑定在消费侧完成：worker 通过 `WorkerMux.Handle(kind, handler)` 注册 `Handler`；常驻任务通过 `taskDefine map[string]OperatorDefine` 注册 `Operator`（`daemon.go`）。详见《03》《05》《06》。

## 结论

`task` 包是 BMW 的统一数据契约：`Task`（生产）→ `SerializerTask`（传输）→ `TaskMessage`（Redis 存储）→ `TaskInfo`（展示）构成一条序列化链路；`Option` 体系以默认值 + 覆盖方式表达队列、重试、超时、去重、延迟等行为；`TaskState` 枚举刻画 pending/scheduled/active/retry/archived/completed 六态生命周期，状态迁移完全由 broker 在 Redis 中移动 key 实现。
