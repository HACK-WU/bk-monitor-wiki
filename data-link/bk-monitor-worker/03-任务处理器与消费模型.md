## 简介

`processor` 包是 BMW 的「消费执行引擎」：`Processor` 从 broker 出队任务、按并发信号量限制并发、调用 `Handler` 执行业务逻辑，并根据结果触发完成/重试/归档；配套的 `Forwarder` 负责将延迟（scheduled/retry）任务按时转回 pending。本篇拆解这两类组件。

## Handler 接口与类型

任务处理的核心接口极简：

```go
type Handler interface {
	ProcessTask(context.Context, *t.Task) error
}
type HandlerFunc func(context.Context, *t.Task) error
// HandlerFunc 适配：func (fn HandlerFunc) ProcessTask(...) { return fn(ctx, task) }

type ErrorHandler interface {
	HandleError(ctx context.Context, task *t.Task, err error)
}
```

- `Handler.ProcessTask` 是任务真正执行的入口，签名与常驻任务 `Operator.Start` 不同（后者接收 `errorReceiveChan`）。
- `ErrorHandler` 可选，在任务失败时回调（如告警/落库），由 `WorkerConfig.ErrorHandler` 注入。

## Processor 结构与启动

```go
type Processor struct {
	Broker          broker.Broker
	Handler         Handler
	QueueConfig     map[string]int
	OrderedQueues   []string          // strict-priority 模式下按优先级排序
	RetryDelayFunc  RetryDelayFunc
	IsFailureFunc   func(error) bool
	ErrHandler      ErrorHandler
	Sema            chan struct{}      // 并发信号量
	ShutdownTimeout time.Duration
	Done, Quit, Abort chan struct{}
}
```

`NewProcessor` 完成组装：`Sema` 容量为 `Concurrency`（默认 `runtime.NumCPU()`）；若 `StrictPriority` 为真，用 `sortByPriority` + `normalizeQueues`（按 GCD 归一化队列权重）生成 `OrderedQueues`；默认 handler 返回「handler not set」错误。`Start(wg)` 起一个 goroutine 循环调用 `Exec`；`Shutdown` 先 `Stop` 再等待所有 `Sema` 释放或 `Abort` 超时。

## 消费循环 Exec

`Exec` 是单轮消费：

1. 尝试向 `Sema` 写入（获取并发令牌）；
2. 从 `Queues()` 返回的队列列表 `Dequeue`（`ErrNoProcessableTask` 时 sleep 1s 释放令牌返回）；
3. 用 `common.NewLease(leaseExpirationTime)` 记录租约，`ComputeDeadline(msg)` 计算截止时间；
4. 起 goroutine：将 `TaskMetadata` 注入 context（`AddTaskMetadata2Context`），先检查 ctx 是否已取消；随后执行 `Perform`；
5. `select` 等待四种结束信号：`Abort`（关停超时，回写队列 `Requeue`）、`lease.Done()`（租约过期，记失败 `HandleFailedMessage`）、`ctx.Done()`（上下文取消）、`resCh`（执行结果）。

```go
p.Sema <- struct{}{}              // 获取令牌
msg, leaseExpirationTime, err := p.Broker.Dequeue(qnames...)
// ...
go func() {
	ctx, cancel := t.AddTaskMetadata2Context(p.BaseCtxFn(), msg, deadline)
	// select ctx.Done() 提前退出
	resCh <- p.Perform(ctx, task)
	// select Abort / lease.Done() / ctx.Done() / resCh
}()
```

## 成功/失败/重试/归档处理

- **成功**：`HandleSucceededMessage` —— 若 `msg.Retention>0` 调用 `MarkAsComplete`（进 completed ZSet），否则 `MarkAsDone`（直接移除）。同时 `RunTaskSuccessTotal` + `RunTaskDurationSeconds` 上报。
- **失败**（`HandleFailedMessage`）：先调 `ErrHandler.HandleError`（若有）；随后判断 `IsFailureFunc(err)`：
  - 非失败错误 → 直接 `Retry(l, msg, err, false)`（不计入失败）；
  - 失败错误且 `msg.Retried >= msg.Retry` 或显式 `skipRetryErr` → `Archive`（最终失败入 archived ZSet）；
  - 否则 `Retry(l, msg, err, true)`。
- **重试**（`Retry`）：`d = RetryDelayFunc(msg.Retried, e, task)`，`retryAt = now + d`，调用 `broker.Retry`（active→retry ZSet）。
- **归档**（`Archive`）：`broker.Archive`（active→archived ZSet，按时间+上限裁剪）。
- `Requeue`：在 `Abort`/关停时把任务回写队列（`lease` 失效则不写，留给 recoverer）。

所有 broker 写操作前均校验 `lease.IsValid()`，无效则跳过（交由独立的 recoverer/lease 过期扫描处理），避免重复写。

## 并发控制与队列优先级

- **并发**：`Sema chan struct{}` 容量 = `Concurrency`，`Exec` 每轮取/还令牌，实现全局并发上限。
- **队列选择**（`Queues()`）：
  1. 单队列 → 直接返回该队列；
  2. 有 `OrderedQueues`（strict-priority）→ 按优先级顺序返回（高优先级先取）；
  3. 否则按 `QueueConfig` 权重把队列名重复铺平（如 `a:2,b:1` → `a,a,b`），随机打散后去重，使权重近似转化为抽取概率。
- `ComputeDeadline`：综合 `Timeout` 与 `Deadline`（取两者较小者；都为 0 时回退 `DefaultTimeout`=30min 并告警）。

## Forwarder 延迟任务转发

`Forwarder` 负责把「时间未到」的任务推到可执行队列：

```go
func (f *Forwarder) Start(wg *sync.WaitGroup) {
	timer := time.NewTimer(f.interval)
	for {
		select {
		case <-f.done: return
		case <-timer.C:
			f.Exec(); timer.Reset(f.interval)
		}
	}
}
func (f *Forwarder) Exec() {
	f.broker.ForwardIfReady(f.queues...) // 将到期的 scheduled/retry 移到 pending
}
```

`interval` 即 `DelayedTaskCheckInterval`（默认 5s，见 `common`）。它只做「到期搬运」，真正的执行仍由 `Processor` 完成。`NewWorker` 中 forwarder 与 processor 共用同一 `rdb` broker 实例。

## 默认重试延迟

`worker.DefaultRetryDelayFunc`（未自定义 `RetryDelayFunc` 时使用）：

```go
func DefaultRetryDelayFunc(n int, e error, t *task.Task) time.Duration {
	r := rand.New(rand.NewSource(time.Now().UnixNano()))
	s := int(math.Pow(float64(n), 4)) + 15 + (r.Intn(30) * (n + 1))
	return time.Duration(s) * time.Second
}
```

退避随重试次数 `n` 呈 **n⁴** 增长（加 15s 基础 + 随机抖动），即重试越多次延迟越大，避免风暴。注意该退避与常驻任务维护器的重试退避（见《06》）是**两套独立机制**。

## 结论

`processor` 是 BMW 异步/周期任务的执行引擎：`Processor` 通过信号量控制并发、按权重/优先级选取队列、出队后 `Perform` 并在多路 `select` 中处理租约过期/关停/取消/结果四类信号；成功进 completed/done，失败按 `RetryDelayFunc`（默认 n⁴ 退避）重试，超限归档；`Forwarder` 周期性把延迟任务搬回 pending。整个消费模型与 asynq 高度相似，是 BMW 可靠执行异步任务的核心保障。
