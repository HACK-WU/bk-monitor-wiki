## 简介

常驻任务是 BMW 三类任务中最特殊的一类：进程不死循环、不返回，需被「维护器」长期保活、失败自动重试、并定期上报心跳。其实现不在 `processor`，而在 `service/scheduler/daemon` 包，由 **调度面（Watcher/Numerator）+ 执行面（RunMaintainer）+ 任务分发（Binding）** 三层协同完成，并通过 `task` 模块的 HTTP API 接收外部指令。本篇完整拆解这条链路。

## Operator 接口与任务注册

常驻任务必须实现 `Operator` 接口：

```go
type Operator interface {
	Start(runInstanceCtx context.Context, errorReceiveChan chan<- error, payload []byte)
	GetTaskDimension(payload []byte) string
}
```

- `Start`：主逻辑入口；死循环**必须**监听 `runInstanceCtx.Done()` 退出；可预知的错误通过 `errorReceiveChan` 发送，维护器据此判定失败并重试。
- `GetTaskDimension`：返回心跳维度（如 APM 预计算的 `DataId`），维护器据此上报 `daemon_running_task_count{task_dimension=...}`。

任务通过 `taskDefine map[string]OperatorDefine` 注册，`OperatorDefine` 含 `initialFunc(ctx) (Operator, error)` 用于获取单例。内置三类：

| Kind | 实现 |
|------|------|
| `daemon:apm:pre_calculate` | `apmTasks.Initial(ctx)`（APM 预计算） |
| `daemon:alarm:cmdb_resource_watch` | `cmdbcache.ResourceWatchDaemon` |
| `daemon:alarm:cmdb_cache_refresh` | `cmdbcache.CacheRefreshDaemon` |

`ComputeTaskUniId` 用 `GetTaskDimension(payload)` 的返回值（空则回退 payload 本身）计算任务唯一 ID，保证任务更新时 UniId 不变。

## 任务分发：Binding 双写

`Binding` 维护两份 Redis Hash 的双写关系，是「task↔worker」分配的核心：

- `DaemonBindingTask()`：field=taskUniId，value=workerId（「这个任务被分到哪个 worker」）；
- `DaemonBindingWorker(workerId)`：field=taskUniId，value=taskBinding（「这个 worker 上跑了哪些任务」）。

`GetBinding()` 返回单例。`addTask(t)` 内部：`computeWorkerId(t)` 从 `WorkerKeyQueuePrefix(queue)*` 随机选一个存活 worker → `ComputeTaskUniId` → `addBinding` 双写两份 Hash。`deleteBinding`/`deleteWorkerBinding` 做反向清理（worker 下线时把其任务重新 `addTask` 再分配）。

## 调度面：Watcher 与 Numerator

常驻任务调度器 `TaskScheduler{watcher, numerator}`（由 `NewDaemonTaskScheduler` 创建）负责把「任务集合」正确映射到「worker 绑定」：

- **DefaultWatcher**（`start()` 起三路监听）：
  - `watchWorker`：周期扫描 `WorkerKeyPrefix*`，worker 上下线 → `handleAddWorker`/`handleDeleteWorker`（下线时 `deleteWorkerBinding` 触发再分配）；
  - `watchTask`：监听 `DaemonTaskKey()` 集合（SMembers），任务增删 → `handleAddTask`/`handleDeleteTask`（写/删 Binding）；
  - `watchReloadRequest`：订阅 `DaemonReloadReqChannel()`，收到 reload 请求后 `reassign`（合并 payload 并通知目标 worker 重载）。
- **DefaultNumerator**：周期（`SchedulerDaemonTaskNumeratorInterval`，默认 60s）做一致性校验——`checkWorkerCorrect`（binding 指向不存在的 task 则删）、`checkTaskCorrect`（task 无 binding 则补加、binding 指向失效 worker 则删），保证 task↔worker 映射最终一致。

## 执行面：RunMaintainer

worker 进程通过 `NewDaemonTaskRunMaintainer(ctx, workerId)` 启动执行面（`RunMaintainer`）：

- 构造时遍历 `taskDefine` 调 `initialFunc` 得到每个 `Kind` 的 `Operator` 单例（`methodOperatorMapping`）；`listenTaskKey = DaemonBindingWorker(workerId)`、`listenReloadKey = DaemonReloadExecQueue(workerId)`。
- `Run()`：周期（`WorkerDaemonTaskMaintainerInterval`，默认 5s）`HGetAll(listenTaskKey)`，对比本地 `taskMarkMapping`，新增 → `handleAddTaskBinding`，消失 → `handleDeleteTaskBinding`。
- `handleAddTaskBinding`：取出 `Operator`，`go define.Start(runInstanceCtx, errorReceiveChan, payload)` 启动常驻逻辑，并起 `listenRunningState` 监控该实例。

```go
go define.Start(runInstanceCtx, errorReceiveChan, taskBinding.Payload)
go r.listenRunningState(taskBinding.UniId, errorReceiveChan, checkerCtx, define.GetTaskDimension(taskBinding.Payload))
```

## 失败重试与心跳指标

`listenRunningState` 是常驻任务的「保活+重试」核心：

- **心跳**：每 30s `metrics.RecordDaemonTask(taskDimension)` → 上报 `daemon_running_task_count{task_dimension}`（Gauge 置 1）。
- **失败重试**：监听 `errorReceiveChan`：
  - 收到 `ReloadSignal` → `reloadCount++`，下次重试间隔 `tolerateInterval=10s`；
  - 收到普通错误 → `retryCount++`；若 `retryCount < RetryTolerateCount`（默认 60）则用 10s，否则用 `maxTolerateInterval=15min`（**超过阈值后重试间隔 2X 级增长**）；
  - `retryTicker` 到期 → 重新 `define.Start` 拉起实例，并 `metrics.RecordDaemonTaskRetryCount`。
- 收到根 ctx 取消 / lifeline 取消 → 清理 `runningInstance` 并退出。

这与《03》异步任务的 n⁴ 退避是**两套独立机制**：常驻任务用「容忍次数阈值 + 10s/15min 两档」策略。

## 重新加载流程

常驻任务更新（如修改 payload）走「reload」而非「重启进程」：

1. `task` 模块 API `ReloadDaemonTask` → 写入 `DaemonReloadReqHash()(taskUniId→newPayload)` 并向 `DaemonReloadReqChannel()` 发 taskUniId；
2. `DefaultWatcher.watchReloadRequest` 收到 → `reassign`：读取新 payload，`overrideAndUpdateTaskPayload`（合并映射，**维度字段不可改**否则 UniId 不一致报错），更新 `DaemonTaskKey` 集合；
3. 若已有 Binding → `addReloadExecuteRequest` 向 `DaemonReloadExecQueue(workerId)` 发布任务；
4. 目标 worker 的 `RunMaintainer.listenReloadSignal` 订阅该频道，收到 → `handleReloadBinding` 把新 binding 写入 `errorReceiveChan` 一个 `ReloadSignal{}`；
5. `listenRunningState` 收到 `ReloadSignal` → 取消旧实例 ctx、以新 payload 在 10s 后重新 `Start`。

## HTTP API

常驻任务通过 `task` 模块的 HTTP 服务（`cmd/task.go` → `http.NewHTTPService()`，端口 `TaskListenPort=10211`）管理，路由（`http/http.go`）：

| 方法 | 路径 | Handler | 说明 |
|------|------|---------|------|
| GET | `/bmw/task/` | `ListTask` | 列出运行中的常驻任务 |
| POST | `/bmw/task/` | `CreateTask` | 启动常驻任务 |
| DELETE | `/bmw/task/` | `RemoveTask` | 删除常驻任务 |
| DELETE | `/bmw/task/<DeleteAllTaskPath>` | `RemoveAllTask` | 删除全部 |
| POST | `/bmw/task/<DaemonTaskReloadPath>` | `ReloadDaemonTask` | 重新加载（reload） |

请求体示例（`kind` 如 `daemon:demo:demo`，`payload` 为参数，`options.queue` 指定队列），详见 README。

## 结论

常驻任务子系统是 BMW 区别于普通任务队列的关键能力：以 `Operator` 接口定义「死循环任务」，由 `Binding` 在 Redis 中维护 task↔worker 双写映射，调度面 `Watcher`/`Numerator` 保证映射最终一致，执行面 `RunMaintainer` 在 worker 侧拉起实例、每 30s 上报 `daemon_running_task_count`、失败后按「10s/15min 两档」重试，并通过 `DaemonReloadReqChannel`/`DaemonReloadExecQueue` 实现不停机 reload。整条链路完全基于 Redis 原语，与异步/周期任务共享同一 broker 底座。
