## 简介

除核心五层（接收/处理/上报/调度/配置）之外，collector 还依赖一组辅助模块支撑元数据缓存、指标自监控、启动与配置热更新：`cache` 提供 K8s Pod 元数据缓存；`pusher` 把 collector 自身运行指标经 GSE 上报；`internal` 是跨层复用的工具集（信号量、限流、JSON、HTTP 中间件等）；`cmd/collector` 是进程入口，负责 beat 初始化、Controller 装配与 reload 收敛；`sidecar` 则监听 K8s Secret 中子配置变化并发送 reload 信号。这些模块共同保障 collector 在生产环境的可用性与可观测性。

## cache（K8s 缓存、Install/Uninstall）

`cache` 包是缓存安装的总入口，`Install(conf)` 从 `cache` 子配置解出 `Config`（一组 `Entity{Name, Config}`），按 `entity.Name` 分派；当前仅支持 `k8scache.Name`（`"k8s_cache"`），用 `mapstructure.Decode` 反序列化后 `Validate` 并 `k8scache.Install`；`Uninstall()` 直接调用 `k8scache.Uninstall()`（未安装时为 noop）。

`k8scache.Cache` 是一个基于 HTTP 拉取的 Pod 元数据缓存：

- 以 `IP → {k8s.bcs.cluster.id, k8s.pod.name, k8s.namespace.name, k8s.pod.ip}` 的 map 存储；
- `Sync()` 在 `synced` 由 false→true 时启动 `loopSync`，按 `Interval`（默认 1 分钟）周期调用 `sync()`；`sync()` 带 `resourceVersion` 增量拉取，对 `Delete` 删除缓存、`CreateOrUpdate` 写入属性；`sync()` 启动时先执行一次；
- `Get(k)` 供运行时（如 processor）按 Pod IP 取元信息；
- `Install/Uninstall` 维护包级 `defaultCache` 单例，`Uninstall` 经 `Clean()` 关闭 `done` 通道退出循环。

该缓存为 K8s 环境下的数据补全（如注入 Pod 维度标签）提供低延迟查询源。

## pusher（指标自监控）

`pusher` 包把 collector 自身运行指标上报到监控后端。`Pusher` 接口仅含 `Start()/Stop()`，提供 `noopPusher`（空白实现，非关键路径失败时兜底）。`New(ctx, conf)`：先 `Unpack` 主机配置（失败则用 `noopPusher` 代替），再用 `beat.NewGsePusherWithConfig` 构造 GSE pusher 并挂 `prometheus.DefaultGatherer`，返回 `metricsPusher`。

`metricsPusher.Start()` 启动 `watcher`（主机信息监听），读取内网 IP / CloudID / BizID / HostID，调用 `updateLabels` 设置固定标签（`bk_component=bk-collector`、`bk_biz_id`、`bk_cloud_id`、`bk_host_innerip`、`bk_host_id`），再 `StartPeriodPush` 周期上报；`handleHostIDWatcherNotify` 监听主机信息变更并热更新标签；`Stop` 取消 ctx、停 watcher、停 pusher。

## internal 工具集

`internal` 是跨接收层、处理层、上报层复用的工具集合，按职责拆分为独立子包（约 25 个），典型包括：

- `semaphore`：并发信号量控制；
- `throttle`：限流（接收层鉴权后使用）；
- `json`：统一 JSON 序列化（被 gse.MarshalFunc 引用）；
- `httpmiddleware` / `grpcmiddleware`：HTTP / gRPC 中间件（鉴权、trace 注入）；
- `mapstructure` / `mapstrings`：结构体与 map 互转（子配置 Decode 用）；
- `metacache`：token 等元信息运行时缓存（`confengine.LoadConfigPath` 写入）；
- `metricsbuilder` / `promlabels` / `labels`：指标与标签构造；
- `generator` / `fields` / `foreach` / `opmatch` / `optmap`：数据遍历与字段操作辅助；
- `tokenparser`：Token 解析；
- `wait`：`wait.Until` 用于 worker 在 ctx 取消后自动重启/退出；
- `random` / `prettyprint` / `utils` / `testkits`：随机、格式化、通用工具与测试脚手架。

这些工具包被各业务层按需引用，避免重复实现通用逻辑（如 Exporter 用 `json`/`wait`，Controller 用 `hook`/`wait`，cache 用 `mapstructure`/`json`）。

## cmd 入口（collector / sidecar）

`cmd/collector/main.go` 是 collector 主进程入口：

1. 用 `beat.InitWithPublishConfig(appName, version, pubConfig, settings)` 初始化 beat（发布模式 `GuaranteedSend`）；
2. `controller.New(confengine.New(config), buildInfo)` 装配并 `Start`；
3. 进入主循环监听三类信号：`beat.ReloadChan`（reload 信号）、`timer.C`（10 秒收敛，避免频繁 reload 拉高 CPU）、`beat.Done`（结束信号，`Stop` 后退出）；
4. 收到 reload 时读取 `beat.GetConfig()` 并调 `collector.Reload(confengine.New(conf))`。

`cmd/sidecar` 则是 sidecar 进程的入口（与下述 `sidecar` 包配合），独立运行以管理 K8s 子配置。

## sidecar（子配置热更新）

`sidecar` 包运行在 sidecar 进程内，负责监听 K8s Secret 中子配置变更并驱动 collector reload。核心结构 `Sidecar` 持有 `config` 与 `secretManager`：

- `New(ctx, config)`：设置 `KUBECONFIG` 环境变量，构造 TLS 配置并创建 K8s 客户端（`k8sutils.NewK8SClient`）；
- `Start()`：先 `sm.Start()`，再进入循环监听 `s.sm.Watch()`（子配置增删改事件）——收到事件后调用 `handleChildConfigFiles` 落盘，并用 `smTimer`（5 秒）**收敛**多次变更，到点统一 `sendReloadSignal()`；`ctx.Done` 时退出；
- `sendReloadSignal()`：读取 `PidPath` 中的 collector PID，向该进程发送 `syscall.SIGUSR1`（collector 收到后触发 reload），实现"子配置变 → 信号 → 主进程热更新"的闭环。

`secretManager`（见 `secret.go`）负责监听指定 Secret、把其中的子配置文件同步到本地目录并产出变更事件；子配置内容经 `confengine` 加载后成为 `TierConfig` 的 instance/service/default 级配置（详见 `10-配置系统ConfEngine`）。

## 结论

辅助模块补全了 collector 的工程能力：`cache`（K8s Pod 元数据缓存）为数据补全提供低延迟查询；`pusher` 把自身运行指标经 GSE 上报实现自监控；`internal` 复用约 25 个工具子包统一限流/序列化/中间件等通用逻辑；`cmd/collector` 入口负责 beat 初始化、Controller 装配与 reload 收敛；`sidecar` 监听 Secret 子配置变更并经 `SIGUSR1` 驱动主进程热更新。它们与核心五层共同构成完整、可观测、可热更新的采集链路。
