## 简介

transfer 的配置有两条主线：一是**运行期配置**（viper 实例封装为 `define.Configuration`，承载 consul 路径、http 端口、scheduler 类型等），二是由 consul 下发的**元数据配置**（描述每个 data_id / 结果表 / 存储集群如何 ETL 与分发）。前者由 `cmd/root.go` 的 `initConfig` 加载，后者由 `config/metadata.go` 中的结构体承载并经 Context 注入管道。

## viper 加载与 initConfig

transfer 使用 cobra 的 `OnInitialize(initConfig)` 在根命令启动时加载配置（`cmd/root.go`）。`initConfig()` 的执行逻辑如下：

1. **配置文件定位**：若通过 `--config/-c` 指定了配置文件，则 `viper.SetConfigFile(cfgFile)` 直接使用；否则以当前工作目录为搜索路径，按 `define.AppName` 作为配置名查找默认配置文件。
2. **环境变量绑定**：通过 `v.SetEnvPrefix(define.AppName)`、`v.AutomaticEnv()` 开启自动环境变量读取，并用 `v.SetEnvKeyReplacer(strings.NewReplacer(".", "_"))` 把配置键中的 `.` 映射为 `_`，使形如 `TRANSFER_HTTP_PORT` 的环境变量能够覆盖嵌套配置。
3. **配置实例构造**：以 `define.NewViperConfiguration(v)` 将 viper 实例封装为 `define.Configuration`。
4. **consul 路径版本解析**：读取 `consul.path_version`（`ConfKeyPathVersion`），为空时走 `parseV0Path`（原样返回），否则走 `parseV1Path`（默认 v1 路径规则，按集群维度重排 service/manual/data_id 路径前缀，并把 `--host`/`--port` 覆盖到 `http.host`/`http.port`）。
5. **前后置钩子**：在读取前后分别发布 `EvSysConfigPreParse` / `EvSysConfigPostParse` 事件，由 `define/hook.go` 等订阅者设置默认值（http 主机/端口、payload 类型、pipeline 严格模式与并发数等）。

`config/viper.go` 在 `init()` 中完成全局单例装配：`Configuration = define.NewViperConfiguration(viper.GetViper())`，并提供 `NewConfiguration()` 工厂以创建独立 viper 实例。

## 配置分类（元数据模型）

`config/metadata.go` 定义了一组描述"数据如何 ETL 与分发"的元数据结构体，这些结构体由 consul 下发的 JSON 反序列化而来：

- **`MetaClusterInfo`**：统一描述每种存储集群（Kafka / Elasticsearch / InfluxDB / Redis）的连接与路由信息，含 `ClusterConfig` / `StorageConfig` / `AuthInfo` 三段 map，以及 `ClusterType`、`BatchSize`、`BulkConcurrency`、`FlushInterval`、`ConsumeRate` 等运行参数；`Clean()` 负责空 map 兜底，`MustGet*` 系列在缺失键时 panic。
- **`MetaFieldConfig`**：结果表字段定义，含 `FieldName`/`AliasName`、`Type`(`MetaFieldType`)、`Tag`(`MetaFieldTagType`)、`Option`、`DefaultValue`、`Disabled`；`Name()` 优先返回别名，`Path()` 取真实路径。
- **`MetaResultTableConfig`**：单个结果表配置，含 `ResultTable`、`SchemaType`、`FieldList`、`ShipperList`（各存储集群的 `MetaClusterInfo`）、`MultiNum`；提供 `VisitFieldByTag`（按 metric/dimension/group 遍历字段）、`ShipperListGroupByType`、`MappingResultTable` 等便捷方法。
- **`PipelineConfig`**：一条数据管道配置，含 `DataID`、`TypeLabel`、`MQConfig`(MetaClusterInfo)、`ETLConfig`、`ResultTableList`；`Clean()` 负责子结构清理与默认值。
- **`RuntimeConfig`**：运行时参数（如 `PipelineCount`），可经 `RuntimeConfigIntoContext` 注入。

## 配置注入与 Context

配置与元数据通过 `context.Context` 在处理链路各节点间传递，避免全局变量耦合：

- `config.FromContext(ctx)` / `config.IntoContext(ctx, conf)`：读写全局 `define.Configuration`（底层 key 为 `define.ContextConfigKey`）。
- `config.MetadataConfig` 接口的 `Clean()`：各元数据结构体在构建前统一清洗。
- `metadata.go` 提供成对的 Context 助手，把具体元数据注入/取出管道：
  - `ShipperConfigIntoContext` / `ShipperConfigFromContext`（key：`ContextShipperKey`）
  - `MQConfigIntoContext` / `MQConfigFromContext`（key：`ContextMQConfigKey`）
  - `PipelineConfigIntoContext` / `PipelineConfigFromContext`（key：`ContextPipelineKey`）
  - `ResultTableConfigIntoContext` / `ResultTableConfigFromContext`（key：`ContextResultTableKey`）
  - `RuntimeConfigIntoContext` / `RuntimeConfigFromContext`（key：`ContextRuntimeKey`）

`cmd/transfer.go` 在 `Run` 中即调用 `config.IntoContext(ctx, conf)` 把全局配置注入上下文，随后 `Scheduler` 构建的 pipeline 节点再从中取出各自的 shipper / mq / result_table 配置。

## 结论

transfer 的配置体系分为"运行期配置"（viper → `define.Configuration`，含 consul v0/v1 路径版本解析）与"元数据配置"（consul 下发的 `MetaClusterInfo` / `MetaResultTableConfig` / `PipelineConfig` 等）两层。前者由 `cmd/root.go` 的 `initConfig` 加载并封装，后者由 `config/metadata.go` 描述并经 `context.Context` 注入到各 pipeline 节点。这种"配置抽象 + Context 注入"的设计，使 transfer 能完全由 consul 配置驱动、无需重启即可热更新数据处理逻辑。
