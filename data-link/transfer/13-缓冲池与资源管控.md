## 简介

为减少高频 `bytes.Buffer` 分配带来的 GC 抖动，transfer 抽出 `bufferpool` 包提供全局复用池；同时 `main` 包的 `resource_limits.go` 监听 `eventbus` 的资源限制事件（`EvSysLimitCPU`/`EvSigLimitResource`），在运行时收敛 `GOMAXPROCS` 等资源占用，避免单实例挤占宿主。

## BufferPool 缓冲池

`bufferpool` 仅一个文件，核心是包级 `sync.Pool`：

```go
var pool = sync.Pool{
    New: func() interface{} {
        return bytes.NewBuffer(make([]byte, 0, 1024))
    },
}

func Get() *bytes.Buffer { return pool.Get().(*bytes.Buffer) }
func Put(b *bytes.Buffer) { b.Reset(); pool.Put(b) }
```

`Get` 取一个 1KB 预分配的 buffer；`Put` 先 `Reset()` 清空内容再归还，避免脏数据跨复用。该池无锁、线程安全，是 transfer 内几乎所有文本序列化（JSON 拼装、索引名拼接、record ID 计算等）的统一步伐。

## 缓冲池的使用场景

`bufferpool` 在热路径被广泛使用，例如：

- `elasticsearch/backend.go` 的 `makeRecordID`（拼接 uniqueField 计算 xxhash `_id`）与 `flush`（读取响应体到 buffer）均通过 `bufferpool.Get()/Put()` 复用 buffer。
- 各 ETL/序列化环节对 `ETLRecord` 的 `To`/`From` 编解码也复用同一池。

统一复用显著降低了每秒数十万级数据点下的分配速率与 GC STW 时间。

## 资源限制管控

`resource_limits.go` 在 `init()` 中订阅两个事件：

- `EvSysLimitCPU`：收到 CPU 上限（可为绝对值或 `0~1` 的比例）后，经 `getLimitsValue` 换算为核数，对 `runtime.NumCPU()` 取比例或绝对值，`>0` 时 `runtime.GOMAXPROCS(max)` 限制并行度。
- `EvSigLimitResource`：收到信号驱动的资源限制（`params` 含 `cpu` 等键值），转 float 后逐键处理，动态收敛资源占用。

比例模式下（`value < 1`）按宿主总资源乘比例计算上限，便于容器/虚拟化环境按配额运行。

## 结论

`bufferpool` 以极简的 `sync.Pool` 封装统一了高频 `bytes.Buffer` 复用，是 transfer 抗 GC 压力的关键；`resource_limits.go` 则通过事件总线在运行时动态约束 CPU/资源，使 transfer 能在多租户或受限环境中平稳运行。
