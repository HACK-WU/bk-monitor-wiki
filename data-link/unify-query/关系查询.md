## 概述

关系查询（`/api/v1/relation/*`）用于前端拓扑/关联分析。其核心结论：**relation 查询并不直接调用 CMDB 实时 API**，而是由 bk-monitor-worker 预先把 CMDB 关系事实派生为 Prometheus 虚拟指标（`*_relation`/`*_info_relation`），unify-query 用图算法计算资源路径，再转成 PromQL 走与 `query/ts` **同一套 tsdb/prometheus 查询层**。详见 [API接口说明.md](API接口说明.md)。

## cmdb v1beta1 模型与图算法

`cmdb.CMDB` 接口（`cmdb/cmdb.go#L16-L22`）仅暴露 `QueryResourceMatcher`（瞬时）与 `QueryResourceMatcherRange`（区间）两个方法。实现体 `*model`（`cmdb/v1beta1/v1beta1.go`）持有一张有向图 `g graph.Graph[string,string]`（`v1beta1.go#L158-L162`）：

- `newModel`：把资源当顶点、关系当边构建拓扑图（`v1beta1.go#L166-L226`）。
- `getPaths`：用 `graph.AllPathsBetween` 求 source→target 的**所有路径**，按最短优先排序并按 `path_resource` 过滤（支持节点屏蔽）（`v1beta1.go#L277-L341`）。
- 资源/关系 schema 来自 `utils/relation/default_config.go`（默认含 22 种资源、26 条关系，覆盖 CMDB/K8s/APM），经 `config_adapter.go` 转换为 v1beta1 `Config`（Required 字段→Index 主键，否则→Info 扩展）。

```mermaid
flowchart LR
    A[RelationMultiResourceRequest] --> B[GetModel 取图模型]
    B --> C[getPaths 求所有路径]
    C --> D[doRequest 逐路径转 QueryTs]
    D --> E[DirectQuery/Range 走 tsdb]
    E --> F[聚合为 MatchersWithTimestamp]
```

## 查询处理链路

以 `HandlerAPIRelationMultiResource`（`api/api.go#L37-L110`）为例：

1. 解码为 `cmdb.RelationMultiResourceRequest`（`cmdb/struct.go#L42-L56`）：`QueryList` 每项含 `timestamp`/`source_type`/`source_info`/`target_type`/`path_resource`/`look_back_delta` 等。
2. `metadata.GetUser(ctx)` → `v1beta1.GetModel(ctx, spaceUID)` 取模型。
3. `ants` 协程池（size=`RelationMaxRouting`）对每个 `qry` 并行调 `QueryResourceMatcher`。
4. `queryResourceMatcher`（`v1beta1.go#L343-L431`）：反推资源类型 → `getPaths` 求路径 → 逐路径 `doRequest`。
5. `doRequest`（`v1beta1.go#L492-L621`）：`QueryFactory.MakeQueryTs` 将路径转成 `structured.QueryTs`，关系指标名按 `{a}_with_{b}_relation` 规则生成，`ToPromQL` 后调用 `instance.DirectQuery`/`DirectQueryRange`——**即共享的 tsdb 查询层**；结果聚合成 `[]cmdb.MatchersWithTimestamp`。
6. handler 组装 `cmdb.RelationMultiResourceResponse`（`TraceID`+`Data[]`）返回（`cmdb/struct.go#L59-L75`）。

## 与 query/ts 的共用与独立

**共用**：同属 `public` 组，共用 MetaData+JWT 中间件；`doRequest` 最终使用 `prometheus.GetTsDbInstance`/`NewInstance` 调 `DirectQuery`/`DirectQueryRange`，与 `query/ts` 同一 Prometheus/VM 实例；复用 `query/structured.QueryTs` 与 PromQL 生成；共享 `metadata.GetUser` 上下文与 Redis 中的资源关系 schema。

**独立**：走独立路由 `/api/v1/relation/*`，不经 `HandlerQueryTs` 主流程；不进入 `space.Router` 多存储路由选择，属一对一 PromQL 直查；查询的是 worker 预写的关系虚拟指标（非用户原始业务指标），并显式 `SetIsSkipK8s(true)`；handler 侧用 `ants` 协程池并发多个 `QueryList` 子查询。

> 一句话：**relation 查询走 tsdb 层（与 query/ts 同一套查询实例），但不走 query/ts 的 handler 主流程，也不实时调用 CMDB HTTP API**——CMDB 集成是"离线派生 + 指标化"模式。

## 典型使用场景

1. **拓扑路径还原**：给定资源实例（如 `pod`）向上/向下追溯关联资源（`pod→node→system`、`host→module→set→business`）。
2. **CMDB 业务集定位**：从主机维度反查所属业务/集群/模块，用于详情抽屉关联展示。
3. **指标联动下钻**：`target_info_show`/`source_expand_info` 返回 `*_info_relation` 扩展属性（如 `env_name`/`service_version`）。
4. **区间"时间旅行"**：`multi_resource_range` 查看某时间段内关联关系变化。
5. **批量展开**：`QueryList` 支持一次请求多个关联查询，协程池并发。
