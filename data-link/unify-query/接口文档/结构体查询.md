## 接口说明

| 项 | 值 |
|----|----|
| 方法 / 路径 | POST `/query/ts` |
| Handler | `HandlerQueryTs` |
| 鉴权 | `MetaData` + `JwtAuth`（公共分组） |
| 用途 | 以结构化指标/维度/过滤条件发起时序查询，支持多子查询与 `metric_merge` 二次运算 |

## 请求示例

```json
{
  "space_uid": "bkcc__2",
  "query_list": [
    {
      "reference_name": "a",
      "table_id": "system.cpu_summary",
      "field_name": "usage",
      "function": [{"method": "MEAN", "dimensions": ["bk_target_ip"]}],
      "time_aggregation": {"method": "SUM", "window": "1m"},
      "conditions": {"field_list": [{"field": "bk_target_ip", "operator": "=", "value": ["10.0.0.1"]}]},
      "dimensions": ["bk_target_ip", "bk_target_cloud_id"]
    }
  ],
  "metric_merge": "a",
  "start_time": "1657848000",
  "end_time": "1657851600",
  "step": "1m",
  "down_sample_range": "5m",
  "timezone": "Asia/Shanghai",
  "instant": false,
  "reference": true,
  "order_by": ["-_time"],
  "limit": 0,
  "from": 0
}
```

## 响应示例

成功时直接返回 `PromData`（HTTP 200，无 `code/data` 包裹）：

```json
{
  "series": [
    {
      "name": "_result0",
      "metric_name": "system.cpu_summary.usage",
      "columns": ["_time", "_value"],
      "types": ["time", "double"],
      "group_keys": ["bk_target_cloud_id", "bk_target_ip"],
      "group_values": ["0", "10.0.0.1"],
      "values": [
        [1657848000, 12.5],
        [1657848060, 13.1]
      ],
      "stat": {"avg": 12.8, "max": 13.1, "min": 12.5, "count": 2}
    }
  ],
  "status": {"series_limit_reached": false, "is_partial": false},
  "trace_id": "a1b2c3d4",
  "is_partial": false,
  "result_table_id": ["system.cpu_summary"]
}
```

错误响应（`ErrResponse`，HTTP 400）：

```json
{"trace_id": "a1b2c3d4", "error": "space_uid not found"}
```

## 请求字段说明

请求体为 `QueryTs`（`query/structured/query_ts.go#L42-L112`）。

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `space_uid` | string | 否 | 空间 UID；通常由 `X-Bk-Scope-Space-Uid` 头注入并覆盖 |
| `query_list` | array[Query] | 否 | 子查询列表，元素结构见下文 |
| `metric_merge` | string | 否 | 多子查询二次运算表达式（PromQL 语法），用 `reference_name` 引用，如 `"a + b"` |
| `order_by` | array[string] | 否 | 排序字段，前缀 `-` 表示倒序，如 `["_time","-_time"]` |
| `result_columns` | array[string] | 否 | 指定保留返回的字段值 |
| `start_time` / `end_time` | string | 否 | 起止时间，单位秒级时间戳 |
| `step` | string | 否 | 步长，如 `"1m"` |
| `down_sample_range` | string | 否 | 降采样周期，需大于 `step` 才生效 |
| `timezone` | string | 否 | 时区，如 `"Asia/Shanghai"` |
| `look_back_delta` | string | 否 | 偏移量 |
| `instant` | bool | 否（默认 false） | 是否瞬时数据 |
| `reference` | bool | 否 | 查询开始时间是否对齐 |
| `not_time_align` | bool | 否 | 查询开始时间与聚合是否对齐 |
| `limit` / `from` | int | 否 | 点数限制 / 翻页起始 |
| `scroll` | string | 否 | 是否启用 Scroll 查询（原始数据滚动查询使用） |
| `slice_max` | int | 否 | 最大切片数量 |
| `is_multi_from` / `is_search_after` | bool | 否 | MultiFrom / SearchAfter 查询开关 |
| `clear_cache` | bool | 否 | 是否强制清理缓存会话 |
| `result_table_options` | object | 否 | 结果表选项 |
| `highlight` | object | 否 | 是否开启高亮 |
| `dry_run` | bool | 否 | 是否启用 DryRun |
| `is_merge_db` | bool | 否 | 是否合并 db |
| `add_dimensions` | array[string] | 否 | 额外聚合维度，与 `function.dimensions` 合并 |
| `tsdb_map` | map | 否 | 路由匹配 tsDB 列表，key 为 `reference_name` |

### 返回字段与请求字段的映射关系

`PromData`（及其 `TablesItem`）的返回字段并非独立于请求，而是与请求字段存在如下映射（均由 `prom_data.go` 的 `Fill` 生成）：

| 返回字段 | 与请求字段的映射关系 | 源码依据 |
|---------|-------------------|---------|
| `group_keys` / `group_values` | 来自返回时序（series）实际携带的标签（维度）**键 / 值集合**；由请求 `dimensions`（以及 `function[].dimensions`、`add_dimensions`）指定的**分组维度**驱动。请求告诉查询"按哪些维度分组"，存储层据此返回对应标签，`group_keys` 收集这些标签的键名（按字母序排序）。即：二者呈"请求定义分组维度 → 返回携带对应标签"的因果关系，而非把 `dimensions` 列表原样搬回——仅实际产生取值差异的维度会出现为不同分组；若某维度被 `conditions` 固定为单一值或经聚合消除，其取值恒定但仍作为标签出现。 | `prom_data.go` Fill L108 `tableItem.GroupKeys = table.GroupKeys`；底层 `influxdb/tables.go` L222-L239 / `query/promql/tables.go` L44-L60 由 series 的 tags/labels 填充 |
| `columns` / `values` | `columns` 仅由时间列 `_time`、数值列 `_value` 组成，**分组维度不进入 `columns`**，其取值落在 `group_values` 中，因此 `values` 每行通常为 `[时间戳, 数值]`（顺序依查询引擎：promql 路径为 `[_time, _value]`，结构化/influxdb 路径为 `[_value, _time]`）。返回示例统一以 `[_time, _value]` 可读顺序展示。 | `prom_data.go` Fill L106-L140（group key 在 L117-L120 被排除出 `columns`） |
| `metric_name` | 由查询翻译层根据 `query_list[].table_id` + `.field_name` 生成的 `MetricName` 传入（如 `system.cpu_summary.usage`）；经 `Fill` L105 赋给 `tableItem.MetricName`。PromQL 路径（`/query/promql`）因无显式指标名，通常为空。 | `influxdb/tables.go` L194 `t.MetricName = metricName`（上游 `metricName` 源自 `table_id`+`field_name`）；赋值点 `prom_data.go` Fill L105 |
| `result_table_id` | 由请求 `table_id` 经 `QueryReference` 路由解析得到的结果表列表 | `prom_data.go` L30-L31、L61-L63 |
| `stat` | 由该 series 的 `values` 点集计算得到（`count`/`sum`/`min`/`max`/`avg`/`last`） | `prom_data.go` Fill L141 `ComputeStatFromPoints` |
| `is_partial` / `status` | 与是否触发了请求 `down_sample_range`、`limit` 等参数相关 | `prom_data.go` L27-L29 |

> 小结：你的猜测方向正确——`group_keys` 确实由请求的 `dimensions` 决定，但其来源是"返回数据中每个 series 实际携带的标签集合"，而不是 `dimensions` 列表的直接回显。本接口文档的返回示例已同步修正：维度不再写入 `columns`/`values`，而是落在 `group_keys`/`group_values`（如请求 `dimensions: ["bk_target_ip","bk_target_cloud_id"]` → 返回 `group_keys: ["bk_target_cloud_id","bk_target_ip"]`）。

错误响应为 `ErrResponse`：`{"trace_id": "...", "error": "..."}`（`service/http/response.go#L96-L99`）。
