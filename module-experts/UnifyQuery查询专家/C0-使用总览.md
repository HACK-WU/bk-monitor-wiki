# UnifyQuery 使用总览

## 能力清单

`UnifyQuery` 是 BK-Monitor 中查询时序/日志/维度数据的统一 Python 门面类，业务代码通过它执行查询，无需关心后端是"统一查询 HTTP 服务"还是"各数据源原生查询"。

| 能力 | 对应方法 | 说明 |
|------|----------|------|
| 时序数据查询 | `query_data()` | 按 `metrics`/`group_by`/`interval` 查询时序聚合数据 |
| 时序数据+统计 | `query_data_with_stat()` | 同上，额外返回每个 series 的统计信息 |
| 引用数据查询 | `query_reference()` | 查询某个序列的最新值（分页级别的引用查询） |
| 原始日志查询 | `query_log()` | 查询原始采集数据（日志/事件），剥离聚合 |
| 维度值查询 | `query_dimensions()` | 查询某个维度字段的取值列表 |
| 下推原生查询 | `_query_data_using_datasource` | 不经过统一查询后端，直连数据源存储 |

**关键区分**：`(BK_MONITOR_COLLECTOR, TIME_SERIES)` 数据源**恒走统一查询后端分支**（`use_unify_query()` 对其始终返回 `True`），不会进入原生查询分支。

## 能力边界

`UnifyQuery` 不负责：
- 数据源的定义与注册（由 `load_data_source` 工厂和元数据模块管理）
- 表名/字段的真实含义（由 `ResultTable` 模型和初始化数据确定）
- 权限校验（由上层调用方处理 `bk_biz_id` / `space_uid` 转换）
- 结果的后处理与展示（由调用方自行处理 `list[dict]` 返回值）

## 已知问题与常见坑

| # | 现象 | 触发条件 | 正确做法 |
|---|------|----------|----------|
| 1 | instant 查询行为与非 instant 完全不同 | `instant=True` 时会：① `step` 强制覆盖为 `"1m"`；② **保留 `end_time` 边界点**（非 instant 会丢弃）；③ 仅返回 `end_time` 单点 | 详见 [C1-能力契约.md#5-instant-参数深度说明](C1-能力契约.md#5-instant-参数深度说明) |
| 2 | 多数据源 `query_dimensions` 退化为全量拉取 | `data_sources` 多于 1 个时，用 `query_data` 拉全量再在 Python 侧去重 | 尽量使用单数据源的维度查询 |
| 3 | `metrics` 多条目对应多条 `query_list` | `to_unify_query_config` 把每个 metric 展开为独立 `query_list` 条目 | 多条目是为关联计算设计的（如 `A/B`），不是批量独立查询 |
| 4 | `AVG` 对应 `avg_over_time + mean` 两层聚合 | 方法名 `"AVG"` 不在 `AggMethods` 中，走 else 分支生成 `time_aggregation` | 用 `avg_without_time` 获得不跨时间聚合的瞬时值 |
| 5 | `query_log` 的 `total` 在统一查询路径下恒为 `0` | 真实总数只在原生查询路径（`_query_log_using_datasource`）返回 | 如需精确总数，确认数据源是否走原生分支，或前置获取 |
| 6 | 时间对齐在 `not_time_align=False` 时发生 | `get_unify_query_params` 会调 `time_interval_align` 对齐到步长边界 | 如需精确的时间范围边界，设 `not_time_align=True` |
