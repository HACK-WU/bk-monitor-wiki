# UnifyQuery 能力契约

## 1. 构造 UnifyQuery 实例

### 1.1 工厂函数 `load_data_source`

**用途**：通过 `(data_source_label, data_type_label)` 二元组获取对应的 `DataSource` 子类。

**参数**：
- `data_source_label`：`DataSourceLabel` 枚举，常用值 `BK_MONITOR_COLLECTOR`、`CUSTOM`、`BK_DATA`、`BK_LOG_SEARCH`、`BK_FTA` 等
- `data_type_label`：`DataTypeLabel` 枚举，常用值 `TIME_SERIES`、`LOG`、`EVENT`、`ALERT` 等

**返回值**：`DataSource` 子**类**（非实例），如 `BkMonitorTimeSeriesDataSource`

**约束**：
- `(BK_MONITOR_COLLECTOR, TIME_SERIES)` 返回的类在 `use_unify_query()` 中恒走统一查询后端分支

### 1.2 查询描述对象

**用途**：实例化 `data_source_class`，构造查询描述。这是传给 `UnifyQuery` 的核心数据。

**参数**：

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `bk_biz_id` | int | 是 | 业务 ID |
| `interval` | int | 否 | 聚合窗口（秒），如 `180` 表示 3 分钟 |
| `metrics` | list[dict] | 是 | 指标列表，每项 `{field: str, method: str, alias: str}` |
| `table` | str | 是 | 结果表 ID，如 `"system.proc"`、`"system.cpu_summary"` |
| `group_by` | list[str] | 否 | 维度字段列表，如 `["bk_host_id", "display_name", "pid"]` |

**metrics 字段说明**：
- `field`：真实指标名，来自 ResultTable 的 metric 字段（如 `cpu_usage_pct`、`usage`）
- `method`：聚合方法，如 `"AVG"`、`"SUM"`、`"COUNT"`、`"MAX"`、`"MIN"`，或 `"avg_without_time"`（不跨时间聚合）
- `alias`：在 `expression` 中的引用名，如 `"A"`

**约束**：
- `method="AVG"` 等普通方法会生成两层聚合（`avg_over_time` + `mean`）；用 `*_without_time` 变体获得不跨时间聚合的瞬时值
- `group_by` 是分组边界，不同 group 互相独立，聚合在组内进行
- 多 `metrics` 会展开为多条 `query_list` 条目，各自有独立的 `reference_name`

### 1.3 `UnifyQuery` 构造

**参数**：

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `data_sources` | list[DataSource] | 是 | 查询描述对象列表 |
| `bk_biz_id` | int | 是 | 业务 ID |
| `expression` | str | 否 | 指标引用表达式，如 `"a"` 表示只查 alias=A 的指标，`"a/b"` 表示比值 |
| `functions` | list | 否 | 额外 PromQL 函数 |
| `time_alignment` | bool | 否 | 是否时间对齐（默认 True） |

**约束**：
- `expression` 可以绑定多个 data_source 的 metrics 做关联计算
- `bk_biz_id` → `space_uid` / `bk_tenant_id` 的转换在构造时自动完成，不进 query 项

**典型构造示例**（来自实际使用场景）：
```python
data_source_class = load_data_source(DataSourceLabel.BK_MONITOR_COLLECTOR, DataTypeLabel.TIME_SERIES)
data_source = data_source_class(
    bk_biz_id=bk_biz_id,
    interval=180,
    metrics=[{"field": "proc_exists", "method": "AVG", "alias": "A"}],
    table="system.proc_port",
    group_by=["bk_host_id", "bk_target_ip", "bk_target_cloud_id", "display_name"],
)
query = UnifyQuery(data_sources=[data_source], bk_biz_id=bk_biz_id, expression="a")
```

## 2. 公开查询方法

### 2.1 `query_data()`

**用途**：查询时序聚合数据，是**最常用**的入口。

**参数**：
- `start_time`：开始时间（datetime 或 时间戳）
- `end_time`：结束时间
- `limit`：返回条数限制
- `instant`：是否瞬时查询（仅返回 `end_time` 单点）
- `not_time_align`：是否跳过时间对齐

**返回**：`list[dict]`，每项含 `_time_`、`_result_` 及所有 `group_by` 维度字段

**典型调用**：
```python
records = query.query_data(start_time=start_time, end_time=end_time)
# records: [{"_time_": 1716946200000, "_result_": 60.2, "bk_host_id": 1, "display_name": "nginx", ...}, ...]
```

**约束**：
- `(BK_MONITOR_COLLECTOR, TIME_SERIES)` 恒走统一查询后端（`POST /query/ts`）
- `instant` 参数改变查询行为——详见 [第 5 节 instant 参数深度说明](#5-instant-参数深度说明)

### 2.2 `query_data_with_stat()`

**用途**：查询时序数据并返回每个 series 的统计信息。

**参数**：同 `query_data()`

**返回**：`{"series": list[dict], "series_stat": dict}`，`series_stat` 以 `(dimensions_hash, metric_field)` 为 key

**与 `query_data` 的差异**：唯一差异是 `with_series_stat=True`，后端返回每个 series 的 `stat` 字段。

### 2.3 `query_reference()`

**用途**：查询某个序列的引用数据（最新值），常用于分页引用场景。

**参数**：同 `query_data()` 基础上额外支持 `limit`、`offset`、`order_by`

**返回**：`list[dict]`

**与 `query_data` 的差异**：
- 调用统一查询后端的 `POST /query/ts/reference`
- 不设置 `down_sample_range`
- `limit/from` 是**每条子查询**级别（与 `query_data` 顶层 `slimit` 语义不同）

### 2.4 `query_log()`

**用途**：查询原始采集数据（日志/事件），剥离所有聚合。

**参数**：同 `query_data()` 基础上额外支持 `limit`、`offset`

**返回**：`(list[dict], total)` 二元组

**与 `query_data` 的差异**：
- 调用 `POST /query/ts/raw`
- 逐条剥离 `function`、`field_name`、`time_aggregation`
- `total` 在统一查询路径下恒为 `0`（仅原生路径返回真实总数）
- **不支持 `instant`** 参数

### 2.5 `query_dimensions()`

**用途**：查询指定维度字段的取值列表。

**参数**：`dimension_field`（维度字段名）

**返回**：`list`（维度值列表，如 `["nginx", "java", "redis"]`）

**分叉行为**：
- **单数据源**：复用 `to_unify_query_config()[0]` 走 `/query/ts/info/tag_values` 维度查询端点
- **多数据源**：退化为 `query_data()` 全量拉取再内存去重（性能差）

**约束**：
- 尽量使用单数据源，避免多数据源退化

## 3. 两层聚合机制与函数映射速查

`metrics[].method` 在 `to_unify_query_config` 中会被分解为**两个独立的聚合层**，分别控制不同的聚合维度：

```
  第二层 function.method（跨 series 聚合）
        ↓
  avg by (dim1, dim2) (
      avg_over_time(cpu_usage[5m])           ← 第一层 time_aggregation（时间轴聚合）
  )
```

| 聚合层 | 字段 | 聚合对象 | 做什么 | 典型示例 |
|--------|------|----------|--------|----------|
| **第一层** | `time_aggregation.function` | 单个时间序列的**时间轴** | 对每条 series 在 `[T-window, T]` 内的多个原始采样点做窗口聚合 → 1 个平滑值 | `avg_over_time`：把 N 个原始采集点压缩为 1 个平均值 |
| **第二层** | `function[0].method` | 同一 group 内的**多条 series** | 在同一个时间点上，跨不同 series（不同维度值）做组内聚合 → 1 个组值 | `mean`：同 group 内多条 series 取算术平均 |

**关键理解**：
- `time_aggregation.window` = `interval`（单位秒），如 `180s`；若无 interval 则回退为 `1h`
- `function[0].dimensions` = `group_by` 列表，定义分组边界。**不同 group 互相隔离，绝不跨组混合**
- `avg` → `function[0].method="mean"` 而非 `"avg"`（`count` → `"sum"` 同理），这是 PromQL 的惯用映射

### 聚合函数映射速查

| 传入 method | time_aggregation.function | time_aggregation.window | function[0].method | 说明 |
|------------|--------------------------|------------------------|-------------------|------|
| `AVG` / `avg` | `avg_over_time` | `{interval}s` | `mean` | **标准两层**：先时间平滑再分组平均 |
| `SUM` / `sum` | `sum_over_time` | `{interval}s` | `sum` | 先时间求和再分组求和 |
| `COUNT` / `count` | `count_over_time` | `{interval}s` | `sum` | 先时间计数再分组求和 (= 总点数和) |
| `MAX` / `max` | `max_over_time` | `{interval}s` | `max` | 先时间取 max 再分组合并 |
| `MIN` / `min` | `min_over_time` | `{interval}s` | `min` | 先时间取 min 再分组合并 |
| `avg_without_time` | **不写**（跳过时间层） | — | `avg` | 只做分组 avg，不跨时间聚合 |
| `sum_without_time` | **不写**（跳过时间层） | — | `sum` | 只做分组 sum，不跨时间聚合 |
| `cp50` / `cp95` / `cp99` | `histogram_quantile` + `vargs_list` | `{interval}s` | `mean` | 分位数，额外带 `position` / `vargs_list` |

### `_without_time` 变体的用途

当**不希望跨时间聚合**（即不想做 `avg_over_time` 平滑）时使用：
- 原始采集点已经很稀疏（如 1 分钟一个点），再做 3 分钟窗口聚合反而丢失细节
- 场景：取某个进程在特定时刻的瞬时值（不是一段时间的平均值）
- 注意：即使跳过时间聚合，**分组聚合仍然执行**（`avg` / `sum` 等）

## 4. 关键映射：入参 → 最终 HTTP 请求

| 调用侧入参 | 最终落点 |
|-----------|----------|
| `metrics[*].field` | `query_list[*].field_name` |
| `method="AVG"` | `function[0].method="mean"` + `time_aggregation={"function":"avg_over_time","window":"<interval>s"}` |
| `table` | `query_list[*].table_id`（data_label 未传则 `table.lower()`） |
| `group_by` | 同时写入 `dimensions` / `function[0].dimensions` / `keep_columns` |
| `interval` | 决定 `time_aggregation.window`；普通查询 `step="<interval>s"`，instant 覆盖为 `"1m"` |
| `expression` | `metric_merge`（PromQL 表达式） |
| `bk_biz_id` | 转为 `space_uid` / `bk_tenant_id`，不直接进 query 项 |
| `metrics` 多条目 | 平铺为 query_list 多条，各自 `reference_name=a0~aN` |

## 5. instant 参数深度说明

**`instant` 参数是 UnifyQuery 最重要的开关之一**。有 `instant=True` 和没有 `instant` 时，查询行为完全不同。不仅影响返回的数据点数量，还影响**数据内容本身**。

### 6.1 行为差异对照表

| 行为 | `instant=False`（默认） | `instant=True` |
|------|------------------------|----------------|
| **返回点数** | 整个时间区间内按 `step` 采样多个评估点 | 仅返回 `end_time` 一个评估点 |
| **`step` 参数** | 来自 `interval`（如 `"180s"`） | **强制覆盖为 `"1m"`** |
| **`end_time` 边界点** | **丢弃**（`process_unify_query_data` 中当 `_time_==end_time` 时 skip） | **保留**（不 skip） |
| **聚合函数** | 不变 | 不变（`avg_over_time` + `mean` 照常执行） |
| **下推到原生查询** | 正常 | `instant` **被忽略**（不走 `_query_data_using_datasource` 时 `instant` 不传递） |
| **`start_time`** | 正常传入 | 正常传入（**不会被重算**） |
| **`end_time`**（builder 层） | 不变 | 若调用 `UnifyQuerySet.instant(align_interval=...)` 则 end_time **前移**一个 interval |

### 6.2 `end_time` 边界点丢弃——最关键差异

这是 `instant` 参数被用户感知的**最直接影响**：

> **非 instant 模式**：SaaS 侧策略是**丢弃时间戳等于 `end_time` 的最后一条数据**。原因是在时序 chart 中，end_time 边界点通常只采集了半个采样周期，会被视为不完整点并排除。
>
> **instant 模式**：**保留 `end_time` 边界点**。因为 instant 本身就是查"此刻"的瞬时值，丢弃边界点会导致结果为空。

**实际影响**：同一时间范围 `[T-start, T]`，非 instant 返回的是 `[T-start, T)` 内的数据点（不含 T），而 instant 返回的是 T 时刻的数据点。

示例（`end_time = 1716946200`，对应 `2024-05-29 10:30:00`，interval=180s）：

| 模式 | `_time_` 返回 | 说明 |
|------|-------------|------|
| 非 instant | `1716946020000`（10:27:00）等 | 最后一个点不是 10:30:00 |
| instant | `1716946200000`（10:30:00） | 只返回 end_time 这一个点 |

### 6.3 Builder 层 `align_interval` 补偿机制

`UnifyQuerySet.instant(align_interval=N)` 在调用 `instant=True` 的同时，还会**把 `end_time` 减去 `align_interval`**：

```python
# builder.py 的逻辑
clone.query.set_end_time(clone.query.end_time - align_interval)
```

**设计意图**：非 instant 丢掉的是 `end_time` 点；instant 保留 `end_time` 点。如果希望 instant 和非 instant 对"同一时刻"的数据达成一致，需要把 instant 的 end_time 往前推一个 interval——这样 instant 返回的就是 `end_time - interval` 时刻的点，恰与非 instant 模式的最后一个有效点对齐。

### 6.4 典型使用模式

**模式 1：普通时序图表查询（非 instant）**
```python
# 不做 instant()，返回整个时间范围的数据点序列
records = query.query_data(start_time=start, end_time=end)
```

**模式 2：瞬时快照查询（instant）**
```python
# 只取 end_time 这个时刻的值
records = query.query_data(start_time=start, end_time=end, instant=True)
```

**模式 3：带对齐的瞬态查询（builder 层）**
```python
# UnifyQuerySet 链式调用：取 end_time - interval 时刻的值
qs.time_agg(False).instant(align_interval=interval).limit(1)
```

### 6.5 约束与限制

- **仅对统一查询后端路径有效**：`_query_data_using_datasource` 分支不受 `instant` 影响
- `(BK_MONITOR_COLLECTOR, TIME_SERIES)` 恒走统一查询后端，故 `instant` **始终生效**
- instant 模式下 `step="1m"` 是**采样步长**，不是聚合窗口；聚合窗口仍然由 `interval` → `time_aggregation.window` 决定
- 不要在 instant 模式下依赖 `start_time` 的值——即便传入，后端也只看 `end_time` 单点
