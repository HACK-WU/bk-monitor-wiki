## 决策清单

### 决策 1：架构设计-数据源分三级接入统一查询（全量 / 灰度 / 未接入），不一次性切换
- **分类**：架构设计
- **动机**：避坑（一次性全量切换的失败风险，见下方 commit 证据）；可维护性（各数据源能力不同，需逐个验证）
- **决策**：`UnifyQuery.use_unify_query()` 按数据源 id（`(data_source_label, data_type_label)`）分三级判定：
  - **全量**（`UnifyQueryDataSources`，3 类）：`(BK_MONITOR_COLLECTOR, TIME_SERIES)`、`(CUSTOM, TIME_SERIES)`、`(BK_APM, EVENT)` —— 恒走统一查询后端
  - **灰度**（`GrayUnifyQueryDataSources`，7 类）：APM 日志 / RUM 日志 / 自定义事件 / 计算平台时序 / 主机采集日志 / 日志检索（LOG、TIME_SERIES）—— 由各数据源的 `switch_unify_query(bk_biz_id)` 决定
  - **未接入**：不在上述两个列表中 → 恒走数据源原生查询（`_query_data_using_datasource`）
- **背景约束**：① 数据源是逐批迁移的（计算平台 2024-01 灰度 → Trace 检索 2025-04 灰度 → 日志 2025-11/2026-03 → 枚举值 2026-08），各批次查询语义与后端能力不一致；② 灰度期间同一份代码对不同业务可能走不同链路。
- **被否决方案**：
  - 一次性全量切换（不分灰度）：否决理由 —— commit e0900310e3 标题即标注「(灰度)」，其后 dc07f88329、c925aacf09 连续两次「bkdata数据查询灰度unify-query查询失败问题修复」，说明分阶段切换是踩坑后的选择
  - 仅按数据源类型判定、不做能力判定：否决理由 —— 多数据源联合查询、表达式、查询函数、分位数等场景原生路径不支持，必须无条件走统一查询（代码注释：「如果是多指标，必然会走统一查询模块」「使用特殊函数必须走统一查询模块」）
- **已知代价**：切换状态耦合 `settings`（`BKDATA_USE_UNIFY_QUERY_GRAY_BIZ_LIST`、`*_UNIFY_QUERY_BLACK_BIZ_LIST`、`IS_ACCESS_BK_DATA`）与 `settings.ROLE`，同一查询在不同环境/业务可能走不同链路，问题难复现。
- **重新评估触发条件**：灰度业务列表包含 0 业务（代码注释约定「灰度列表包含 0 业务即全量」）后，可移除灰度分支；或新增数据源类型接入
- **关联代码**：`UnifyQuery.use_unify_query` @ unify_query/query.py；`UnifyQueryDataSources` / `GrayUnifyQueryDataSources` @ constants/data_source.py
- **证据来源**：代码注释（use_unify_query 各判定分支：「如果是多指标，必然会走统一查询模块」「灰度切换unify-query判定，不灰度就全量放开」）；commit e0900310e3、dc07f88329、c925aacf09、8e9217a8a3、485290b5a6、f0453a87d6

### 决策 2：接口契约-灰度数据源的切换判定：能力强制开启 + 黑名单反向豁免
- **分类**：接口契约
- **动机**：避坑（原生路径不支持某能力时静默出错）；止损（出问题时用黑名单快速切回，而非改代码发布）
- **决策**：灰度数据源的 `switch_unify_query(bk_biz_id)` 采用**黑名单**语义——默认走统一查询，命中黑名单的业务不走；同时把「仅统一查询支持的能力」设为无条件开启：
  - 能力强制：`_value` 排序（TopK）、`query_string` 非 `*`（nested 场景）、日志聚类表（`_clustered` 后缀）、自定义事件 `group_by` 含 `type`（聚合补 0）→ 直接返回 `True`
  - 黑名单：`*` 在黑名单中 → 全部业务不走统一查询；否则 `bk_biz_id` 或其字符串形式命中黑名单 → 不走
  - 计算平台（`BkdataTimeSeriesDataSource`）走另一套：**白名单灰度 + 特殊场景豁免**——web 角色恒走；有 functions 恒走；`metrics` 多于 1 个（特殊逻辑）**不走**（用 bksql）；灰度期按 `BKDATA_USE_UNIFY_QUERY_GRAY_BIZ_LIST` 判定，列表含 0 即全量
- **背景约束**：黑名单用于线上快速止损；但某些能力原生路径根本没有，黑名单也不能把它们切回原生。
- **被否决方案**：统一用白名单（默认不走、逐个放开）：否决理由 —— 无相关记录；从现状看黑名单语义可让新业务自动纳入统一查询，减少维护成本
- **已知代价**：黑名单命中即整业务降级，粒度粗（无法按场景豁免）；且与「能力强制开启」规则冲突时以能力优先，黑名单对该场景无效。
- **重新评估触发条件**：出现「某能力需要按业务维度豁免」的需求（当前黑名单无法覆盖）；或黑名单长期为空、可移除
- **关联代码**：`BaseBkMonitorLogDataSource.switch_unify_query`（TopK `_value` / nested `query_string` / 黑名单）/ `LogSearchTimeSeriesDataSource.switch_unify_query`（日志聚类 `_clustered` 后缀 + 黑名单）/ `BkMonitorLogDataSource.switch_unify_query`（自定义事件 `group_by` 含 `type` 聚合补 0，子类 `CustomEventDataSource` 继承）/ `BkdataTimeSeriesDataSource.switch_unify_query`（灰度业务列表 + 特殊场景豁免）@ data_source/__init__.py
- **证据来源**：代码注释（「如果业务在黑名单中，则不使用 UnifyQuery」「* 在黑名单中，则不使用 UnifyQuery」「_value 是内置的聚合排序（TopK）关键字，仅 UnifyQuery 支持」「query_string 可能存在 nested 场景，仅 UnifyQuery 支持」「聚合补 0 仅 UnifyQuery 支持」「不支持一次查询多个指标，使用 bksql」「灰度状态：灰度业务列表不包含0业务表示灰度中」）

### 决策 3：接口契约-排序统一用虚拟时间字段 `_time`，由统一查询后端按 `time_field` 替换
- **分类**：接口契约
- **动机**：避坑（时间字段硬编码 → 排序被静默丢弃或查询报错）
- **决策**：`get_unify_query_params` 的 `order_by` 未显式传入时默认 `["-_time"]`，使用统一查询的**虚拟时间字段** `_time`，而不是各数据源的真实时间字段名（如 `time` / `dtEventTimeStamp`）。
- **背景约束**：bkdata / bklog 等索引以 `dtEventTimeStamp` 为时间字段，硬编码 `time` 时统一查询后端要么静默丢弃该排序条件（降级为不排序），要么命中 keyword 类型导致查询报错。
- **被否决方案**：按数据源 `DEFAULT_TIME_FIELD` 取真实字段名拼 `order_by`：否决理由 —— 见上述背景，硬编码/直取真实字段名在跨源场景下不可靠
- **重新评估触发条件**：统一查询后端取消虚拟字段 `_time` 支持；或某数据源的时间字段无法被正确替换
- **关联代码**：`UnifyQuery.get_unify_query_params` @ unify_query/query.py
- **证据来源**：代码注释（query.py：「使用 unify-query 虚拟时间字段 "_time"，会按 query_list 中的 time_field 替换为真实时间字段。背景：但在 bkdata / bklog 等以 dtEventTimeStamp 为时间字段的索引上，硬编码为 time 要么被 uq 静默丢弃（降级为不排序），要么命中 keyword 导致查询报错」）

### 决策 4：接口契约-instant 语义：step 固定 `1m`，且保留 `end_time` 边界点
- **分类**：接口契约
- **动机**：一致性（instant 是查「此刻」的瞬时值，按非 instant 规则丢弃边界点会返回空）
- **决策**：`instant=True` 时 ① 请求参数追加 `instant=True` 且 **`step` 被覆盖为 `"1m"`**（忽略原 interval 计算出的 step）；② 结果后处理 `process_unify_query_data` 中**保留** `_time_ == end_time` 的点（非 instant 会丢弃）。Builder 侧 `instant(align_interval=N)` 通过前移 `end_time` 补偿，使 instant 返回值与非 instant 丢弃边界点后的最后一个有效点对齐。
- **背景约束**：① 非 instant 模式下 `end_time` 边界点采集周期不完整，图表中应排除；② `step` 只是采样步长，真正的聚合窗口是 `time_aggregation.window`（由 `interval` 决定），因此 instant 覆盖 step 不改变聚合语义。
- **被否决方案**：instant 沿用原 step / 沿用非 instant 的边界点丢弃规则：否决理由 —— 前者返回点数不可控；后者在「当前时刻无完整采集点」时返回空
- **已知代价**：instant 查询的 `step` 参数失效（固定 1m）；`start_time` 不受 instant 影响，仍原样下传；instant 对 `_query_data_using_datasource`（原生）分支无效。
- **重新评估触发条件**：需要 instant 查询返回自定义步长数据；或统一查询后端调整 instant 的边界点语义
- **关联代码**：`UnifyQuery._query_unify_query`（`step = "1m"`）、`UnifyQuery.process_unify_query_data`（边界点丢弃分支）@ unify_query/query.py；`UnifyQuerySet.instant(align_interval=...)` @ unify_query/builder.py
- **证据来源**：代码注释（query.py：「使用 instant 查询时 step 固定为 1m」「如果是最后一条数据，且时间戳等于结束时间，不返回」且该分支带 `not params.get("instant")` 条件；builder.py `UnifyQuerySet.instant`：「时序数据在 SaaS 侧的处理策略为「丢弃最后一个时间戳为 end_time 的点」。瞬时量（instant）在相同时间范围内是返回时间戳为 end_time 的点。为保证瞬时和时序行为一致（end_time - interval），instant 的 end_time 需要往前推一个 interval」）

### 决策 5：接口契约-时间对齐默认开启，通过 `not_time_align` 显式关闭
- **分类**：接口契约
- **动机**：一致性（对齐到步长边界，避免同一步长内出现半个采集周期的点）
- **决策**：`get_unify_query_params` 在 `time_alignment=True` 且 `not_time_align=False` 时，把 `start_time` / `end_time` 经 `time_interval_align(秒, step)` 对齐到步长边界；`query_data` / `query_data_with_stat` 提供显式入参 `not_time_align=True` 关闭对齐。
- **背景约束**：图表按固定步长渲染，未对齐的时间边界会产生不完整数据点。
- **被否决方案**：无（未找到相关记录）
- **已知代价**：需要精确时间边界的查询（如告警比对、日志示例时间对齐）必须显式传 `not_time_align=True`，否则边界会被移动。
- **重新评估触发条件**：出现「时间范围被对齐导致边界数据缺失/时间不一致」的反馈累计 ≥ 2 次
- **关联代码**：`UnifyQuery.get_unify_query_params` @ unify_query/query.py
- **证据来源**：commit 565e246744、caabd6675b（「unify-query 接口增加一个参数 not_time_align」）、b3ea4eb131（「优化 unify-query 时间对齐判定」）；代码实现（time_interval_align 分支）

### 决策 6：接口契约-两层聚合：`time_aggregation`（时间轴）+ `function`（跨 series），并提供 `*_without_time` 变体
- **分类**：接口契约
- **动机**：一致性（同时支持 PromQL 风格与 InfluxDB 风格的聚合语义）
- **决策**：`TimeSeriesDataSource.to_unify_query_config` 把 `metrics[].method` 拆成两层：普通 method（`avg`/`sum`/`count`/`max`/`min`）→ `time_aggregation = {"function": "<method>_over_time", "window": "<interval>s"}` + `function[0].method`（`avg`→`mean`、`count`→`sum`）；`AggMethods` 中的 `*_without_time` 变体（5 种：sum/avg/count/min/max）→ **不生成 `time_aggregation`**，只做跨 series 聚合（PromQL 风格）；`CpAggMethods`（cp50/90/95/99）→ `time_aggregation.function = "histogram_quantile"` 并带 `vargs_list` / `position`。
- **背景约束**：同一查询既要「时间窗口平滑」又要「同组多条 series 归并」，二者是独立维度；部分场景（如进程实例数、稀疏采集点）需要跳过时间聚合。
- **被否决方案**：单一聚合层（只做时间聚合或只做跨 series 聚合）：否决理由 —— 无法同时表达两种语义；从 `AggMethods` 与 `CpAggMethods` 的并存结构看，两层拆分是必须的
- **已知代价**：`method="AVG"` 实际是 `avg_over_time` + `mean` 两层，与调用方直觉不符（C0 已知问题 4）；需要瞬时值必须显式用 `avg_without_time`。
- **重新评估触发条件**：需要新的聚合语义（如不跨 series 也不跨时间的原始点直出）且两层模型无法表达
- **关联代码**：`TimeSeriesDataSource.to_unify_query_config` @ data_source/__init__.py；`AggMethods` / `CpAggMethods` @ unify_query/functions.py
- **证据来源**：代码实现（if/else 两分支 + `_over_time` 生成）；functions.py 中 `AggMethods` 各条目 `name` 字段标注「(PromQL)」；项目记忆 `专题记忆/数据源查询机制` 已有「count_without_time 与 COUNT 聚合语义差异」条目

### 决策 7：[推测] 架构设计-统一查询分支失败不回退原生查询
- **分类**：架构设计（本条为推测，查询侧请降级使用）
- **动机**：可维护性（两条链路返回结构与口径不同，自动回退会掩盖问题）
- **决策**：`_query_data_internal` 中统一查询分支异常时被 `except` 捕获、仅上报 Prometheus 指标（`DATASOURCE_QUERY_COUNT` 带 `status`/`exception`）后**直接抛出**，不会改走 `_query_data_using_datasource`。
- **背景约束**：统一查询与原生查询的结果结构、聚合口径、字段命名存在差异，静默切换会导致同一查询在不同时刻返回不同口径的数据。
- **被否决方案**：无（未找到相关记录）
- **已知代价**：统一查询服务故障时查询整体失败，调用方需自行兜底（降级/重试/提示）。
- **重新评估触发条件**：出现统一查询后端大面积不可用且需要保底查询（可观测判据：UQ 分支 5xx/异常占比 > 1%）
- **关联代码**：`UnifyQuery._query_data_internal` @ unify_query/query.py
- **证据来源**：无直接证据，基于 try/except 捕获异常后仅 `labels` 上报并在末尾 `raise exc`、except 块内未调用原生查询分支的实现结构推断

### 决策 8：接口契约-`query_log` 强制剥离聚合与函数
- **分类**：接口契约
- **动机**：一致性（原始日志查询不需要聚合语义）
- **决策**：`_query_log_using_unify_query` 对 `query_list` 的每一项覆盖 `function=[]`、`field_name=""`、`time_aggregation={}`，再调用 `api.unify_query.query_raw`。
- **背景约束**：日志原始记录查询取的是文档本身，聚合与函数无意义且会改变返回结构。
- **被否决方案**：无（未找到相关记录）
- **已知代价**：统一查询路径下 `query_log` 返回的 `total` 恒为 0，精确总数只在原生查询分支（`_query_log_using_datasource`）返回（C0 已知问题 5）。
- **重新评估触发条件**：统一查询后端在 `query_raw` 中支持返回总数
- **关联代码**：`UnifyQuery._query_log_using_unify_query` @ unify_query/query.py
- **证据来源**：代码注释（query.py：「原始日志查询，无需聚合及函数」）；代码实现（`query.update({"function": [], "field_name": "", "time_aggregation": {}})`）

### 决策 9：兼容处理-多数据源 `query_dimensions` 退化为全量拉取 + Python 侧去重
- **分类**：兼容处理
- **动机**：可维护性（统一查询的维度查询接口只支持单数据源，多源场景需自行兜底）
- **决策**：`data_sources` 多于 1 个时，`query_dimensions` 只取 `dimension_field[0]`（列表入参降级为首个字段），调用 `query_data` 拉取全量数据后在 Python 侧用 `set` 去重返回；单数据源且 `supports_unify_query_dimensions` 为真时才走 `_query_dimensions_using_unify_query`。
- **背景约束**：维度值查询需要后端聚合去重能力，多数据源联合查询下无法下推。
- **被否决方案**：无（未找到相关记录）
- **已知代价**：全量拉取受 `limit` 截断影响，维度值可能不全；大数据量场景性能差（C0 已知问题 2）。
- **重新评估触发条件**：统一查询后端支持多数据源维度查询；或出现「维度下拉值不全」的反馈
- **关联代码**：`UnifyQuery.query_dimensions` @ unify_query/query.py
- **证据来源**：代码实现（`if len(self.data_sources) > 1` 分支内 `query_data` + set 去重）

### 决策 10：兼容处理-返回结构的三重兜底（无 series / 缺 `_result_` / 多表维度后缀）
- **分类**：兼容处理
- **动机**：避坑（统一查询后端不同版本/不同场景返回结构差异 → 解析直接报错或丢字段）
- **决策**：`process_unify_query_data` 中 ① `data.get("series") or []` 兜底无 series 字段的响应；② 单指标无 `_result_` 列时回退取 `query_list[0]["reference_name"]` 对应的值；③ 多表关联产生的维度名后缀 `_tableN` 由 `RE_DIMENSION_SUFFIX` 剥离还原（如 `bk_target_ip_table0` → `bk_target_ip`）。
- **背景约束**：统一查询后端是独立服务（datalink），返回结构演进不受本仓库控制。
- **被否决方案**：无（未找到相关记录）
- **已知代价**：兜底逻辑使解析层与后端结构耦合，后端结构调整时需同步维护正则与回退规则。
- **重新评估触发条件**：统一查询后端固化返回结构并移除上述差异（可移除兜底）；或出现新的返回结构差异导致解析异常
- **关联代码**：`UnifyQuery.process_unify_query_data`、`UnifyQuery.extract_unify_query_series_dimensions`、`UnifyQuery.RE_DIMENSION_SUFFIX` @ unify_query/query.py
- **证据来源**：commit 11360d44a8（「兼容unify-query数据查询无series字段的情况」）；代码注释（「单指标情况下避免缺少_result_字段」「维度名可能带多表关联后缀 "_tableN"…此处将其剥离还原为原始维度名」）

### 决策 11：架构设计-租户与空间参数在构造期统一注入，不由调用方逐条拼装
- **分类**：架构设计
- **动机**：避坑（多租户下漏传 `bk_tenant_id` → 鉴权失败或跨租户数据误判，见场景视图侧的同类修复 commit bf4bab8141）
- **决策**：`UnifyQuery.__init__` 中未显式传 `bk_tenant_id` 时由 `bk_biz_id` 推导；推导失败则记录 warning 并取 `DEFAULT_TENANT_ID`；随后对**每个** data_source 调用 `set_bk_tenant_id` 注入。`space_uid` 由 `bk_biz_id_to_space_uid` 转换并以 `cached_property` 延迟计算。
- **背景约束**：多租户改造后，每个子查询都必须带上租户标识，逐条拼装易漏。
- **被否决方案**：无（未找到相关记录）
- **已知代价**：租户推导失败时静默降级为默认租户（只 warning），可能掩盖配置错误。
- **重新评估触发条件**：出现「租户推导失败但未被发现」的线上问题；或默认租户策略调整
- **关联代码**：`UnifyQuery.__init__`、`UnifyQuery.space_uid` @ unify_query/query.py
- **证据来源**：commit 3c2f49a154（「数据查询模块支持多租户改造」）、fe7bfc819b（「chore: unify-query支持多租户主动传参」）；代码注释（「如果未传入租户ID，则根据业务ID获取租户ID」「设置租户ID」）

### 决策 12：架构设计-后台查询提供类 ORM Builder（`QueryConfigBuilder`），替代 dict 拼装
- **分类**：架构设计
- **动机**：可维护性（各场景重复拼装查询 dict，冗长且易错）
- **决策**：新增 `unify_query/builder.py`，提供 `QueryConfigBuilder` / `UnifyQuerySet`，复用已有 datasource 模块，让后台以类 ORM 链式调用（`.table().metric().group_by().conditions()`）构造查询，再由 Builder 转成 `query_list` / `query_configs`。
- **背景约束**：① 统一查询结构原本由前端拼接参数，后台只负责解析；② APM 存在预计算路由、服务接口统计等需要后台对多结果表做聚合查询的复杂场景。
- **被否决方案**：继续在各场景手写 dict 拼装：否决理由 —— 模块文档明确「每个场景的查询都在进行相似的数据结构拼装，过于重复冗长」
- **已知代价**：新增一层抽象，简单查询也要走 Builder；两套构造方式（直接构造 `UnifyQuery` vs Builder）并存。
- **重新评估触发条件**：Builder 无法表达某类查询（需回退手写 dict）；或 dict 直构方式被完全取代
- **关联代码**：`QueryConfigBuilder`、`UnifyQuerySet` @ unify_query/builder.py
- **证据来源**：模块级文档字符串（builder.py「做了什么：复用已有 datasource 模块，支持使用类 ORM 模式进行 UnifyQuery 查询 / 背景：…APM 存在预计算路由，服务接口统计等复杂查询场景… / 解决了什么问题？…每个场景的查询都在进行相似的数据结构拼装，过于重复冗长，基于 unify[query_configs] 场景进行类 ORM 的封装」）

### 决策 13：性能取舍-ES 批处理 `is_es_batch` 默认关闭，由调用方按需 opt-in
- **分类**：性能取舍
- **动机**：优化（APM Trace 跨结果表查询的批量 ES 读取性能）
- **决策**：统一查询 `query_raw` 的可选参数 `is_es_batch` **缺省时不发送**（不改变其他调用方行为）；仅 APM Trace 的跨结果表 Trace 查询（`TraceQuery.query_by_trace_ids`）显式传 `is_es_batch=True`；前端资源参数不暴露该开关。
- **背景约束**：批处理是性能优化手段，未经验证前不应影响既有调用方的行为与返回。
- **被否决方案**：全局开启 ES 批处理：否决理由 —— 会改变所有 `query_raw` 调用方的行为，风险面过大（commit body 明确「缺省时不发送，不改变其他调用方行为」「调用范围由 APM Trace 服务端控制」）
- **已知代价**：需要该优化的场景必须逐个显式开启，收益面受限。
- **重新评估触发条件**：批处理被验证稳定且需要推广到更多场景；或出现批处理相关的查询异常
- **关联代码**：`UnifyQuery._query_log_using_unify_query`（`is_es_batch` 分支）@ unify_query/query.py；`TraceQuery.query_by_trace_ids` @ apm_web 侧
- **证据来源**：commit b3307f2138（body：「UQ query_raw 请求模型支持可选 is_es_batch 参数；缺省时不发送，不改变其他调用方行为」「仅在 TraceQuery.query_by_trace_ids 的跨 RT Trace 查询中显式传入 is_es_batch=true」「前端资源参数不暴露该开关，调用范围由 APM Trace 服务端控制」）
