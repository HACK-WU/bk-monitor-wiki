## 流程 1：告警聚合到 Issue

- **业务目标**：当一条告警触发 fta_action 时，将其归入对应 Issue，供后续统一跟进。
- **调用顺序**：
  1. 构造 `IssueAggregationProcessor(alert, strategy)`。
  2. 调用 `processor.process()`。
  3. 返回 `True` 表示告警已关联/创建 Issue；`False` 表示未进入 Issue 池。
- **事务边界**：
  - 无显式数据库事务；ES UPSERT + Redis 缓存各自保证最终一致。
  - `AlertDocument.issue_id` 写入失败会重试 1 次，仍失败仅日志记录，不阻塞通知等主流程。
- **预期结果**：
  - 已有活跃 Issue：该告警被追加到 Issue，`alert.issue_id` 指向已有 Issue。
  - 无活跃 Issue：新建 `pending_review` 状态的 Issue，写入 CREATE 活动日志，`alert.issue_id` 指向新 Issue；满足条件时异步派发 LLM 标题任务。
- **错误处理**：
  - 配置未开启/级别不匹配/条件过滤/缺维度/抢锁失败 → 返回 `False`，调用方不处理。
  - ES 写入异常 → 内部重试 1 次，仍失败则该告警本次未关联成功，由周期任务后续补偿。
- **使用示例**：
  ```python
  from alarm_backends.service.fta_action.issue_processor import IssueAggregationProcessor

  for alert in alerts:
      # strategy 来自策略缓存，需包含 issue_config
      associated = IssueAggregationProcessor(alert, strategy).process()
      if associated:
          print(f"alert {alert.id} associated with issue {alert.issue_id}")
  ```

## 流程 2：Issue 状态流转

- **业务目标**：根据运维处置动作，变更 Issue 生命周期状态并留下审计记录。
- **调用顺序**：
  1. `IssueDocument.get_issue_or_raise(issue_id, bk_biz_id=...)` 加载 Issue。
  2. 根据当前状态和目标动作选择方法：
     - 待审核 → 指派：`issue.assign(assignees, operator)`（进入未解决）。
     - 任意状态 → 改派：`issue.reassign(assignees, operator)`。
     - 活跃 → 已解决：`issue.resolve(operator)`。
     - 活跃 → 归档：`issue.archive(operator)`。
     - 已解决 → 未解决：`issue.reopen(operator)`。
     - 归档 → 恢复：`issue.restore(operator)`。
  3. 返回结果中的 `status` 与 `activities` 可用于前端刷新。
- **事务边界**：
  - 单条 Issue 的 ES UPSERT + 活动日志写入 + Redis 缓存更新是一个原子操作组合；失败时 `IssueDocumentWriteError` 会上抛，活动日志可能未写入。
  - 级联同步 member 状态是 best-effort，失败仅日志，不影响主 Issue 状态变更。
- **预期结果**：
  - Issue 状态按规则流转。
  - 活动日志写入 `STATUS_CHANGE` / `ASSIGNEE_CHANGE` 等记录。
  - 非活跃状态自动删除 Redis 缓存；活跃状态更新缓存。
- **错误处理**：
  - 状态不合法 → `ValueError`，前端应提示用户。
  - Issue 是合并 member → `IssueFrozenError`，前端应引导先拆分。
  - 重复 `resolve` → 空列表，按成功处理。
- **使用示例**：
  ```python
  from bkmonitor.documents.issue import IssueDocument

  issue = IssueDocument.get_issue_or_raise("1751234567a1b2c3d4", bk_biz_id=2)

  # 首次指派
  if issue.status == "pending_review":
      activities = issue.assign(assignees=["admin"], operator="admin")
  else:
      activities = issue.reassign(assignees=["admin"], operator="admin")

  # 标记已解决
  activities = issue.resolve(operator="admin")

  #  reopen
  activities = issue.reopen(operator="admin")
  ```

## 流程 3：周期同步

- **业务目标**：由后台任务定期校准活跃 Issue 的告警统计、影响范围，并回填漏关联告警。
- **调用顺序**：
  1. 调度器触发 `sync_issue_alert_stats.delay()`。
  2. 任务内部逐页扫描活跃 Issue。
  3. 对每个 Issue：
     - 若该 strategy 本周期未 backfill，则批量扫描 unlinked alerts 并回填。
     - 按 `issue_id` 聚合关联告警，得到 `alert_count` 与 `last_alert_time`。
     - 重算 `impact_scope`。
     - 检测 orphan Issue（创建超过 5 分钟且无关联告警则 error 日志）。
     - 批量 UPDATE IssueDocument。
  4. 任务结束前续命 legacy 迁移哨兵。
- **事务边界**：
  - 无全局事务；单条 Issue 更新失败仅计数并继续。
  - backfill 的 `AlertDocument.issue_id` 更新是批量 UPSERT，失败时停止该 strategy 的本次回填。
- **预期结果**：
  - 活跃 Issue 的 `alert_count`、`last_alert_time`、`impact_scope`、`update_time` 与 ES 中关联告警保持一致。
  - 因写入失败或部署窗口期产生的漏关联告警被回填到正确 Issue。
  - orphan Issue 被记录到日志，供监控告警发现。
- **错误处理**：
  - 单条 Issue 处理异常被捕获，任务继续，失败数计入最终日志。
  - legacy Issue 直接跳过，不更新统计。
- **使用示例**：
  ```python
  from alarm_backends.service.fta_action.tasks.issue_tasks import sync_issue_alert_stats

  # 通常由 Celery beat 调度；手动触发示例
  sync_issue_alert_stats.delay()
  ```

## 流程 4：LLM 标题自动生成

- **业务目标**：新建 Issue 后，对日志类告警自动总结生成可读标题。
- **调用顺序**：
  1. `IssueAggregationProcessor.process()` 新建 Issue 后，内部调用 `_maybe_dispatch_llm_title(issue)`。
  2. 仅当部署 env `ENABLE_ISSUE_LLM_TITLE` 存在且业务在白名单时，派发 `generate_issue_llm_title.delay(...)`。
  3. 任务消费后取关联日志 → 限流检查 → 调 LLM → 校验输出 → CAS 写入 `issue.name`。
- **事务边界**：
  - 标题生成是独立任务，与主流程解耦；失败不影响 Issue 核心数据。
  - `rename` 内部有业务内唯一性校验，但系统路径传 `enforce_unique=False`。
- **预期结果**：
  - 成功：Issue 名称被替换为 LLM 生成的可读标题，活动日志写入 `NAME_CHANGE`（operator=`system`）。
  - 失败/不适用：保留默认名，result label 记录原因（`empty_log`、`ratelimited`、`name_changed` 等）。
- **错误处理**：
  - 仅 `alert_not_found` 按 1s/3s 延迟重试；其他失败不重试、不入队、静默保留默认名。
- **使用示例**：
  ```python
  from alarm_backends.service.fta_action.tasks.issue_tasks import generate_issue_llm_title

  # 通常由 processor 内部自动派发；手动触发示例
  generate_issue_llm_title.delay(
      issue_id="1751234567a1b2c3d4",
      bk_biz_id=2,
      default_name="策略名 - 维度值",
      alert_id="alert-id-001",
  )
  ```

## 流程 5：LLM 标题运维重生成

- **业务目标**：对未成功生成或需要重新生成 LLM 标题的 Issue，由运维显式补偿。
- **调用顺序**：
  1. 调用 `regenerate_issue_llm_title(issue_id, bk_biz_id, operator=..., alert_id=...)`。
  2. 函数先做资格检查：Issue 活跃、非合并 member、非用户改名、存在可用告警。
  3. 资格通过后走 `_apply_llm_title`，CAS 写入新标题。
- **事务边界**：
  - 同步执行，绕过 `ENABLE_ISSUE_LLM_TITLE` 部署闸门与业务白名单，保留业务级限流。
  - 失败返回 `result` 字段，不抛异常。
- **预期结果**：
  - 成功：`result="ok"`，`new_name` 为 LLM 生成标题。
  - 跳过：`result` 为 `skipped_user_renamed`、`skipped_inactive`、`skipped_merged_member`、`no_alert` 等。
- **错误处理**：
  - 调用方根据返回的 `result` 提示运维；不能改写真实用户改名的标题。
- **使用示例**：
  ```python
  from alarm_backends.service.fta_action.tasks.issue_tasks import regenerate_issue_llm_title

  result = regenerate_issue_llm_title(
      issue_id="1751234567a1b2c3d4",
      bk_biz_id=2,
      operator="ops_admin",
  )
  if result["result"] != "ok":
      print(f"regenerate skipped: {result['result']}")
  ```

## 流程 6：批量解决 Issue

- **业务目标**：在合并/拆分、批量运维等场景下，一次性将多个 Issue 标记为已解决。
- **调用顺序**：
  1. 对每条目标 Issue 调用 `IssueDocument.get_issue_or_raise(issue_id, bk_biz_id=...)` 加载。
  2. 逐个调用 `issue.resolve(operator)`。
  3. 收集每条结果：成功返回活动列表，幂等返回空列表，失败抛出异常。
- **事务边界**：
  - 无批量事务；单条失败不影响其他条目。
  - 对主 Issue resolve 会级联把其 active member 同步为 `resolved`（best-effort）。
- **预期结果**：
  - 所有活跃 Issue 进入 `resolved`，写入 `resolved_time`，删除 Redis 缓存。
  - member Issue 跟随主 Issue 级联解决，但合并关系保留。
- **错误处理**：
  - 对 member 直接 resolve：幂等短路先于冻结守卫，重复调用返回空列表；非重复调用抛 `IssueFrozenError`。
  - 状态非法 → `ValueError`。
- **使用示例**：
  ```python
  from bkmonitor.documents.issue import IssueDocument

  results = []
  for issue_id in issue_ids:
      try:
          issue = IssueDocument.get_issue_or_raise(issue_id, bk_biz_id=2)
          results.append({"issue_id": issue_id, "activities": issue.resolve(operator="admin")})
      except Exception as e:
          results.append({"issue_id": issue_id, "error": str(e)})
  ```

## 流程 7：Issue 合并

- **业务目标**：将多个相关 Issue 合并到一个主 Issue 下，统一跟进与展示。
- **调用顺序**：
  1. 调用方保证待合并 Issue 不存在链式合并、跨业务等冲突（由 Issue 合并业务入口负责，本专家仅说明状态侧影响）。
  2. 合并关系写入 `IssueMergeRelation`（status=`active`）。
  3. 主 Issue 的后续状态变更通过 `_cascade_follow_status` 同步 member ES status；member Issue 被冻结，直接操作会抛 `IssueFrozenError`。
- **事务边界**：
  - 关系写入 MySQL；member 状态同步 ES 是 best-effort，失败不破坏关系。
- **预期结果**：
  - 列表/搜索默认隐藏 member Issue（`filter_out_members`）。
  - 主 Issue 详情聚合 member 的 `alert_count`、`first_alert_time`、`last_alert_time`、`impact_scope`。
  - 主 Issue resolve/archive/reopen/restore 时，active member 跟随同步。
- **错误处理**：
  - 直接对 member 做状态变更 → `IssueFrozenError`，`extra.conflicting_main_issue_id` 指向主 Issue。
  - 合并关系查询失败 → Resolver 降级 noop，列表可能暂时展示 member（fail-open）。
- **使用示例**：
  ```python
  from bkmonitor.issue_merge import IssueMergeResolver, MergeResolverContext

  # 列表查询前加载合并上下文
  context = MergeResolverContext(bk_biz_id=2)
  context.load()

  # 将 member ID 展开为主 + members，用于反查告警
  full_ids = IssueMergeResolver.expand_to_full_ids(["main-issue-id"], context)

  # 默认过滤掉 member
  visible_ids = IssueMergeResolver.filter_out_members(issue_ids, context)
  ```

## 流程 8：Issue 拆分

- **业务目标**：将已合并的 member Issue 恢复为独立 Issue。
- **调用顺序**：
  1. 调用方将 `IssueMergeRelation` 对应行 status 置为 `split`，并记录 `split_reasons` / `split_kind`。
  2. 调用 `IssueDocument.bulk_reset_for_split(member_ids, operator, kind="manual", main_issue_id=..., bk_biz_id=..., reasons=...)`。
  3. member Issue 被批量重置为 `pending_review`，assignee 清空，并写入 `SPLIT_FROM` / `STATUS_CHANGE` / `ASSIGNEE_CHANGE` 活动日志。
- **事务边界**：
  - 关系状态更新与 ES 重置非原子；ES 重置失败仅 warning，可由运维命令修复。
- **预期结果**：
  - member Issue 恢复独立，状态为 `pending_review`，可重新被指派、解决等。
  - 拆分溯源保留在活动日志与关系表中。
- **错误处理**：
  - 关系表更新与 ES 重置分离，失败通过 `repair_issue_merge_state` management command 兜底。
- **使用示例**：
  ```python
  from bkmonitor.documents.issue import IssueDocument

  IssueDocument.bulk_reset_for_split(
      member_ids=["member-issue-id-1", "member-issue-id-2"],
      operator="admin",
      kind="manual",
      main_issue_id="main-issue-id",
      bk_biz_id=2,
      reasons=["根因不同，需独立跟进"],
  )
  ```
