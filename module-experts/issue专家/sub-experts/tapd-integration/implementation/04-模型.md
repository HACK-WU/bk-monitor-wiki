## 简介

TAPD 集成涉及 3 个核心 MySQL 模型：`TapdWorkspaceBinding`、`TapdWorkspaceManualUnbind`、`IssueTapdRelation`。均继承 `AbstractRecordModel`，自动携带 `create_time`、`update_time`、`create_user`、`update_user` 审计字段。

## 校验规则

| 规则 | 位置 | 说明 |
|------|------|------|
| 唯一约束 | `TapdWorkspaceBinding.Meta.unique_together` | 同一租户+空间+项目只能有一条 binding |
| 唯一约束 | `TapdWorkspaceManualUnbind.Meta.unique_together` | 同一租户+空间+项目只能有一条 tombstone |
| 唯一约束 | `IssueTapdRelation._meta.constraints` | 同一业务+Issue+项目+单据只能有一条关联 |
| 外键/引用无硬约束 | — | `issue_id` 为 ES 文档 ID，MySQL 无 FK；`workspace_id` 为 TAPD 项目 ID，无 FK |
| 审计字段自动填充 | `AbstractRecordModel.save()` | 通过 `set_local_username` 在回调视图中显式覆盖 |

## 索引与性能提示

- `tapd_workspace_binding` 和 `tapd_workspace_manual_unbind` 在 `(bk_tenant_id, space_uid, tapd_workspace_id)` 上均有唯一索引，可满足按空间+项目查询。
- `bkmonitor_issue_tapd_relation` 当前仅在 `(bk_biz_id, issue_id, workspace_id, tapd_id)` 上有唯一约束，未显式创建 `(bk_biz_id, issue_id)` 查询索引；`ListIssueTapdRelationsResource` 按 `issue_id` 过滤时依赖该唯一索引的前缀扫描或全表扫描，若数据量大建议补充索引。

## 结论

- TAPD 集成模型层设计简洁：binding 表负责关联，tombstone 表负责解绑记忆，关系表负责 Issue-TAPD 映射。
- 所有模型均通过 `bk_tenant_id + space_uid` 做多租户隔离，与项目整体租户模型一致。
- `IssueTapdRelation` 未与 ES Issue 做外键约束，依赖应用层 `IssueDocument.get_issue_or_raise` 校验存在性。
