# C0-使用总览：kernel_api 网关专家

## 1. 能力清单

kernel_api 是 BK-Monitor 的**内核 API 网关**（部署角色为 `api`），对外（API 网关/其他系统）暴露监控内核能力，并作为 `web`（monitor_saas）访问告警后台（alarm_backends）的唯一中转层。

| 能力域 | 说明 | 代码位置 |
|--------|------|----------|
| 版本化 API 注册 | `register_v2/v3/v4` 按版本批量注册 `ResourceViewSet`，v3 支持 `INSTALLED_APIS` 按需挂载模块 | `urls.py` |
| 三层 API 版本 | v2（历史/兼容）、v3（collector/meta/models/query）、v4（当前主版本，40+ 文件） | `views/v2|v3|v4/` |
| 认证与授权 | 三种认证：apigw JWT、API Token（Bearer）、MCP 请求认证；`AppWhiteListModelBackend` 自动创建用户 | `middlewares/authentication.py` |
| 异常处理 | `api_exception_handler` 统一渲染 `{code, result, message, data}`，恒 200 + body.code | `exceptions.py` |
| 字段适配 | `ApiRenderer` 把内核字段名映射为蓝鲸规范字段（`biz_id`→`bk_biz_id` 等） | `adapters.py` |
| DB 路由 | `KernelAPIRouter` 把 `monitor_api`/`metadata` 表路由到 backend 库 | `dbroutors.py` |
| 扩展点 | `ALLOW_EXTEND_API=True` 时动态加载 `extend_views`/`extend_resource` | `extend_*` 目录 |
| 内部 Resource 复用 | `resource/` 下批发场景 Resource，被 ViewSet 或 MCP/AI 复用 | `resource/` |
| RPC 函数注册 | `KernelRPCRegistry` 注册大量"函数"（admin 运维巡检 / bkm-cli 只读命令 / 平台信息），经 `KernelRPCResource` 统一暴露 | `rpc/` |
| 运维工具 | `check_apis` 校验 API 配置完整性 | `management/commands/check_apis.py` |

## 2. 能力边界

- **不做前端渲染**：kernel_api 是纯 API 角色，不含 monitor_web/fta_web 等 Web 页面逻辑（但 `config/role/api.py` 通过 `from config.role.web import *` + `from config.role.worker import *` 同时挂载了 SaaS 与 Worker 类 APP，可访问其 Resource）。
- **不直接暴露给前端**：`resource/` 下的 Resource 是内部复用层，前端只能通过 `views/` 的 `ResourceViewSet` 访问。
- **不是唯一入口**：`rest/v2/`（grafana 视图）与 `apm_api/v1/`、`rum_api/v1/` 也挂在 kernel_api 的 URLConf 下。
- **HTTP 状态码恒 200**：kernel_api 层业务错误统一 200 + `body.code`，HTTP 4xx/5xx 由 web 端网关转换（见 C1）。
- **认证跳过权限中心**：`SKIP_IAM_PERMISSION_CHECK=True`（api 角色默认跳过 IAM 检查，MCP 请求单独做权限校验）。

## 3. 已知问题与常见坑

| 现象 | 触发条件 | 正确做法 |
|------|----------|----------|
| 前端看到 HTTP 500 而非真实业务错误码 | web 端经 `APIResource` 调 kernel_api，kernel_api 恒 200，web 网关 `BKAPIError` 默认包装为 500 | 前端认 `body.code` 而非 HTTP 状态码；要 4xx 需在 web 端 Resource 捕获 `BKAPIError` 按 `e.data.code` 重抛专有错误 |
| kernel_api 层 `data` 字段为空/丢失 | `api_exception_handler` 只白名单透传 `error_code`/`next_actions`，`exc.data` 其他键被丢弃（防泄露） | 需要透传结构化字段时用 `error_code`/`next_actions` 键，或用 web 端重新识别 `body.code` |
| 新增错误码冲突 | 错误码与 `core/errors/upgrade.py` 的 3318001 等已占用段冲突 | 新增错误码前先 grep `code = 33` 全局占用，选未占用段（如 issue 用 3327xxx） |
| 用户自动创建后租户不匹配 | 多租户模式下 apigw 应用态不校验用户名与租户对应 | `AppWhiteListModelBackend` 会查 `bk_login` 确认用户属于当前租户后更新 `tenant_id` |
| `get_request_tenant_id()` 在标准请求中不可靠 | Django 标准请求中 `RequestProvider` 中间件未调用 `set_request()` | 用 `bk_biz_id_to_bk_tenant_id(bk_biz_id)` 从业务 ID 反查租户 |
| MCP 请求缺少 `bk_biz_id` 被拒 | MCP 认证要求请求带业务 ID | 请求侧必须携带 `bk_biz_id`（GET 参数 / POST 表单 / JSON body） |

## 5. 强依赖与外部依赖

- `core.drf_resource`（Resource / APIResource / ResourceViewSet / ResourceRoute / ResourceRouter）——公共框架，不建专家
- `alarm_backends`——api 角色运行时挂载（`config/role/api.py`），告警后台能力
- `metadata` / `apm` / `rum`——同工程 app，经 Resource 调用（metadata 已有"元数据管理专题"专家）
- `bkmonitor.models`（`ApiAuthToken`、`AuthType`）——认证 Token 数据模型
