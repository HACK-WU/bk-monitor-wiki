## 三、专家划分

### 3.1 专家总览

| # | 专家名 | 覆盖范围 | 子专家数 | 批次 |
|---|--------|---------|---------|------|
| 1 | 元数据核心模型 | data_source, result_table, common, entity_relation | 2 | Batch 1 |
| 2 | 存储与数据链路 | storage, data_link, es_snapshot, influxdb_cluster, vm/ | 2 | Batch 1 |
| 3 | 空间与自定义上报 | space/, custom_report/, record_rule/ | 2 | Batch 1 |
| 4 | 任务调度与运维 | task/, management/commands/, dataflow/, health_check | 0 | Batch 2 |
| 5 | API与工具库 | resources/, utils/, service/, bcs/ | 2 | Batch 2 |

### 3.2 专家 1：元数据核心模型

**职责**：管理监控系统的核心元数据定义——数据源、结果表、字段、标签、集群信息。

**核心文件**：

| 文件 | 大小 | 主要内容 |
|------|------|---------|
| `models/data_source.py` | 62 KB | DataSource 模型、数据源 CRUD、连接管理 |
| `models/result_table.py` | 139 KB | ResultTable、ResultTableField、Label 模型与管理逻辑 |
| `models/common.py` | 9 KB | 基础模型抽象、公共字段 |
| `models/entity_relation.py` | 8 KB | 实体关系模型（跨模块：metadata + APM + bkm_ipchooser） |

> ⚠️ **`models/constants.py`（139KB）不归属本专家核心文件**。该文件为全局常量，被所有专家引用，将在 T0-专题总览中做结构化索引（按功能域分组），各子专家按需引用，不作为任何子专家的核心文件。

**子专家**：

| 子专家 | 范围 | 重点文件 |
|--------|------|---------|
| 数据源管理 | DataSource 全链路 | `data_source.py`, `common.py` |
| 结果表管理 | ResultTable + Field + Label | `result_table.py` |

### 3.3 专家 2：存储与数据链路

**职责**：管理监控数据的存储引擎配置（InfluxDB/ES/Kafka/VM）、数据链路（清洗/汇聚/流转）、ES 快照、集群管理。

**核心文件**：

| `models/storage.py` | **240 KB** | InfluxDB/ES/Kafka/VM 存储配置模型、存储管理 |
| `models/data_link/data_link.py` | 56 KB | 数据链路主模型 |
| `models/data_link/data_link_configs.py` | 42 KB | 数据链路配置 |
| `models/data_link/relation.py` | 18 KB | 数据链路关系 |
| `models/data_link/service.py` | 8 KB | 数据链路服务层 |
| `models/data_link/utils.py` | 10 KB | 数据链路工具 |
| `models/es_snapshot.py` | 55 KB | ES 快照模型与管理 |
| `models/influxdb_cluster.py` | 34 KB | InfluxDB 集群管理 |
| `models/vm/` | 6 文件 | VM (VictoriaMetrics) 相关 |

**子专家**：

| 子专家 | 范围 | 重点文件 |
|--------|------|---------|

> ⚠️ **数据链路子专家范围边界**：本子专家仅覆盖 `metadata/models/data_link/` 的模型定义层。APM 层的数据链路操作服务（`apm/views.py`、`apm/models/config.py`、`apm/core/discover/precalculation/storage.py`）不在本专题范围内，如需了解请参考 APM 监控模块专家。

### 4.2 Batch 0：专题架构先行

**目标**：创建专题层文件，确立跨专家架构。

**产出**：

| 文件 | 内容 |
|------|------|
| `topic.md` | 专题名片：名称、范围、专家列表、创建信息 |
| `T0-专题总览.md` | 跨专家架构图（Mermaid）、专家导航表、子专家索引、数据流全景图、跨模块依赖边界、`constants.py` 结构化索引 |
| `PLAN.md` | 本文件（已创建） |

**T0-专题总览必须包含的章节**：

1. **跨专家架构图**（Mermaid）：展示 5 个专家之间的数据流向与调用关系
2. **专家导航表**：专家名 → 覆盖范围 → 子专家 → 批次
3. **跨模块依赖边界**：明确标注以下跨模块组件的归属与边界
   - `entity_relation.py`（metadata 8KB）— 核心逻辑在 APM 层（`apm/views.py`、`apm/models/config.py`），跨 metadata + APM + bkm_ipchooser 三个模块，本专题仅覆盖 metadata 侧模型定义
   - `data_link` 操作服务 — metadata 侧为模型定义，操作服务在 APM 层，本专题不含 APM 层
4. **`constants.py`（139KB）结构化索引**：按功能域分组列出常量类别（存储/数据源/结果表/空间/自定义上报/任务调度等），各子专家按需引用，不作为任何子专家核心文件
5. **公共依赖标注**：`common.py`、`utils/` 中的公共工具，标注被哪些专家引用

**执行方式**：主 agent 直接创建，不派子 agent。

### 4.3 Batch 1：三专家并行创建

**目标**：同时创建专家 1、2、3 及其各自子专家。

**并行策略**：3 个专家同时启动，每个专家内部先产出契约层 + 实现层，再拆子专家。

| 专家 | 子专家数 | 实现文档数 | 契约文档数 | 预估子 agent 数 |

**产出总计**：45 份实现文档 + 18 份契约文档

### 4.4 Batch 2：剩余两专家并行创建

**目标**：创建专家 4、5，专家 4 无子专家。

| 专家 | 子专家数 | 实现文档数 | 契约文档数 | 预估子 agent 数 |

**产出**：

|------|------|

## 七、风险与注意事项

| 风险 | 影响 | 缓解措施 |
|------|------|---------|
| `storage.py`(240KB) 单文件过大 | 子 agent 上下文溢出 | 存储引擎子专家优先聚焦核心模型，细节按需引用源码行号 |
| `constants.py`(139KB) 常量过多 | 子 agent 产出冗长 | 契约层只收录高频常量，低频常量按需引用 |
| 并行子 agent 可能重复调研公共模块 | 资源浪费 | T0-专题总览提前标注公共依赖边界 |
| 子专家间有交叉调用 | 文档重复描述 | agent.md 中明确"不负责"边界，交叉部分由上游专家覆盖 |
| 产出文档总量 ~100 份 | 落盘耗时 | 分批落盘，每批完成后立即验收 |
