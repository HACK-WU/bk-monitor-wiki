def init_label_data():
    """增加默认的label信息"""
    Label = models["Label"]
    init_data_path = os.path.join(config.BASE_DIR, "metadata/data/init_label.json")
    with open(init_data_path) as init_file:
        label_data = json.load(init_file)
    labels = [Label(**label) for label in label_data]
    Label.objects.bulk_create(labels, batch_size=BATCH_SIZE)

**实现要点**：
- 使用 `bulk_create` 批量插入，`BATCH_SIZE=500`
- 直接解包 JSON 对象为 Model 构造参数（`Label(**label)`）
- 无幂等性保护，重复执行会因 unique 约束失败

## 四、init_resulttable() 实现

```python
def init_resulttable():
    """增加默认的结果表信息"""
    init_data_path = os.path.join(config.BASE_DIR, "metadata/data/init_resulttable.json")
    with open(init_data_path) as init_file:
        result_table_list = json.load(init_file)
    for result_table in result_table_list:
        table_id = result_table["table_id"]
        # 1. 创建结果表
        add_resulttable(models=models, table_id=table_id, ...)
        # 2. 创建结果表Option
        add_resulttable_option(models=models, table_id=table_id, ...)
        # 3. 创建结果表字段及Option
        add_resulttablefield(models=models, table_id=table_id, field_item_list=result_table["field_list"], ...)
        # 4. 创建data_id和该结果表的关系
        add_datasourceresulttable(models=models, data_id=result_table["bk_data_id"], table_id=table_id, ...)
        # 5. 创建实际结果表记录
        if result_table["default_storage"] == "influxdb":
            database, table_name = table_id.split(".")
            add_influxdbstorage(table_id=table_id, database=database, real_table_name=table_name, source_duration_time="90d")
        elif result_table["default_storage"] == "elasticsearch":
            add_esstorage(table_id)

    # 6. 创建 Kafka 存储
    storage_path = os.path.join(config.BASE_DIR, "metadata/data/init_storage.json")
    with open(storage_path) as init_file:
        storage_data = json.load(init_file)
    for table_id in storage_data["kafka_storage"]:
        topic = "_".join([config.KAFKA_TOPIC_PREFIX_STORAGE, table_id])
        add_kafkastorage(table_id, topic)
```

**实现要点**：
- 每条结果表执行 5 步：创建表 → 创建选项 → 创建字段 → 创建数据源关联 → 创建存储
- InfluxDB 存储的 `source_duration_time` 固定为 `"90d"`
- `table_id` 按 `.` 分割为 `database` 和 `table_name`
- Kafka 存储的 topic 格式为 `{prefix}_{table_id}`
- 所有操作通过 `migration_util` 中的工具函数完成

**章节来源**: [0002_initial_data.py](file:///root/bk-monitor/bk-monitor-base/src/bk_monitor_base/metadata/migrations/0002_initial_data.py) L83-L127

## 六、result_table_id 格式转换

### 6.1 问题背景

`description_unit.json` 中的 `result_table_id` 使用**下划线**格式（如 `system_cpu_summary`），而数据库中的 `ResultTable.table_id` 使用**点号**格式（如 `system.cpu_summary`）。

### 6.2 转换实现

**位置**: [0008_import_field_descriptions.py](file:///root/bk-monitor/bkmonitor/metadata/migrations/0008_import_field_descriptions.py) L48-L67

```python
def import_description(apps, schema_editor):
    for field_info in field_list:
        # 转换结果表ID
        old_table_id = field_info["result_table_id"]
        first_index = old_table_id.index("_")

        table_id = ".".join([old_table_id[:first_index], old_table_id[first_index + 1:]])
        field_name = field_info["item"]

        try:
            field_object = models["ResultTableField"].objects.get(table_id=table_id, field_name=field_name)
        except models["ResultTableField"].DoesNotExist:
            print("table->[{}] field->[{}] is missing".format(table_id, field_name))
            continue

        field_object.description = field_info["item_display"]
        field_object.unit = field_info["conversion_unit"]
        field_object.save()
```

**转换逻辑**：
- 找到第一个 `_` 的位置
- 将其替换为 `.`
- 例如：`system_cpu_summary` → `system.cpu_summary`

**设计维度分析**：

**维度 1：格式不一致的根因** — `init_resulttable.json` 使用点号格式（`system.cpu_summary`），而 `description_unit.json` 使用下划线格式（`system_cpu_summary`）。这是因为 `description_unit.json` 可能来自外部数据源，格式未统一。

**维度 2：转换的局限性** — 该转换假设 `table_id` 中只有一个 `_` 需要替换。对于包含多个 `_` 的表名（如 `custom_report_aggate`），转换结果 `custom.report_aggate` 可能不正确。但当前种子数据中不存在此类情况。

**章节来源**: [0008_import_field_descriptions.py](file:///root/bk-monitor/bkmonitor/metadata/migrations/0008_import_field_descriptions.py) L48-L67

## 七、K8s 指标/事件全局缓存机制

### 7.1 缓存实现

**位置**: [k8s_metric.py (bk-monitor-base)](file:///root/bk-monitor/bk-monitor-base/src/bk_monitor_base/metadata/utils/k8s_metric.py) L10-L42

```python
K8S_METRICS = []
K8S_EVENTS = []

def get_built_in_k8s_metrics():
    global K8S_METRICS
    if K8S_METRICS:
        return K8S_METRICS  # 缓存命中，直接返回
    metrics = []
    BASE_DIR = os.path.dirname(os.path.dirname(os.path.abspath(__file__)))
    g = os.walk(os.path.join(BASE_DIR, "data/k8s_metrics"))
    for path, _, file_list in g:
        file_list = [file for file in file_list if file.split(".")[-1] == "yaml"]
        for file_name in file_list:
            with open(os.path.join(path, file_name)) as f:
                metrics.extend(yaml.safe_load(f.read()))
    K8S_METRICS = metrics  # 写入缓存
    return metrics

def get_built_in_k8s_events():
    global K8S_EVENTS
    if K8S_EVENTS:
        return K8S_EVENTS  # 缓存命中，直接返回
    events = []
    BASE_DIR = os.path.dirname(os.path.dirname(os.path.abspath(__file__)))
    file_name = os.path.join(BASE_DIR, "data/k8s_events.json")
    with open(file_name) as f:
        events.extend(json.loads(f.read()))
    K8S_EVENTS = events  # 写入缓存
    return events
```

### 7.2 两份实现的差异

| 属性 | bk-monitor-base 侧 | bkmonitor 侧 |
|------|-------------------|-------------|
| 文件 | [k8s_metric.py](file:///root/bk-monitor/bk-monitor-base/src/bk_monitor_base/metadata/utils/k8s_metric.py) | [k8s_metric.py](file:///root/bk-monitor/bkmonitor/bkmonitor/utils/k8s_metric.py) |
| BASE_DIR 计算 | `os.path.dirname(os.path.dirname(os.path.abspath(__file__)))` | `os.path.abspath(os.getcwd())` |
| YAML 加载 | `yaml.safe_load(f.read())` | `yaml.safe_load(f.read())` |
| 数据目录 | `data/k8s_metrics/` | `metadata/data/k8s_metrics/` |
| 实际调用方 | 无直接调用（仅定义） | `resources/resources.py`、`metric_list_cache.py` |

**设计维度分析**：

**维度 1：代码重复** — 两份 `k8s_metric.py` 功能几乎相同，仅在 BASE_DIR 计算方式上不同。bkmonitor 侧使用 `os.getcwd()` 依赖进程工作目录，bk-monitor-base 侧使用 `__file__` 相对路径更可靠。

**维度 2：缓存生命周期** — 模块级全局变量缓存在进程生命周期内有效。如果种子数据文件在运行时更新，需要重启进程才能生效。这适用于种子数据不会热更新的场景。
