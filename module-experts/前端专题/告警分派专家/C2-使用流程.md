# 使用流程：告警分派专家

> 契约快照生成于 2026-10-14（commit ff89f63ff4）。
> 若使用中发现行为与契约不符，可能代码已变更——expert-lookup 会自动增量修正，或用 expert-team 全量重建。

## 新建规则组并配置分派规则：从零配置一条分派链路

- **业务目标**：创建一个规则组，配置「分派给谁 → 匹配哪些告警 → 如何执行分派 → 修改原告警内容」，并生效。
- **调用顺序**：
  1. 列表页「新建」→ 填写组名 + 优先级（默认值自动推算，不可与现有组冲突）→ `createAssignGroup({ name, priority })` → 取响应 `id` 跳转配置页
  2. 配置页加载：`listAssignGroup()` 定位当前组 + `listAssignRule({ assign_group_id })` 拉规则（空组自动生成一条空行）+ `allKVOptions` 装载条件选项
  3. 逐行编辑：选告警组（`AlarmGroupSelect`）→ 编辑匹配条件（`CommonCondition`）→ 选流程套餐 / 配置通知升级 → 等级调整 / 追加标签 → 启用开关
  4. 点击「调试并生效」：`handleStartDebug` 逐行校验（`debugVerificatory` + 标签校验）→ 组装 `debugData`（`getSubmitParams()`）→ 打开 `DebuggingResult`
  5. 抽屉内 `matchDebug`（默认 `now-7d ~ now`）预览命中告警 → 点击「保存」→ `batchUpdate(debugData[0])`
- **提交边界**：**整组规则一次性提交**（`batchUpdate` 单请求）；`matchDebug` 与 `batchUpdate` 必须使用同一份 `debugData`（试算=提交的一致约定）。中途关闭抽屉则本次编辑全部不落库。
- **预期结果**：保存成功 → `isEffect=true` → 自动返回列表页（离开拦截直接放行）；列表页重新加载可见新组与规则。
- **错误处理**：行级校验失败停留在配置页（错误行列标红）；`batchUpdate` 失败静默不提示成功，需看网络面板/后端日志；离开拦截会在有未保存修改时二次确认。
- **使用示例**（真实链路代码，来源 `alarm-dispatch.tsx` + `alarm-dispatch-config.tsx` + `debugging-result.tsx`）：
  ```js
  // ① 列表页：新建规则组
  import { createAssignGroup } from 'monitor-api/modules/model';
  const data = await createAssignGroup({ name: '关键业务分派', priority: 100 });
  this.$router.push({ name: 'alarm-dispatch-config', params: { id: String(data.id) } });

  // ② 配置页：编辑完成后组装并保存（规则行由 RuleData 承载）
  const debugData = [{
    bk_biz_id: this.ruleGroupData.bk_biz_id,
    assign_group_id: this.ruleGroupData.id,
    priority: this.ruleGroupData.priority,
    group_name: this.ruleGroupData.name,
    rules: this.tableData.filter(row => !row.isNullData).map(row => row.getSubmitParams()),
    settings: { public_conditions: !!this.unifiedSettings.conditions?.length },
  }];
  this.debugData = debugData;
  this.showSideliner = true;   // 打开 DebuggingResult：matchDebug 预览 → 用户确认 → batchUpdate

  // ③ 保存成功回调（配置页）
  handleSaveSuccess() {
    this.isEffect = true;
    this.$router.push({ name: 'alarm-dispatch' });
  }
  ```

## 修改已有规则组的规则并生效

- **业务目标**：调整某规则组的匹配条件 / 分派动作 / 内容修改，并使其生效。
- **调用顺序**：
  1. 列表页找到目标组（可用 `?groupName=` / `?group_id=` 直达）→ 点「配置规则」进入配置页
  2. 编辑：行内编辑（条件/告警组/流程/等级/标签/启停）、批量编辑（勾选行后表头批量行）、统一设置（公共条件下发全员）、查找替换（`ConditionFindReplace`）
  3. 编辑过程自动维护三级变更标记（行级 `resetConfig`、格级 `config`、五态行样式），可随时「撤回」恢复上次生效值
  4. 「调试并生效」→ `matchDebug` 预览（本次未保存数据生效后的效果）→ 保存 → `batchUpdate`
- **提交边界**：与新建相同——整组一次性提交；`isRuleChange` 判断「行数变化或任一行与快照有差异」。
- **预期结果**：保存成功回列表页；未保存离开会收到「是否放弃本次操作？」确认。
- **错误处理**：编辑与统一设置发生冲突时（改动命中统一设置条件）弹「变更当前值将会使[统一设置条件失效]，是否确定变更？」——确认则清空统一设置，取消则回滚该次编辑。
- **使用示例**（统一设置与冲突确认的真实方法论，来源 `alarm-dispatch-config.tsx`）：
  ```js
  // 统一设置：把「所有规则共有」的条件集合下发到每条规则
  import { statisticsSameConditions } from './typing/condition';
  const common = statisticsSameConditions(this.tableData.map(r => r.conditions)); // 交集；任一规则无条件则返回 []
  this.unifiedSettings.conditions = common;      // 反推展示
  // 确认后逐行应用（两条路径由 RuleData 内部选择）
  this.tableData.forEach(row => row.unshiftConditions(addConditions));       // 新增路径
  // 或
  this.tableData.forEach(row => row.setUnifiedSettings(findData, replaceData, row.conditions)); // 替换路径
  ```

## 删除规则组（调试并删除）

- **业务目标**：删除一个不再需要的规则组（组内规则随之删除，不可恢复）。
- **调用顺序**：
  1. 列表页点击组标题行的删除图标 → `$bkInfo` 确认（okText「调试并删除」，副标题「删除该组及组内规则会一起删除,且不可恢复」）
  2. 确认后打开 `DebuggingResult`（`excludeGroups=[id]`）→ `matchDebug({ exclude_groups: [id], start_time, end_time })` 预览「移除该组后」的分派去向
  3. 用户确认「保存」→ `destroyAssignGroup(id)` → `delSuccess` → 列表页重拉
- **提交边界**：删除为单请求；**不要绕过调试抽屉直接调 `destroyAssignGroup`**（这是模块不变量）。
- **预期结果**：组与组内规则被删除，列表刷新后不再出现。
- **错误处理**：删除失败静默（无 toast）；内置组（`edit_allowed=false`）删除入口禁用并提示「内置的分派规则组不允许修改」。
- **使用示例**（真实代码，来源 `alarm-dispatch.tsx` `handleDeleteGroup` 与 `debugging-result.tsx` `handleSave`）：
  ```js
  // 列表页：确认后交给调试抽屉
  this.$bkInfo({
    type: 'warning',
    okText: window.i18n.t('调试并删除'),
    title: window.i18n.t('是否删除{name}?', { name: item.name }),
    subTitle: window.i18n.t('删除该组及组内规则会一起删除,且不可恢复'),
    confirmFn: () => {
      this.delGroups = [item.id];
      this.showDebug = true;      // DebuggingResult（excludeGroups 模式）
    },
  });

  // 调试抽屉「保存」分支（debugging-result.tsx）
  import { destroyAssignGroup } from 'monitor-api/modules/model';
  const ok = await destroyAssignGroup(this.excludeGroups[0]).then(() => true).catch(() => false);
  if (ok) this.$emit('delSuccess');
  ```

## 用 CSV 导入导出搬运规则

- **业务目标**：把一组规则导出留档，或把规则批量搬运到另一个规则组/环境。
- **调用顺序**：
  1. 配置页导出：`handleExportChange` 将 `tableData` 按固定 7 列表头（告警组 / 匹配规则 / 通知升级 / 流程 / 等级调整 / 追加标签 / 状态）拼 CSV → `downCsvFile` 下载（文件名 `{组名}-{时间戳}.csv`，带 BOM）
  2. 配置页导入：`MonitorImport` 选择 `.csv`（`return-text`）→ `csvToArr` 解析 → 表头必须与导出表头逐字一致 → 逐行还原为 `RuleData`（`transformDataKey` + `JSON.parse` 还原 JSON 列）**追加**到现有表格
  3. 导入行随后走常规编辑与「调试并生效」链路
- **提交边界**：导入本身**不落库**（纯前端追加）；落库仍需整组 `batchUpdate`。
- **预期结果**：导入行出现在表格末尾，带新增/变更标记，可继续编辑。
- **错误处理**：表头不一致静默忽略（源码 `// to do 校验`）；行级解析错误仅 `console.log`（无用户提示）——导入后需人工核对。
- **使用示例**（真实调用链，来源 `alarm-dispatch-config.tsx`）：
  ```js
  import { csvToArr } from '../custom-escalation/utils';

    downCsvFile(csvStr, `${this.ruleGroupData.name}-${dayjs.tz().format('YYYY-MM-DD HH-mm-ss')}.csv`);
  ```

## 从告警组 / 流转记录直达规则组

- **业务目标**：从告警组管理页或告警流转记录一键跳到「相关的告警分派规则」。
- **调用顺序**：
  1. 入口侧构造跳转（`query.groupName` 或 `query.group_id`）
  2. 列表页 `created` 读取 query 预填搜索 → 等「告警组字典」与「规则数据」两个请求都完成后自动执行一次过滤
- **提交边界**：只读流程，无写操作。
- **预期结果**：列表只展示与目标告警组相关（或组 ID 匹配）的规则组；清空搜索恢复全量。
- **错误处理**：搜索命中为空时显示空态（`search-empty`）。
- **使用示例**（两处真实入口，来源 `alarm-group-common/alarm-group.tsx` 与 `trace/.../alarm-records.tsx`）：
  ```js
  // 告警组页「相关分派规则」
  this.$router.push({ name: 'alarm-dispatch', query: { groupName: name } });

  // 告警流转记录的外链形态（记录项构造 url 字段，渲染层点击后新窗口打开）
  if (routerName === 'alarm-dispatch') {
    return {
      ...item,
      url: `${location.origin}${location.pathname}?bizId=${params?.biz_id}#/alarm-dispatch?group_id=${params?.group_id}`,
    };
  }
  ```
