## 决策清单

### 决策 1：接口契约-「调试所见=保存所提交」：试算与提交共用同一份 debugData

- **分类**：接口契约
- **动机**：一致性（避免「调试预览一套、保存落库另一套」的用户信任问题）
- **决策**：配置页把本次编辑组装的 `debugData`（数组恒为 1 项）先传给 `matchDebug` 试算；用户确认后**同一对象**原样传给 `batchUpdate`，不重新组装、不重新取值
- **背景约束**：规则编辑为整组批量提交，中间无逐条保存；调试与保存之间隔着用户确认步骤，若分别取值可能因编辑态变化而不一致
- **被否决方案**：无（源码注释只说明现状）
- **重新评估触发条件**：出现「调试结果与保存后实际分派行为不一致」的反馈
- **关联代码**：`DebuggingResult.getRuleMatchDebug` / `DebuggingResult.handleSave` @ `components/debugging-result.tsx`；`AlarmDispatchConfig.handleStartDebug` @ `alarm-dispatch-config.tsx`
- **证据来源**：代码注释原文（`debugging-result.tsx` props 注释）「此为调试数据，保存时也用此数据 防止有批量调试，故采用数组格式 此数据为空则为全局调试」

### 决策 2：其他-删除必须先经「调试并删除」闸门

- **分类**：其他（交互/产品决策）
- **动机**：避坑：直接删除无法感知影响面 → 误删后分派链路断裂且**不可恢复**
- **决策**：列表页删除入口不直接调 `destroyAssignGroup`，而是打开调试抽屉（`excludeGroups` 模式）→ 用户看过「移除该组后」的分派结果再确认删除；确认按钮文案即「调试并删除」
- **背景约束**：删除规则组会连带删除组内规则且不可恢复
- **被否决方案**：直接调用 `destroyAssignGroup` 静默删除——源码中该旧实现被注释保留（`// await destroyAssignGroup(id);`），改为统一走调试闸门
- **重新评估触发条件**：无
- **关联代码**：`AlarmDispatch.handleDeleteGroup` @ `alarm-dispatch.tsx`；`DebuggingResult.handleSave` @ `components/debugging-result.tsx`
- **证据来源**：代码注释（`handleDeleteGroup` 中被注释的旧实现与 `$bkInfo` 的 `okText: '调试并删除'`）+ 注释原文（`debugging-result.tsx`）「出数据用于删除并调试 点击生效按钮根据此参数删除规则组」

### 决策 3：架构设计-配置页整组一次性提交，不提供规则级即时保存

- **分类**：架构设计
- **动机**：一致性（组内规则存在优先级与公共条件（统一设置）的组级语义，逐条保存会出现语义中间态）
- **决策**：所有规则修改（含组名、优先级）汇总为整组 payload 经 `batchUpdate` 一次性提交；规则级 REST 端点（`create/update/partialUpdate/destroy/retrieveAssignRule`、`retrieve/updateAssignGroup`）保留定义但前端零调用
- **背景约束**：统一设置（公共条件）会命中组内所有规则，逐条保存无法保证组级语义一致
- **被否决方案**：无
- **重新评估触发条件**：单组规则数达到数百条导致提交体过大或编辑-预览链路不可用（如单组规则 > 500 条）
- **关联代码**：`AlarmDispatchConfig.handleStartDebug` @ `alarm-dispatch-config.tsx`；`model.js` 中 7 个零调用点的规则级端点
- **证据来源**：结构实证——全前端 grep 确认 7 个规则级 REST 端点无调用点（见 `implementation/05-接口.md`）；`debugData` 数组结构注释（同决策 1）

### 决策 4：接口契约-条件选项批量取数与后端上限显式同步（批次 20）

- **分类**：接口契约
- **动机**：避坑：前后端字段上限不一致 → 批量取 TopN 值候选项被后端拒绝或截断（条件编辑器值候选缺失）
- **决策**：前端以 20 为字段分片批次（`chunkFields`）批量调 `alertTopN` 取标签值候选，常量注释要求与后端 `AlertTopNResource.MAX_NESTED_TOP_N_FIELDS` 保持同步
- **背景约束**：标签维度值候选需按字段批量请求，单请求字段数受后端嵌套聚合上限约束
- **被否决方案**：无
- **重新评估触发条件**：后端 `MAX_NESTED_TOP_N_FIELDS` 调整（前后端不同步会立即导致批量取数失败或多余请求）
- **关联代码**：`TAG_FIELD_BATCH_SIZE` / `chunkFields` @ `typing/condition.ts`
- **证据来源**：代码注释原文「需与后端 AlertTopNResource.MAX_NESTED_TOP_N_FIELDS 保持同步」

### 决策 5：接口契约-统一设置落库语义由前端重算（`settings.public_conditions`）

- **分类**：接口契约
- **动机**：无
- **决策**：提交时 `settings.public_conditions` = 当前统一设置的公共条件是否非空（前端按编辑态**重算**），而非透传后端原值
- **背景约束**：统一设置是前端概念（多条规则共有条件的集合），后端只持久化布尔语义标记
- **被否决方案**：无
- **重新评估触发条件**：后端需要掌握公共条件明细（如需按条件统计或作为索引）
- **关联代码**：`AlarmDispatchConfig.handleStartDebug`（组装处）/ `unifiedSettingInit`（反推处）@ `alarm-dispatch-config.tsx`
- **证据来源**：代码实现（`settings: { public_conditions: !!unifiedSettings.conditions.length }`）+ `unifiedSettingInit` 依据 `public_conditions` 反推公共条件；见 `implementation/03-数据流转.md`「统一设置与查找替换」

### 决策 6：安全合规-追加标签输入以不可能字符串规避 XSS

- **分类**：安全合规
- **动机**：避坑：追加标签的 key/value 为用户输入自由文本，曾作为 tooltip 选择器参与渲染 → XSS 注入风险
- **决策**：追加标签输入框的 `tooltip-key` 固定为不可能字符串（`__null__`），使真实标签值不进入 tooltip 选择器
- **背景约束**：标签值自由输入且会进入 tooltip 渲染路径（列表页「修改告警内容」列与批量编辑）
- **被否决方案**：无（注释只说明改法）
- **重新评估触发条件**：底层 tooltip 组件修复 key 注入问题（届时方可移除该防御常量）
- **关联代码**：`alarm-dispatch-config.tsx` 与 `alarm-batch-edit.tsx` 中的 `tooltip-key='__null__'`
- **证据来源**：代码注释原文「这里有xss注入问题 改成一个不可能字符串字段」

### 决策 7：其他-空组保护：删除到最后一行回退「空组初始态」

- **分类**：其他（交互/产品决策）
- **动机**：可用性（表格恒保留可编辑行，避免空表格无添加入口）
- **决策**：删除唯一行 / 批量删除全部时不清空表格，而是重建一条空白新规则（`addId` 标记、`isEnabled: true`）
- **背景约束**：空组语义依赖「一条空行」形态（`isNullData` 豁免校验与提交过滤）
- **被否决方案**：无
- **重新评估触发条件**：无
- **关联代码**：`AlarmDispatchConfig.handleOperateAction`（delete / batchDelete 分支）@ `alarm-dispatch-config.tsx`
- **证据来源**：代码注释原文「当剩一个规则时, 也支持删除 这里删除的意思 回到空组时的初始状态」

### 决策 8：[推测] 架构设计-条件编辑器半受控与随机 key 重建

- **分类**：架构设计
- **动机**：性能（条件编辑含多段 tag 与多层弹层，若全受控逐键上报会让父表格深层监听与 diff 在高频输入下抖动）
- **决策**：现行 `CommonCondition` 不在 `value` 变化时同步内部状态（无 value watch）；外部数据刷新统一用「更换组件 key 强制重建」（`conditionsRenderKey` / `conditionsKey` / `conditionsSelectorKey`）
- **背景约束**：条件值改动必须回写宿主行数据参与差异对比与提交
- **被否决方案**：旧版实现对 `value` 做受控同步（`@Watch('value')`，对照实现；无明确否决记录）
- **重新评估触发条件**：出现「外部数据刷新后组件状态陈旧」的反馈累计 ≥ 2 次
- **关联代码**：`CommonCondition` @ `components/common-condition-new.tsx`（对照旧版 `common-condition.tsx` 的 `@Watch('value')`）；三个随机 key 的刷新时机
- **证据来源**：无直接证据，基于「新版删除 value watch + 全部刷新点均使用随机 key」的结构推断

### 决策 9：[推测] 性能取舍-列表页懒渲染分帧（每批 2 组）

- **分类**：性能取舍
- **动机**：性能（组多规则多时一次性渲染全部组的主机表格与条件 tag 行代价大，无虚拟化）
- **决策**：规则组列表不一次性渲染——以底部哨兵节点 + IntersectionObserver 分帧追加（每批 2 组）；哨兵仍在视口时经 `requestIdleCallback` 短暂移出再追加，形成空闲期连续渲染
- **背景约束**：组内规则表格的条件列渲染完整 tag 行（无虚拟化），单组渲染成本随规则数增长
- **被否决方案**：无
- **重新评估触发条件**：组数量级显著下降（首屏可一次渲染）或引入表格虚拟化
- **关联代码**：`AlarmDispatch.observerTableGroup` / `handleTriggerObserver` / `isInViewport` @ `alarm-dispatch.tsx`
- **证据来源**：无直接证据，基于哨兵分帧的配套实现（`requestIdleCallback` + `hiddenFooter` 短时移出）的结构推断

### 决策 10：[推测] 架构设计-页面 action 权限服务跨模块组件，本体编辑性由数据字段驱动

- **分类**：架构设计
- **动机**：无
- **决策**：本模块页面声明的 action 权限（`MANAGE_ACTION_CONFIG` / `ALARM_GROUP_MANAGE_AUTH`）其消费方是子树中的跨模块组件（套餐详情编辑按钮、告警组管理入口）；本模块自身页面/按钮的可编辑性由服务端数据字段 `edit_allowed` 驱动
- **背景约束**：「内置规则组不可改」是服务端业务规则（与用户权限无关），无法用 action 权限表达
- **被否决方案**：无
- **重新评估触发条件**：后端将内置组保护改为按权限表达（如新增 action 类型）
- **关联代码**：`authority-map.ts`；两个 page 壳的 `authorityMixinCreate`；跨模块消费方 `set-meal-detail.tsx` 与 `strategy-config/.../alarm-group.tsx`
- **证据来源**：无直接证据，基于「authority-map 注释 + 本模块 `@Inject('authority')` 零消费（grep 实证）+ 跨模块组件消费 + `edit_allowed` 列表/配置双处独立判断」的结构推断
