## 流程 1：制作并发布一个新插件（用户全链路）

**业务目标**：从零定义一个指标插件（如 CPU 采集），调试确认后发布，使其可被采集配置选用。

**调用顺序**：

1. **进入向导**：列表页「新建」→ 路由 `plugin-add`（`MANAGE_AUTH`）；可带 `objectId` 预设分类（采集配置跳入时）
2. **Step1 定义插件（`step-set-plugin.vue`）**：填基本信息（插件 ID 经 `checkIdCollectorPlugin` 失焦校验）→ 选类型（7 类）→ 上传包/脚本（`upload.vue` / `new-plugin-monaco`）→ 定义参数（`config-param`）→ 描述 md → 「下一步」触发 `createCollectorPlugin`；如 `needRegister` 为真继续 `pluginRegister` **异步轮询（1500ms）**取 `token`
3. **Step2 插件调试（`step-set-test.vue`）**：选目标主机（`select-host`）→ `startDebugCollectorPlugin` → **2s 轮询** `fetchDebugLogCollectorPlugin` 渲染终端（`timeOut>180` 自动停）→ 调试数据可唤起指标维度弹窗编辑 → 「保存」= `savePlugin()`（仅置 `saveData.from='save'` 后前进）
4. **Step3 完成发布（`step-set-done.vue`）**：`activated` 时 `from === 'save'` → **`releaseCollectorPlugin(plugin_id, {config_version, info_version, token})` 真正发布**；`from !== 'save'` 走 `simRelease` 缓存模拟结果
5. **出口**：成功后提供「前往采集配置升级插件」（`related_conf_count > 0` 时）/「新建采集配置」（`collect-config-add`）

**提交边界 / 生效时机**：

- **两阶段提交**：`createCollectorPlugin`/`register` 只生成版本与 token；**只有 `releaseCollectorPlugin` 成功，插件才真正生效**。
- 步骤2「保存」不是发布（真正发布在步骤3）；两步之间可回退（`$bus.forward`），步骤状态由 `stepsMap.done` 推进。
- 未完成向导离开页面会被 `beforeRouteLeave` 拦截（目标非 `plugin-add`/`plugin-edit` 且 `step < 2` 时二次确认）。

**预期结果**：插件出现在列表且 `status` 非 draft；可在采集配置的插件选择器中被选用；插件变更联动「采集配置升级」入口。

**错误处理**：ID 校验失败停留 Step1；注册失败弹注册对话框（`registerDialog`）展示原因；调试失败在终端展示日志；发布失败展示 `err.message`（无回滚，见 C0 已知坑）。

**使用示例**（真实调用链组合，来源 `step-set-plugin.vue` / `step-set-test.vue` / `step-set-done.vue`）：

```js
// Step1 提交与注册（简化自 handleNextStep / handleRegisterFlow）
await createCollectorPlugin(params);                       // POST collector_plugin/
const task = await pluginRegister({ plugin_id, config_version, info_version }, { isAsync: true });
// 1500ms 轮询直至 is_completed → 取 data.token 存入 pluginInfo
// Step2 调试（简化自 startDebug / handleDebugLog）
const taskId = (await startDebugCollectorPlugin(plugin_id, params, { cancelToken })).task_id;
setInterval(() => fetchDebugLogCollectorPlugin(plugin_id, { task_id: taskId }), 2000);
// Step2 保存仅前进；Step3 activated 中真正发布
await releaseCollectorPlugin(plugin_id, { config_version, info_version, token });
```

## 流程 2：修改插件的指标与维度（用户/开发者）

**业务目标**：给已有插件增改指标、维度或分组规则并使其生效。

**调用顺序**（三条入口，共享同一份 `metric_json` 契约）：

1. **选择入口**：
   - `plugin-setmetric` 路由页（列表行「设置指标&维度」，仅 `normal` 且非官方）→ `MetricDimensionDialog`（`isRoutePage=true`）
   - 向导步骤2 内嵌弹窗 → 同一组件（`isRoutePage=false`）
   - 插件详情「指标维度」tab → `PluginIndicatorDimension`（v2 工具族）
2. **编辑**：分组（`group_default` 不可删）/ 字段行内编辑 / 批量移动 / 规则维护 / 自动采集开关；校验上限（普通 5000 / SNMP 500）与唯一性（指标全局 / 维度组内 / 别名全局）
3. **提交**：剔除前端态字段 → `saveMetric`（`need_upgrade: true`）→ 若返回 `token` 则 `releaseCollectorPlugin(plugin_id, 整个响应体)` 发布
4. **反馈**：v1 通过 `changeVersion` 事件把版本写回向导（供步骤3 release）；路由页保存成功后 `$router.back()`

**提交边界 / 生效时机**：`saveMetric` 不返回 token 时为「仅保存」（落草稿）；返回 token 的场景**必须补 release**，否则不生效。

**预期结果**：指标/维度在编辑器与详情页回显一致；插件版本（`config_version.info_version`）递增；采集配置侧可感知版本变化。

**错误处理**：`saveMetric` 失败手动 `$bkMessage`（`needMessage: false`）；`release` 失败静默（`catch(() => false)`），可能出现「新版本已生成、未发布」中间态。v2 单条编辑为 `silent` 即存（连续快速编辑会并发保存，请求乱序时后端最终版本不可控）。

**使用示例**（真实用法，来源 `metric-dimension-dialog.tsx` `handleSave` 简化）：

```js
const data = await saveMetric(params, { needMessage: false });   // params.metric_json 已剔除前端态字段
if (data.token) {
  await releaseCollectorPlugin(pluginId, data);                   // 两阶段提交第二阶段，含 token 必须调用
}
```

## 流程 3：导入插件包并处理冲突（用户链路）

**业务目标**：把外部/官方插件包（`.gz/.tgz`）导入平台；遇到重名/冲突时选择正确的处理分支。

**调用顺序**：

1. **选择文件**：列表页「导入」（隐藏 `input accept=".gz,.tgz" multiple`）→ 按文件数分流
2. **单文件（`handeFileSingel`）**：打开 `plugin-dialog-single` → `importPluginCollectorPlugin({ file_data })` → **先 `SET_PLUGIN_CONFIG(data)` 缓存** → 按响应分支：
   - 无冲突且 `is_official` → `saveAndReleasePlugin(data)` 直接覆盖更新（成功后重拉列表）
   - 无冲突且非官方 → 跳 `plugin-add`（`params.isImportPlugin=true`）继续制作
   - 非超管且官方 → 无权限提示（引导新建）
   - 有 `conflict_detail` → 冲突弹窗：按 `conflict_ids` 判定可否「更新插件」（**2/3/5 不提供**）、「创建插件」跳 `plugin-add`、「更新至现有插件」（官方 + 超管）走 `saveAndReleasePlugin`
3. **多文件（`handleFileMultiple`）**：逐文件并发导入 → `plugin-dialog-multiple` 列表展示；仅 `(is_official || is_safety) && !duplicate_type` 的文件执行 `saveAndReleasePlugin`（`bk_biz_id` 官方取 0），其余提示「插件包不完整/名字冲突/插件冲突」；全部完成后关闭弹窗触发列表重拉

**提交边界 / 生效时机**：导入解析本身不改动平台数据；只有 `saveAndReleasePlugin`（或跳向导完成制作）才落库。**导入缓存仅在跳转 `plugin-add`/`plugin-update` 之间保留**——离开列表或刷新即丢。

**预期结果**：插件出现在列表；冲突包按所选分支完成升级或新建。

**错误处理**：解析失败置失败态；`conflict_ids` 场景按分级限制分支（见 C5 决策 1）；超管限制（`isSuperUser`）影响「更新至现有插件」可用性。

**使用示例**（真实用法，来源 `handeFileSingel` / `plugin-dialog-single.vue` 简化）：

```js
const data = await importPluginCollectorPlugin({ file_data: file });
this.$store.commit('plugin-manager/SET_PLUGIN_CONFIG', data);   // 缓存导入配置
if (data.conflict_detail) { /* 冲突弹窗：按 conflict_ids 决定可用的处理分支 */ }
else if (data.is_official) { await saveAndReleasePlugin({ ...data, bk_biz_id: 0 }); this.getPluginListData(); }
else { this.$router.push({ name: 'plugin-add', params: { pluginData: data, isImportPlugin: true } }); }
```
