## 流程 1：新增一个采集配置（用户全链路）

**业务目标**：为一批主机/服务实例上线一个新的采集任务（如 CPU 指标采集），并确认下发成功。

**调用顺序**：

1. **进入向导**：列表页「新建」（或分类 tab 预选插件类型）→ 路由 `collect-config-add`（`MANAGE_AUTH`）
2. **Step1 配置（`config-set`）**：加载插件与变量（`retrieveCollectorPlugin`、`getCollectVariables`）→ 填参数（采集周期/超时/插件参数/维度注入）→ `canNext` 聚合校验通过 → `$emit('next')`
3. **Step2 选择目标（`config-select`）**：`monitor-ip-selector` 选择拓扑/主机/服务实例；Process 类型先 `checkPluginVersion`（低版本主机弹窗可强制继续）
4. **保存即下发**：「开始下发」→ `saveCollectConfig` 保存配置 → 进入 Step3（**保存动作在本步发生，不是 Step3**）
5. **Step3 下发（`config-delivery`）**：`isTaskReady`（2s 递归）等就绪 → `collectTargetStatus`（10s）展示下发进度；失败可 `rollbackDeploymentConfig` 回滚；K8S 分支有独立 loading 与「任务终止」（CancelToken）
6. **Step4 完成（`config-done`）**：成功/失败统计；出口为「可视化」（`collect-config-view`）或「策略配置」（受 `STRATEGY_VIEW_AUTH`）

**提交边界 / 生效时机**：

- `saveCollectConfig` 成功前不产生任何配置；成功后配置即入库并触发下发（无独立的"部署"按钮）。
- 下发失败后的状态由后端推导，前端只能「重试」（重发 save）或「回滚」（`rollbackDeploymentConfig`）。
- K8S 分支的下发请求可被 `CancelToken` 中止（`handleDeliveryCancel`）。

**预期结果**：配置出现在列表（`config_list`），目标状态收敛为成功（`task_status=SUCCESS`）；失败目标在列表/详情中显示异常并可重试。

**错误处理**：Step1/Step2 校验或保存失败停留在当前步；下发接口失败 → 结果面板重试入口；页面刷新后状态由 5s 轮询从服务端拉回。

**使用示例**（真实调用链组合，来源：`config-select.vue handleDelivery` + `config-delivery.vue`）：

```js
// Step2「开始下发」：校验 → 保存（保存即下发）
const res = await checkPluginVersion(params).catch(() => ({ result: false }));
if (!res.result) { /* 弹窗列出低版本主机，用户确认后继续 */ }
await saveCollectConfig(params);            // POST rest/v2/collecting_config/save/
this.$emit('next');                          // 进入 Step3

// Step3 就绪门闩 + 进度轮询
await this.taskReadyStatusPromise(this.config.data.id);   // isTaskReady 2s 递归，永不 reject（配置 id 在 config 大对象的 .data 内）
this.getHosts();                                      // collectTargetStatus
this.pollingStatus();                                 // 10s 轮询至 hasRunning=false
```

## 流程 2：给采集列表增加一个筛选维度（开发者）

**业务目标**：让列表按新的条件筛选（如按采集对象类型 `target_object_type` 筛选），并保证与现有 tab/统计卡互不干扰。

**调用顺序**：

1. **确认后端支持**：`config_list` 的 `search` 参数是否支持该字段（后端 `monitor_web/collecting` 侧；不支持则先推动后端）
2. **前端加参数映射**：`collector-config.vue` 的 `getSearchOfParams` 中把 UI 状态翻译为 `search` 字段（该方法是筛选的唯一翻译点）
3. **UI 接入**：在工具区/统计卡增加触发控件，变更后调用 `handleSearch`（内部取消在途请求 + 300ms debounce + 重拉）
4. **（如涉及统计）** 统计口径变化改 `fetchCollectConfigStat` 的消费与 `getFilterTabList` 的过滤/排序，**不要动 `TableStore.tabData`**（遗留口径）
5. **回归**：node:test 现有 3 个采集测试 + 手工覆盖"筛选后翻页 / 切换 tab / 搜索词前缀"

**提交边界**：无（纯前端+接口查询）。

**预期结果**：筛选条件变化后列表与统计一致刷新；切 tab/点统计卡行为与既有约定一致（注意：现有行为会清空搜索词，见 C0 已知坑）。

**错误处理**：接口失败 → 首轮置 500 空态并停止轮询；轮询失败 → 保留旧数据。

**使用示例**（来源：`collector-config.vue getSearchOfParams`，新增字段的落点）：

```js
getSearchOfParams() {
  const search = {};
  // ...既有映射：collect_type / status / task_status / need_upgrade / plugin_id / id / fuzzy
  if (this.panel.objectType) {
    search.target_object_type = this.panel.objectType;   // ← 新增筛选维度的落点
  }
  return search;
}
```

## 流程 3：后端采集接口变更的前端适配（开发者）

**业务目标**：后端 `rest/v2/collecting_config/config_list`（或其它接口）新增/修改字段后，前端正确消费。

**调用顺序**：

1. **找影响面**：查 `.fe-index/monitor-pc/apis/collect.md`「直接调用页面」列确认受影响页面（🟢/🟡 才算在用）
2. **改映射点**：`config_list` 的字段消费唯一集中在 `store.ts` 的 `TableStore` 构造（snake_case → 行模型）——先改此处
3. **改消费点**：行模板/列配置（`selectedColumns`）、详情组件（`frontend_config_detail` 的字段在 `collector-config-detail.vue` / `collector-configuration.tsx` 消费）
4. **补测试**：可参照 `tests/collector-detail-isolation.test.cjs` 的「直跑源码 + 依赖 mock」模式补回归
5. **回归清单**：列表渲染、详情两入口（独立页 + 侧滑）、导出/列设置

**提交边界**：无。

**预期结果**：新字段在列表/详情正确展示；旧字段删除时无残留消费点（`grep` 全仓确认）。

**错误处理**：字段不一致会以两种典型形态暴露——`TableStore` 构造抛错中断列表加载（类型一致性破坏，如 `type_list` 缺项）；或字段缺失静默显示空。

**使用示例**（来源：`store.ts TableStore` 构造，新增字段的落点）：

```js
this.data.push({
  id: item.id,
  name: item.name,
  // ...既有字段映射
  newField: item.new_field,          // ← 新增接口字段的映射落点（snake_case → camelCase）
});
```
