# 告警屏蔽专家 — 使用总览

**专家名称**：告警屏蔽专家
**模块路径**：`bkmonitor/packages/monitor_web/shield` + `bkmonitor/alarm_backends/service/converge/shield`
**创建日期**：2026-07-28

---

## 能力清单

本专家覆盖告警屏蔽模块的完整知识，包括：

| 能力域 | 说明 |
|--------|------|
| 屏蔽配置 CRUD | 新增、编辑、解除、列表查询、详情查看 5 种屏蔽类型 |
| 五种屏蔽类型 | 范围屏蔽(scope)、策略屏蔽(strategy)、告警屏蔽(alert)、事件屏蔽(event)、维度屏蔽(dimension) |
| 屏蔽匹配引擎 | 告警引擎中的维度匹配 + 时间匹配双校验机制 |
| 屏蔽缓存同步 | DB → Redis 的定时刷新机制（含 10 分钟预取） |
| 屏蔽结束静默关闭 | `end_policy=close` 型屏蔽接管期间产生的告警，屏蔽结束后由独立任务静默关闭 |
| 屏蔽通知 | 开始/结束通知的触发、幂等锁、多渠道发送 |
| 屏蔽展示 | 前端列表/详情的维度翻译、拓扑路径解析、动态分组名解析 |
| 批量屏蔽 | 多告警批量创建、拓扑节点降级为范围屏蔽 |
| 时区处理 | 业务时区感知的时间解析与周期配置 |

## 使用边界

| 边界 | 说明 |
|------|------|
| 不覆盖告警引擎其他检测器 | 仅覆盖 ShieldStatusChecker，不覆盖收敛、QoS 等 |
| 不覆盖通知模板渲染细节 | 仅覆盖通知触发逻辑，模板见 `notice/shield/` 目录 |
| 不覆盖 IAM 权限配置细节 | 仅标注所需 Action，权限管理见 `bkmonitor.iam` |
| 不覆盖前端 Vue/React 组件 | 仅覆盖后端 API 和 Resource 层 |

## 已知坑

| # | 坑 | 影响 | 规避方式 |
|---|---|------|----------|
| 1 | `event` 类型在存储时会被转换为 `alert` | 查询时需兼容两种类型 | `AddShieldResource.perform_request` 中 `data["category"] = ShieldCategory.ALERT if data["category"] == ShieldCategory.EVENT else data["category"]` |
| 2 | `dimension_config` 中 `_` 开头的键不参与屏蔽匹配 | 存储了附加信息但不匹配 | `_alert_id`、`_severity`、`_alert_message`、`_dimensions` 等以下划线开头 |
| 3 | `ShieldDetectManager`（Web 层）和 `ShieldObj`（引擎层）是两套独立匹配逻辑 | Web 层用集合交集快速检测，引擎层用条件树精确匹配 | 不要混用，Web 层仅用于策略页快速判断是否被屏蔽 |
| 4 | 周期屏蔽的时间处理：`handle_shield_time` 会用 `cycle_config` 的时间部分替换日期时间 | 单次屏蔽和周期屏蔽的时间语义不同 | 周期类型 ≠ 1 时，begin_time/end_time 的时分秒来自 cycle_config |
| 5 | `BulkAddAlertShieldResource` 有 `bk_topo_node` 时会自动将 category 改为 `scope` | 批量屏蔽的类型可能动态变化 | 见 `handle_alerts` 方法中的 `data["category"] = "scope"` |
| 6 | `AlertShieldObj` 使用类级别缓存 `_alert_dimension_cache`（上限 1000） | 大量告警时缓存可能被清理 | 简单 LRU 策略，删除最旧一半 |
| 7 | `ShieldCacheManager.refresh` 会预取未来 10 分钟内生效的屏蔽 | 缓存中有尚未生效的配置 | 引擎层匹配时需检查时间 |
| 8 | 快捷屏蔽接口不在 `ShieldViewSet` 中，而是分散在 `EventViewSet` 和 `QuickAlertHandleViewSet` | 不同 ViewSet 有不同的认证/渲染器 | `quick_shield` 使用 `NoCsrfSessionAuthentication`；`alert/quick_shield` 和 `alert/quick_ack` 使用 `PlainTextRenderer` 返回重定向 HTML |
| 9 | 两个 `quick_shield` 接口（`QuickShield` vs `QuickAlertShield`）功能相似但入口、认证、返回值完全不同 | 容易混淆，选错接口会导致认证失败或返回格式不匹配 | `QuickShield`（POST）是移动端手动操作，支持 scope/strategy/event 三种模式，返回 JSON；`QuickAlertShield`（GET）是通知链接入口，token 验权后批量屏蔽，返回 HTML 重定向 |
| 10 | `add_shield` 和 `quick_shield` 最终都调用 `AddShieldResource`，但 quick_shield 跳过了大量处理逻辑 | quick_shield 不更新 AlertDocument.is_shielded、不检查重复、不处理通知、不校验 MANAGE_DOWNTIME 权限 | 不要假设 quick_shield 和 add_shield 行为一致；如需完整功能（通知、重复检测、ES 状态同步），必须走 add_shield |
| 11 | 移动端 `QuickShield` 独立于 `ShieldViewSet` 存在，有独立的 ViewSet、认证和权限模型 | 移动端（微信 WebView）CSRF 机制不可靠 + 用户通常无 MANAGE_DOWNTIME 权限 + 无法构造完整 dimension_config | 这是合理的设计分层：`EventViewSet` 用 `NoCsrfSessionAuthentication` 绕过 CSRF，`get_permissions()` 返回 `[]` 把权限交给 Resource 自身做宽松校验，`QuickShield.handle_scope/strategy/event` 自动从事件数据推导 dimension_config，移动端只需传 type+event_id+end_time |
| 12 | `dimension_keys` 和 `dimension_conditions` 容易混淆 | 两个字段功能边界不清，用错会导致屏蔽范围不符合预期 | `dimension_keys` 控制"选哪些维度键名参与匹配"（白名单），`dimension_conditions` 控制"维度值如何匹配"（eq/regex/nregex 条件树）。详见 [C1-能力契约 §3a.3](C1-能力契约.md) |
| 13 | scope/event/alert 类型的快捷屏蔽的 `dimension_conditions` 在所有环节（serializer → 持久化 → 匹配引擎）直到 2026-07-30 才补全支持 | 此前传入的 `dimension_conditions` 会被 serializer 静默丢弃或引擎层不消费 | 现已修复：`ScopeSerializer` / `EventSerializer` / `AlertSerializer` 均已添加 `dimension_conditions`（⚠️ 移动端 QuickShield type=event 实际走 `category=alert` → `AlertSerializer`，2026-07-30 才补上，此前该链路字段被静默丢弃），`handle_scope()` / `handle_alert()` 已透传，`ShieldObj._parse_dimension_config()` 已添加 SCOPE + ALERT 分支 |
| 14 | `_parse_dimension_conditions` 对解析失败的条件采用 **fail-close** 语义（替换为永不命中占位 `_NeverMatchCondition`） | 解析失败的条件使所在 AND 组整体不命中，屏蔽范围**收窄**而非扩大 | 设计意图：过度屏蔽（漏告警）比屏蔽不生效更危险。分组边界仅由 condition 声明的 and/or 关系决定，与解析成败无关；全部失败时整个 dimension_conditions 条件组不命中，不会退化为无维度过滤 |
| 15 | `end_policy`（屏蔽结束处理方式）只对 scope/strategy/dimension 开放，且**创建后不可修改** | category 为 alert/event 或 `is_quick=True` 时传 `close` 会被序列化器拒绝；编辑接口传入不同值同样报错 | 快捷屏蔽两入口（`weixin EventViewSet` / `fta_web QuickAlertHandleViewSet`）不传该字段，走默认 `notify_once`；需要 `close` 必须走标准 `add_shield` 且类型合规 |
| 16 | `close` 型屏蔽接管的告警被标记 `shield_end_close=True`，其**通知/分派/复合/动作创建/周期状态检查等副作用全部被切断** | 排查"告警存在但不通知、不执行处理套餐"时，先看该标记，不要误判为通知链路或套餐配置故障 | 只有 `check_shield_end_close_alert`（每分钟）会处理这批告警，确认屏蔽已结束后关闭；判定失败时保留告警不关闭（fail-safe） |
| 17 | `dimension_conditions[].method` 的合法枚举以 `SUPPORT_SIMPLE_METHODS` 为准 = `("include","exclude","gt","gte","lt","lte","eq","neq","reg","nreg")`（`bkmonitor/utils/range/__init__.py:24`），**没有** `contain`/`not_contain` | 按错误枚举传值会被 `DimensionConditionSlz.method` 的 `ChoiceField` 直接拒绝（400）；"包含/排除"语义对应的是 `include`/`exclude` | 以 `SUPPORT_SIMPLE_METHODS` 为准（C1 §3a.4 曾误写 contain/not_contain，2026-09-21 已修正）；`condition` 合法值以 `SUPPORT_COMPOSITE_METHODS = ("or","and")` 为准 |
| 18 | 外部调用方传入**不带时区**的 `begin_time`/`end_time` 字符串时，`handle_shield_time` 会把它**按业务时区解释**（不是按调用方本地时区换算） | 调用方机器时区 ≠ 业务时区时（如 UTC 构建机 + Asia/Shanghai 业务），屏蔽窗口会整体偏移，表现为"时长不对/提前或延后结束" | 调用方尽量传带时区的时间串；或不带时区时间必须按业务时区构造。排查"屏蔽时长不对"时先核对调用方时区与业务时区 |
