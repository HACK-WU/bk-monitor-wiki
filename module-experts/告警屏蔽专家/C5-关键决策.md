## 贯穿原则（先读）

本模块的多条决策共享同一条**保守原则**：**屏蔽范围扩大 = 漏告警，比屏蔽不生效更危险**。因此凡是「无法判定」的场景，一律选择**不屏蔽**（fail-safe toward alerting）。下方决策 1 是这条原则的总则，决策 2、3 是它在不同位置的具体落地。

## 决策清单

### 决策 1：接口契约-屏蔽判定一律 fail-safe：无法判定时选择「不屏蔽」
- **分类**：接口契约
- **动机**：避坑（过度屏蔽 → 漏告警；漏告警的代价高于多告警）
- **决策**：模块内所有「无法判定」的分支都选择不屏蔽，三处实现方向一致：
  - `shield_obj.py`：`dimension_condition` 解析失败 → 替换为永不命中的占位条件（详见决策 2）
  - `shielder/saas_config.py`：`HostShielder.is_matched` 捕获异常后 `return False`（主机屏蔽判定异常时按「未屏蔽」处理，不因异常意外屏蔽告警）
  - `shield_conditions.py`：PromQL 指标换算或表达式搜索不成立 → 一律返回未命中（详见决策 3）
- **背景约束**：屏蔽是「抑制告警」的能力，判定失效的方向决定后果——判定失败时若按「屏蔽」处理会静默吞掉真实告警，比多告警危险得多。
- **被否决方案**：判定失败时忽略该条件继续匹配（fail-open）：否决理由 —— 条件被静默丢弃后屏蔽范围被动扩大，等于漏告警（代码注释：「过度屏蔽导致漏告警，比屏蔽不生效更危险」）
- **已知代价**：配置写错（如条件表达式非法）时表现为「屏蔽不生效」，排障时容易被误认为功能缺陷；需靠日志定位（解析失败会打 `logger.error`）。
- **重新评估触发条件**：出现「因配置解析失败导致屏蔽不生效、且用户无感知」的反馈累计 ≥ 2 次（届时需考虑在列表页暴露配置健康状态）
- **关联代码**：`_NeverMatchCondition` / `_parse_dimension_conditions` @ shield_obj.py；`HostShielder.is_matched` @ shielder/saas_config.py；`PromqlAwareMetricIdCondition` @ shield_conditions.py
- **证据来源**：代码注释（shield_obj.py `_NeverMatchCondition` docstring：「确保解析失败不会让屏蔽范围被动扩大（过度屏蔽导致漏告警，比屏蔽不生效更危险）」）；commit 719abff350（body：「屏蔽范围扩大等于漏告警，比屏蔽不生效更危险」「换算或搜索不成立一律返回未命中，维持「不屏蔽」」）

### 决策 2：接口契约-条件解析失败用「永不命中占位条件」兜底，且分组结构不漂移
- **分类**：接口契约
- **动机**：避坑（解析失败的条件若被静默丢弃，等于该维度不过滤 → 屏蔽范围扩大）
- **决策**：`_parse_dimension_conditions` 中，任何一条 `dimension_conditions` 解析失败（非 dict 或抛异常）都替换为 `_NeverMatchCondition()`（一个 `is_match` 恒返回 `False` 的占位条件），使**所在 AND 组整体不命中**；同时「分组边界仅由 condition 声明的 and/or 关系决定，与解析成败无关」——解析失败不影响分组切分，保证分组结构不漂移。全部条件失败时整个 `dimension_conditions` 条件组不命中，不会退化为「无维度过滤」。
- **背景约束**：维度条件树是 AND/OR 分组结构，丢弃一条条件会改变整组的匹配语义。
- **被否决方案**：
  - 解析失败则跳过该条（continue 不加占位）：否决理由 —— AND 组会因此少一个约束，屏蔽范围被动扩大
  - 解析失败则整条屏蔽配置失效：否决理由 —— 无相关记录；从实现看选择了更细粒度的「组内失败」
- **已知代价**：屏蔽范围**收窄**而非扩大（安全方向）；失败原因只体现在日志（`shield(%s) parse dimension_condition(%s) failed`）。
- **重新评估触发条件**：需要把条件解析失败暴露到屏蔽配置列表/详情（当前只在日志）
- **关联代码**：`_NeverMatchCondition`、`ShieldObj._parse_dimension_conditions` @ shield_obj.py
- **证据来源**：代码注释（shield_obj.py：「分组边界仅由 condition 声明的 and/or 关系决定，与解析成败无关，保证解析失败时分组结构不漂移」「解析失败的条件替换为永不命中的占位条件（fail-close）：所在 AND 组整体不命中，避免条件被静默丢弃后屏蔽范围被动扩大（过度屏蔽导致漏告警）」）

### 决策 3：接口契约-PromQL 策略的按指标屏蔽：独占维度键 + 专用条件类，不并入 `metric_id`
- **分类**：接口契约
- **动机**：避坑（按标准指标建立的屏蔽对引用同一底层指标的 PromQL 策略不生效 → 用户以为屏蔽了实际没屏蔽）
- **决策**：新增 `PromqlAwareMetricIdCondition` 作为 `metric_id` 维度的专用条件——等值匹配命中即短路；失败后才把屏蔽配置的标准 `metric_id` 换算成 PromQL 指标名（`build_promql_metric_names()`：`bk_monitor.system.io.util` → `bkmonitor:system:io:util` / `system:io:util`），按 **token 边界**在原始表达式中搜索，多指标表达式命中任一即命中。原始 PromQL 表达式承载在**独立**告警维度键 `_promql_expressions` 上。
- **背景约束**：PromQL 策略的 `metric_id` 是整段查询表达式（`get_metric_id()` 对 prometheus 数据源直接返回 `promql`），与标准指标的 `bk_monitor.xxx` 集合交恒为空；产品语义是「屏蔽这个指标」，实现却按查询身份字符串比较。
- **被否决方案**（commit body 明确列出）：
  - 把原始表达式并入 `metric_id` 维度：否决理由 —— 会让以 `metric_id` 为 key 的 `dimension_conditions` 多看到一个值，`eq` / `include` / `issuperset` 可能由不命中变命中，即屏蔽范围被动扩大（屏蔽范围扩大等于漏告警）；独立键以下划线开头且不会出现在任何屏蔽配置中，对其它条件零影响
  - 反方向（解析 PromQL 抽取指标名再转标准 `metric_id`）：否决理由 —— 两段式 `data_label:field` 需查 `MetricListCache` 才能还原结果表，会把 DB 查询引入屏蔽匹配路径
  - 依赖 `QueryConfig.metric_id` 做匹配：否决理由 —— 该字段是 `CharField(128)`，`get_metric_id()` 对超长 PromQL 截断成 `promql[:125] + "..."`，指标名可能整个落在截断之外（实测一条 4 维度聚合表达式中指标名结束于偏移 105，再多一个聚合维度即被切掉）
  - 加长 `QueryConfig.metric_id` 字段：否决理由 —— 该截断是字段约束下的有意兜底，正确做法是匹配时不把它当作 PromQL 的完整身份
- **已知代价**：token 边界限定为不匹配 `[A-Za-z0-9_:]`（避免异数据源同名误命中、更长指标名部分命中、截断残缺前缀命中），因此省略前缀的写法走候选匹配；仅在等值失败后才进入新增分支（换算结果按配置 `lru_cache`），非 PromQL 策略无额外开销。
- **重新评估触发条件**：PromQL 表达式中出现无法用 token 边界判定的指标命名形式；或出现「该命中未命中」的漏屏蔽反馈
- **关联代码**：`PromqlAwareMetricIdCondition`、`PROMQL_EXPRESSION_DIMENSION` @ shield_conditions.py；`ShieldObj._parse_dimension_config` / `_calculate_alert_dimension` @ shield_obj.py；`build_promql_metric_names` / `build_promql_metric_patterns` @ bkmonitor/utils/metric_id.py
- **证据来源**：commit 719abff350（body 的「问题 / 改动 / 边界与取舍 / 性能 / 测试」五段，含上述全部被否决方案与实测偏移量数据）

### 决策 5：性能取舍-屏蔽缓存预取未来 10 分钟生效的配置，引擎层仍做时间校验
- **分类**：性能取舍
- **动机**：一致性（避免缓存刷新间隔内新生效的屏蔽「迟到生效」）—— 缓存预取是空间换时间，代价是缓存里存在尚未生效的配置
- **决策**：`ShieldCacheManager.refresh` 拉取 `begin_time <= now + 10分钟` 且 `end_time >= now` 的启用中屏蔽配置，按业务维度写入 Redis；匹配侧（`ShieldObj.is_match`）仍独立校验时间。
- **背景约束**：缓存由定时任务刷新，若只取「当前已生效」，两次刷新之间新生效的屏蔽会延迟到下次刷新才起作用。
- **被否决方案**：只缓存当前已生效 + 缩短刷新间隔：否决理由 —— 无相关记录；现状选择的是固定预取窗口
- **已知代价**：缓存中包含尚未生效的配置，**任何读缓存的旁路都必须自行校验时间**，否则会把未生效的屏蔽当成已生效（C0 已知坑 7）。
- **重新评估触发条件**：预取窗口内（10 分钟）出现「屏蔽提前生效」的反馈；或缓存刷新机制改为事件驱动（届时可移除预取）
- **关联代码**：`ShieldCacheManager.refresh` @ core/cache/shield.py；`ShieldObj.is_match` / 时间匹配 @ shield_obj.py
- **证据来源**：代码注释（core/cache/shield.py：「拉取生效的屏蔽配置，因为是缓存，把未来十分钟内会生效的屏蔽配置也拉进来」）

### 决策 6：[推测] 架构设计-Web 层与引擎层两套匹配逻辑并存，未合并
- **分类**：架构设计（本条为推测，查询侧请降级使用）
- **动机**：性能取舍（Web 层只需快速判断，引擎层需精确匹配）
- **决策**：`ShieldDetectManager`（Web 侧，集合交集快速检测，用于策略列表页判断是否被屏蔽）与 `ShieldObj`（引擎侧，条件树 + 时间匹配精确判定）**并存**，各服务各场景，未抽取公共匹配内核。
- **背景约束**：Web 层面向「策略列表页是否被屏蔽」这类高频轻量判断；引擎层面向「告警是否真的被屏蔽」的精确判定，两者的输入（策略维度 vs 告警维度）与精度要求不同。
- **被否决方案**：无（未找到相关记录）
- **已知代价**：**两套逻辑不可混用**——Web 层结果只能用于展示性判断，不能作为告警是否被屏蔽的依据（C0 已知坑 3）；两边语义漂移时不易发现。
- **重新评估触发条件**：出现「Web 层显示已屏蔽但引擎未屏蔽（或反之）」的反馈；或需要统一的屏蔽预检能力
- **关联代码**：`ShieldDetectManager` @ monitor_web/shield/utils.py；`ShieldObj` @ alarm_backends/service/converge/shield/shield_obj.py
- **证据来源**：无直接证据说明「为何不合并」，基于两套实现的并存结构、各自用途差异与 C0 已知坑 3 的「不要混用」提示推断

### 决策 7：接口契约-通知幂等用 Redis 锁（开始 set / 结束 delete + 无锁不发结束），但任务调度层仍未加锁
- **分类**：接口契约
- **动机**：避坑（定时扫描周期性执行，同一屏蔽的开始/结束通知被重复发送）
- **决策**：`ShieldObj.check_and_send_notice` 中——开始通知前 `NOTICE_SHIELD_KEY_LOCK.client.set(notice_lock_key, "__lock__", ttl)`；`can_send_end_notice` **先检查锁是否存在，无锁直接返回 False**（即只有发过开始通知的屏蔽才可能发结束通知）；结束通知发出后 `delete` 锁。
- **背景约束**：屏蔽通知由 Celery 定时任务周期性扫描触发（`check_and_send_shield_notice` → 分片 `do_check_and_send_shield_notice`），同一配置会被反复扫描到。
- **被否决方案**：无（未找到相关记录）
- **已知代价/遗留问题**：`shield/tasks.py` 仍保留 `# TODO: 确定是否需要加锁，防止重复通知`——**幂等只在 ShieldObj 层，任务调度层（分片重复执行、多实例并发扫描）未加锁**；锁有 TTL，TTL 内外的边界场景（如屏蔽时长超过 TTL）需额外注意。
- **重新评估触发条件**：出现重复通知的线上反馈；或屏蔽周期可能超过锁 TTL 时需评估锁的有效期
- **关联代码**：`ShieldObj.check_and_send_notice` / `can_send_end_notice` / `notice_lock_key` @ shield_obj.py；`do_check_and_send_shield_notice` @ shield/tasks.py
- **证据来源**：代码实现（shield_obj.py 327-349 的 set/get/delete 锁逻辑）；`shield/tasks.py` 第 55 行 TODO 注释（「确定是否需要加锁，防止重复通知」）

### 决策 8：架构设计-移动端快捷屏蔽独立分层：绕过 CSRF、权限下沉、自动推导 dimension_config
- **分类**：架构设计
- **动机**：可维护性（移动端限制无法复用标准屏蔽链路，只能另开入口）
- **决策**：`QuickShield` 独立于 `ShieldViewSet` 存在，具备独立的 ViewSet / 认证 / 权限模型：`EventViewSet` 使用 `NoCsrfSessionAuthentication` 绕过 CSRF，`get_permissions()` 返回 `[]` 把权限交给 Resource 自身做宽松校验，`QuickShield.handle_scope/strategy/event` 从事件数据**自动推导** `dimension_config`，移动端只需传 `type` + `event_id` + `end_time`。
- **背景约束**：① 移动端（微信 WebView）CSRF 机制不可靠；② 移动端用户通常无 `MANAGE_DOWNTIME` 权限；③ 移动端无法构造完整的 `dimension_config`。
- **被否决方案**：复用标准 `ShieldViewSet` 链路：否决理由 —— 上述三条约束下走不通（CSRF 校验失败 / 权限不足 / 参数构造不出）
- **已知代价**：`quick_shield` 与 `add_shield` 最终都调用 `AddShieldResource`，但 quick_shield **跳过大量处理**——不更新 `AlertDocument.is_shielded`、不检查重复屏蔽、不处理通知、不校验 `MANAGE_DOWNTIME` 权限（C0 已知坑 10）；两个 `quick_shield` 接口（`QuickShield` POST 返回 JSON vs `QuickAlertShield` GET token 验权返回 HTML 重定向）易混淆（C0 已知坑 9）。
- **重新评估触发条件**：移动端需要通知、重复检测或 ES 状态同步能力（届时不能简单走 quick_shield）
- **关联代码**：`QuickShield` @ monitor_web 微信/事件侧 ViewSet；`AddShieldResource` @ shield/resources/backend_resources.py
- **证据来源**：C0 已知坑 9、10、11 条目（2026-07-28 资产沉淀时记录的设计说明，含上述三条背景约束）；代码实现（认证类与 `get_permissions()` 覆写）

### 决策 9：接口契约-`dimension_conditions` 全链路补全（含 regex/nregex 正则过滤）
- **分类**：接口契约
- **动机**：避坑（此前传入的 `dimension_conditions` 被 serializer 静默丢弃或引擎层不消费 → 屏蔽范围不符合预期）
- **决策**：全链路支持维度过滤条件——`DimensionConditionSlz` 提取到顶层复用，`ScopeSerializer` / `EventSerializer` / `AlertSerializer` 均新增 `dimension_conditions` 字段；`handle_scope` / `handle_alert` 透传；`ShieldObj._parse_dimension_conditions` 增加 SCOPE + ALERT 分支，并对单条解析失败做 `try/except` 防御性跳过（配合决策 2 的占位条件）；移动端 `QuickShield` 新增 `dimension_conditions` 入参并与屏蔽类型无关地合并进 `shield_params`。
- **背景约束**：维度屏蔽需要「维度键名白名单」（`dimension_keys`）与「维度值匹配方式」（`dimension_conditions`，支持 eq/regex/nregex 条件树）两层能力，此前只有前者。
- **被否决方案**：无（未找到相关记录）
- **已知代价**：`BulkAddAlertShieldResource` **暂未透传** `dimension_conditions`（commit 中标注 TODO）；2026-07-30 之前创建的屏蔽配置不含该字段。
- **重新评估触发条件**：批量屏蔽场景需要维度过滤条件（届时补齐 `BulkAddAlertShieldResource` 透传）
- **关联代码**：`ScopeSerializer` / `EventSerializer` / `AlertSerializer` / `DimensionConditionSlz` @ shield/serializers.py；`handle_scope` / `handle_alert` @ shield/resources/backend_resources.py；`_parse_dimension_conditions` @ shield_obj.py

### 决策 10：接口契约-周期屏蔽的时间语义：`cycle_config` 的时分秒覆盖日期时间
- **分类**：接口契约
- **动机**：一致性（周期屏蔽表达的是「每天/每周的某段时间」，而非一段绝对时间）
- **决策**：`handle_shield_time` 对**周期类型 ≠ 1** 的屏蔽配置，用 `cycle_config` 中的时间部分（begin_time / end_time 的时分秒）**替换** `begin_time` / `end_time` 的日期时间部分；单次屏蔽（周期类型 = 1）则按绝对时间处理。
- **背景约束**：周期屏蔽需要「按天/周重复生效」，必须把重复的时间片段叠加到具体日期上。
- **被否决方案**：无（未找到相关记录）
- **已知代价**：单次屏蔽与周期屏蔽的时间语义不同，跨类型复用时间字段易出错（C0 已知坑 4）；历史上有两轮修复（commit 40c0c40403、393ce1df90）。

### 决策 11：兼容处理-屏蔽接口的时间字段按业务时区解析与展示
- **分类**：兼容处理
- **动机**：一致性（屏蔽时间由用户按本地时间填写与查看，后台统一存 UTC）
- **决策**：屏蔽相关接口在出入参两侧做业务时区转换——详情/列表用 `utc2biz_str` / `strftime_local` 输出，解析用 `localtime` / `str2datetime`；周期屏蔽的时间处理同样基于业务时区。
- **背景约束**：DB 与告警引擎统一使用 UTC，而用户按业务所在时区理解「几点到几点」。
- **被否决方案**：统一用 UTC 或服务器时区：否决理由 —— 无相关记录；从现状看业务时区是明确选择
- **已知代价**：时区转换分散在多个 Resource / DisplayManager 中，新增时间字段时容易漏做转换；跨时区业务的屏蔽展示需按各自业务时区渲染。
- **重新评估触发条件**：出现跨时区业务的时间展示错误；或统一改为前端负责时区渲染
- **关联代码**：`handle_shield_time`（入口，通过 `SpaceApi.get_space_detail` 取业务时区）@ shield/resources/backend_resources.py；`AddShieldResource` / `EditShieldResource` / `ShieldDetailResource` / `FrontendShieldListResource` 的时间转换 @ shield/resources/*.py；`ShieldDisplayManager` @ bkmonitor/utils/shield.py
- **证据来源**：代码 docstring（`handle_shield_time`：「处理屏蔽时间，将时间统一转换为业务时区处理」）；commit 40c0c40403、586259c915（「屏蔽相关接口支持时区」）、393ce1df90（「屏蔽时间处理逻辑问题」）；代码实现（`utc2biz_str` / `strftime_local` / `localtime` 调用）
