### 测试文件详解

**① test_quick_shield.py — `QuickAlertShield.perform_request` 控制流**

- 位置：`bkmonitor/packages/fta_web/tests/alert/test_quick_shield.py`
- 被测源码：`QuickAlertShield.perform_request`（[fta_web/alert/resources.py](file://bkmonitor/packages/fta_web/alert/resources.py#L3099-L3125)）
- 特点：**从源码精确复制被测方法**，通过依赖注入（`now_fn` / `redirect_fn` / `add_shield_fn` / `handle_fn`）隔离全部外部依赖，纯逻辑测试，无需数据库与外部服务。
- 覆盖用例（11 个）：全部成功→重定向 / 部分失败→统计文案 / 全部失败 / 空 alert_ids / 自定义 shield_hours / 默认 3 小时 / handle 抛异常 / add_shield 抛异常 / 单告警成功 / 单告警失败 / `validated_data.pop("alert_ids")` 副作用。

**② test_add_shield.py — 屏蔽 CRUD 全链路**

- 位置：`bkmonitor/tests/api/fta/test_add_shield.py`
- 被测类：`BulkAddAlertShieldResource`、`AddShieldResource`、`ShieldListResource`、`ShieldDetectManager`、`QuickAlertShield`、`QuickAlertAck`
- 依赖：mock `AlertDocument.mget/get/bulk_create`、`AlertLog.save`，需要 Django 测试库。
- 覆盖用例（4 个）：批量告警屏蔽创建、dimension 类型屏蔽 + 列表回查、strategy 类型屏蔽 + `ShieldDetectManager.check_shield_status` 检测、`QuickAlertShield`/`QuickAlertAck` token 快捷操作。

**③ test_shield.py — 引擎层维度补全与主机屏蔽**

- 位置：`bkmonitor/alarm_backends/tests/service/converge/test_shield.py`
- 被测类：`KubernetesCMDBEnricher`（K8s 告警维度补全）、`HostShielder.is_matched`
- 依赖：`KubernetesCMDBEnricher` mock、CMDB host/topo mock、`HostManager`/`HostIPManager` 缓存初始化、`pytest.mark.django_db`。
- 覆盖用例（5 个）：K8s 维度补全（单业务增量 / 多业务增量 / 主机已存在）、HostShielder（主机不存在 / 主机已存在）。

**④ test_strategy_target_shield.py — 策略 target shield 条件合并**

- 位置：`bkmonitor/alarm_backends/tests/core/cache/test_strategy_target_shield.py`
- 被测函数：`StrategyCacheManager.add_target_shield_condition`
- 特点：纯函数测试（monkeypatch CMDB topo 接口），无 django_db。
- 覆盖用例（3 个）：系统事件 target 屏蔽尊重 agg_condition / 相同查询屏蔽保留 / query_md5 分组保持。

## 3. 运行方式

### 3.1 环境要求

- Python 3.11 + 项目 `.venv`（系统 Python 缺 `bkcrypto` 等依赖链，settings 无法加载）
- 显式注入环境变量（`pyproject.toml` 的 `D:` 前缀在变量已置空时不生效）：

```bash
export BKAPP_DEPLOY_PLATFORM=community
export DJANGO_CONF_MODULE=conf.worker.development.community
export USE_DYNAMIC_SETTINGS=0
```

- 必须绕过 `filterwarnings` 解析失败问题（见 [test/known-failures.md](../test/known-failures.md) #1）：

```bash
# pyproject.toml 中的 RemovedInDjango51Warning 在 Django 4.2.27 下解析失败，
# 需 --override-ini 覆盖，或修正 pyproject.toml
```

### 3.2 运行命令

```bash
cd /root/bk-monitor/bkmonitor

# ① 快捷屏蔽纯单元测试（无需 DB，最快）
.venv/bin/python -m pytest packages/fta_web/tests/alert/test_quick_shield.py -q --override-ini "filterwarnings="

# ② 策略 target shield 条件合并（纯函数）
.venv/bin/python -m pytest alarm_backends/tests/core/cache/test_strategy_target_shield.py -q --override-ini "filterwarnings="

# ③ 屏蔽 CRUD Resource（需要 Django 测试库 + 完整迁移文件）
.venv/bin/python -m pytest tests/api/fta/test_add_shield.py -q --override-ini "filterwarnings="

# ④ 引擎层（需要 Django 测试库 + fakeredis/fake ES，见 conftest.py）
.venv/bin/python -m pytest alarm_backends/tests/service/converge/test_shield.py -q --override-ini "filterwarnings="
```

### 3.3 conftest 全局 mock

`alarm_backends/tests/conftest.py` 的 `pytest_configure` 会全局替换：
- Redis → `fakeredis.FakeRedis`（`alarm_backends.core.storage.redis.redis.Redis`）
- ES → `FakeElasticsearchBucket`（`elasticsearch_dsl.connections.Connections.create_connection`）
- `settings.PUSH_MONITOR_EVENT_TO_FTA = False`
- `TestCase.databases = {"default", "monitor_api"}`

`alarm_backends/tests/service/conftest.py` 额外 mock 掉延时队列 `BaseRedisCache.delay`。

## 4. 已知失败

当前开发环境（稀疏检出 43%、Django 4.2.27）下运行测试的已知失败与规避方式，逐一切面标注见 [test/known-failures.md](../test/known-failures.md)。

核心结论（详细见 known-failures）：

| # | 问题 | 影响 |
|---|------|------|
| 1 | `filterwarnings` 引用 `RemovedInDjango51Warning`，Django 4.2.27 无此属性 | 默认 pytest 启动即失败（EXIT=4），所有测试需 `--override-ini "filterwarnings="` |
| 2 | 环境变量需显式注入 | 不注入则 settings 加载报 `BKAPP_DEPLOY_PLATFORM should not be empty` |
| 3 | `test_add_shield.py`：`monitor_web.extend_account` app 未注册 | 收集期 `UserAccessRecord` app_label 报错，需核对 conf 环境配置 |
| 4 | `test_shield.py`：迁移图不一致（metadata.0252 依赖 monitor_web.0076）+ 测试库已存在 | DB setup 失败，需完整检出迁移文件 + 清理 test_bkmonitor_saas |

## 5. 测试缺口

优先级从高到低：

1. **`ShieldObj._parse_dimension_config` / `_parse_dimension_conditions` 条件树解析单测**（含 fail-close 语义、`_NeverMatchCondition` 占位、regex 语法错误不命中）——这是 2026-07-30 修复的核心逻辑，当前无任何直接测试。
2. **`ShieldObj` 时间匹配 + 通知幂等单测**（`can_send_start_notice` / `can_send_end_notice` / Redis 锁行为）。
3. **`ShieldCacheManager.refresh` 缓存刷新单测**（10 分钟预取窗口、按业务分组、无屏蔽删 Key）。
4. **`DisableShieldResource` / `EditShieldResource` 行为单测**（批量解除、失败时间戳、幂等）。
5. **`dimension_conditions` 全链路透传测试**（serializer → `handle_*` → `ShieldObj` 匹配），防止 2026-07-29~30 修复的字段静默丢弃问题回归。
