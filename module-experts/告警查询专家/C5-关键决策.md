## 决策清单

### 决策 1：接口契约-全字段业务名称检索限制 1000 业务命中，超限直接报错而非截断
- **分类**：接口契约
- **动机**：避坑（业务名称全字段检索在应用层把空间名转业务 ID 再生成 ES `terms` 分支，关键词过宽时会生成超大 DSL）
- **决策**：最终去重业务 ID 命中数量**上限 1000**；第 1001 个不同业务 ID 命中时**返回明确校验错误，不生成 ES DSL**；多个全文检索值按合并去重后的业务集合统一计数；租户与显式业务范围过滤**先于**上限判断；1000 及以内保持现有 `terms` / 显式范围 `match_all` 语义。
- **背景约束**：无显式业务范围时，业务名称检索无法安全地化简为 `match_all` 或补集查询——**否则会扩大 Alert / Incident 的召回范围**（越过权限边界）。
- **被否决方案**（commit body 明确列出）：
  - 化简为 `match_all` 或补集查询：否决理由 —— 可能扩大 Alert / Incident 召回范围，属越权风险
  - 截断到前 N 个业务：否决理由 —— commit 明写「不截断」，截断会让结果静默不完整
  - 静默跳过业务名称分支：否决理由 —— commit 明写「不静默跳过」，用户会误以为查全了
- **已知代价**：命中 1001 个业务时整个查询失败（需用户收窄关键词或指定业务范围）；上限值 1000 是硬编码阈值。
- **重新评估触发条件**：出现「业务数在 1000 附近、用户无法理解为何失败」的反馈；或空间名称检索改为 ES 侧完成（可移除应用层展开）
- **关联代码**：`MAX_FULLTEXT_BIZ_MATCHES`（= 1000，模块级常量）@ handlers/base.py；`BaseBizQueryHandler.build_additional_fulltext_query` / `get_fulltext_biz_name_entries` @ handlers/base.py
- **证据来源**：commit e766fa4c79（body 的「背景/修改/验证/Test plan」四段，含上述三条否决方案、1000 上限与「本地 5 万空间模拟：全命中在第 1001 个不同业务处终止，不生成约 290KB DSL」实测数据）；代码 docstring（`build_additional_fulltext_query`：「将业务名称子串命中转换为业务 ID 精确查询，**不对 ES 执行名称通配**」）；代码注释（「空间名称是全文检索的可降级分支」，加载失败时降级为空不阻断主查询）

### 决策 2：安全合规-业务可见性过滤改 fail-close，「全部业务」查询在全量授权时可省略业务 terms
- **分类**：安全合规
- **动机**：避坑（过滤子句为空时业务过滤整体消失 → 越权可见）；优化（十万级 terms 撑爆查询 DSL）
- **决策**：`add_biz_condition` 四种情形收口——已构造业务子句取并集；**指定了业务范围但无任何业务子句 → 追加 `match_none` 失败关闭**；未指定业务范围保持各 Handler 既有语义；单租户 + 明确 `-1` + IAM 全量授权时可省略业务 terms（需同时满足五条件：单租户、请求含 `-1`、`OP.ANY` 或 `skip_check`、授权业务非空、无真实未授权业务）。
- **背景约束**：生产取证中授权业务列表可达 **11.5 万个**，展开后单次查询 DSL 约 **1.15 MB**，是 `/fta/alert/alert/top_n/` 超时的放大因素之一。
- **被否决方案**：见 `.module-experts/issue专家/C5-关键决策.md` 决策 10（同一 commit 的完整否决理由清单：fail-open 状态、以及「通过缓存覆盖推断全量权限」方案）
- **已知代价（告警查询侧特有）**：
  - `add_biz_condition` 是**告警、故障、处理记录、Issue 共用的业务可见性入口**，改它等于改四个域的可见性语义，回归面大
  - 多租户模式、显式业务 ID 列表、无请求上下文、IAM 非全量策略四种情况仍保留 terms（不做省略），因此 TopN 超时问题在多租户下未完全解决
  - 本模块内 `get_bucket_count` 仍使用 `track_total_hits=True`（与搜索主链路的 10000 不同），基数聚合走的是另一条路径
- **重新评估触发条件**：历史索引补齐 `bk_tenant_id` 后可评估多租户下的省略优化；或 TopN 超时仍有复发
- **关联代码**：`add_biz_condition` @ handlers/action.py；`parse_biz_item` / `get_biz_filter_ids` @ handlers/base.py；`get_bucket_count` @ resources.py
- **证据来源**：commit bdc35a27d2（body 五段，含 11.5 万 / 1.15 MB 实测数据）；commit 71b100a2dd、96c8639cb0、f199ce93f3；交叉引用 `.module-experts/issue专家/C5-关键决策.md` 决策 10

### 决策 3：接口契约-`bk_biz_ids=-1` 是「全业务」哨兵，必须展开为授权业务集后才能过滤
- **分类**：接口契约
- **动机**：避坑（把 `-1` 当真实业务 ID 塞进 ES `terms` → 查不到任何告警，`total=0`）
- **决策**：`BaseBizQueryHandler.parse_biz_item` 在构造期把 `-1` 解析为**用户实际授权的业务集**（`authorized_bizs`）；经 `resource.alert.*` 或直接构造 `AlertQueryHandler` 都会自动展开。**切勿**把 `-1` 直接写进 ES `terms` 过滤。
- **背景约束**：`-1` 是「全部业务」的前端标记，不是真实业务 ID，也不应出现在 `unauthorized_bizs` 里（commit bdc35a27d2 已把它归一化移除）。
- **被否决方案**：把 `bk_biz_ids` 原样透传给 ES：否决理由 —— 见上述现象，`total=0`
- **已知代价**：展开结果依赖 IAM 授权集，授权为空时业务子句为空（由决策 2 的 fail-close 兜底）；下游若绕过 handler 直接查 ES 会踩这个坑。
- **重新评估触发条件**：引入新的「全部业务」表达方式（需同步所有 handler 的解析）
- **关联代码**：`BaseBizQueryHandler.parse_biz_item` @ handlers/base.py；`get_biz_filter_ids`
- **证据来源**：C0 已知坑 1（「切勿把 -1 直接塞进 ES terms 过滤」）；commit 71b100a2dd（「新增 get_biz_filter_ids 收口 bk_biz_ids 的 -1 哨兵，防按业务过滤查空复发」）

### 决策 4：接口契约-查询异常 fail-open：返回空响应但携带部分结果后重抛
- **分类**：接口契约
- **动机**：可用性（ES 抖动 / DSL 错误时整页 500 的体验劣于降级展示）
- **决策**：`AlertQueryHandler.search` 捕获异常 → `logger.exception("search alerts error: %s")` → `make_empty_response()` 构造空响应 → 把已构造的 result 挂到 `exc.data` 后**重新抛出**。
- **背景约束**：告警列表是高频主入口，短时故障不应直接返回错误页。
- **被否决方案**：异常直接向上抛（整页 500）：否决理由 —— 无相关记录；现状选择的是「降级数据 + 保留异常」，让前端既能展示又能感知
- **已知代价**：**前端看到的是「无数据」而不是报错**，极易被误判为查询条件写错；排查必须看日志 `search alerts error` 或 `exc.data`。异常仍然会抛，若调用方未处理仍可能 500。
- **重新评估触发条件**：出现「因 fail-open 掩盖了真实故障」的反馈；或需要把降级状态显式返回给前端
- **关联代码**：`AlertQueryHandler.search` @ handlers/alert.py
- **证据来源**：代码实现（try/except + `make_empty_response` + `exc.data = result` + `raise exc`）；C0 已知坑 4；实现层「结论」段（「异常被 search() 捕获并 fail-open，排查时需关注日志」）

### 决策 5：接口契约-结果不完整时用 `partial` 标记 + `total_relation=gte` 显式告知调用方
- **分类**：接口契约
- **动机**：避坑（部分聚合失败时结果静默不完整，用户以为查全了）
- **决策**：聚合/子流程失败时调用 `_mark_partial(code=..., scopes=[...])` 记录不完整范围（如 `aggs.notice_way`）；响应中通过 `get_partial_metadata()` 返回 `partial_reasons`；当 `partial_reasons` 中包含 `total` 时把 `total_relation` 从默认 `eq` 改为 **`gte`**（与 ES 的 `track_total_hits` 语义一致）。
- **背景约束**：告警查询由多个子流程拼装（主查询 + overview + aggs + 通知方式聚合），任一子流程失败都不应让整个查询失败，但必须让调用方知道结果不完整。
- **被否决方案**：子流程失败即整块失败 / 静默返回不完整结果：否决理由 —— 前者可用性差，后者会静默误导；现状是「继续返回 + 显式标记」
- **已知代价**：调用方必须检查 `partial_reasons` 才能知道数据是否可信；新增聚合路径时容易漏加 `_mark_partial`。
- **重新评估触发条件**：出现「调用方未感知 partial 导致误判」的反馈；或需要把不完整范围细化到字段级
- **关联代码**：`_mark_partial` / `get_partial_metadata` / `partial_reasons` / `_check_search_response_completeness` @ handlers/alert.py（及 handlers/base.py）
- **证据来源**：代码实现（`total_relation = "gte"` 分支、`_mark_partial(code="notice_way_aggregation_failed", scopes=["aggs.notice_way"])`）；commit 9ec2fc4119（「告警通知方式查询部分结果缺少完整性标识」）、a564b3f73c（「命中 10000 上限时打 warning 日志，便于排查 notice_way 过滤不完整问题」）

### 决策 6：性能取舍-搜索主链路 `track_total_hits` 用 10000 而非 `True`
- **分类**：性能取舍
- **动机**：优化（`track_total_hits=True` 会强制 ES 精确全量计数，大索引下开销显著）
- **决策**：搜索主链路 `search_object.params(track_total_hits=10000)`；`page_size` 上限 5000（serializers 约束）；导出走 `export_alert`（全量 `scan`，`page_size=0` 语义）。
- **背景约束**：列表展示只需要「够用」的总数精度，超过 1 万的精确总数对分页体验无实际价值。
- **被否决方案**：`track_total_hits=True`（精确计数）：否决理由 —— commit 明写「避免大索引强制全量计数」
- **已知代价**：`total` 超过 1 万时**不精确**（C0 能力边界已声明）；依赖总数做业务判断的调用方会拿到截断值。
- **重新评估触发条件**：出现「需要超过 1 万的精确总数」的诉求；或 ES 集群规格变化使精确计数不再成为瓶颈
- **关联代码**：`AlertQueryHandler.search_raw` @ handlers/alert.py；`page_size` 约束 @ serializers.py；`get_bucket_count`（仍用 `True`）@ resources.py
- **证据来源**：commit a564b3f73c（「perf: track_total_hits=True 改为 10000，避免大索引强制全量计数」）；C0 能力边界与已知坑 5

### 决策 7：接口契约-包含匹配的大小写不敏感用 `case_insensitive=true`，不改 ES mapping
- **分类**：接口契约
- **动机**：一致性（UI 模式的「包含/不包含」应符合用户对大小写不敏感的直觉）
- **决策**：UI 模式 `include` / `exclude` 的 wildcard 查询统一设置 `case_insensitive=true`，保持现有 `*value*` 子串、多值 OR 与排除语义。
- **背景约束**：历史数据已按现有 mapping 写入，改 mapping 需要重建索引。
- **被否决方案**：调整 ES mapping 或为大小写不敏感新增 analyzer：否决理由 —— commit 明写「**无需调整 Elasticsearch mapping 或迁移历史数据**」
- **已知代价**：依赖 ES 的 wildcard `case_insensitive` 参数支持；对 wildcard 查询有额外开销。
- **重新评估触发条件**：ES 版本升级导致该参数行为变化；或出现 wildcard 性能问题需改为 ngram/normalizer 方案
- **关联代码**：`include` / `exclude` 条件构造 @ handlers/base.py（或 handlers/alert.py 条件分支）
- **证据来源**：commit a5326a3bee（body「变更说明」三条，含「无需调整 Elasticsearch mapping 或迁移历史数据」与 94 passed 测试）

### 决策 8：接口契约-`issue_id` 过滤自动展开合并成员，且必须用 `authorized_bizs` 而非原始 `-1`
- **分类**：接口契约
- **动机**：避坑（按合并后主 Issue ID 过滤时，被并入的告警不出现；全业务场景下展开失效）
- **决策**：`AlertQueryHandler.__init__` 内调用 `_expand_merged_issue_conditions()` **原地改写** `self.conditions`，一处覆盖所有经 `AlertQueryHandler` 的路径（search / date_histogram / TopN）；展开时用已解析的 `self.authorized_bizs` 作为 biz 维度；关系层异常或无合并关系时 **fail-open**（保持原条件，体感等同「无合并」）。
- **背景约束**：全业务查询传 `bk_biz_ids=[-1]` 时 `BaseBizQueryHandler` 已把它解析为授权业务集；**直接用 `[-1]` 查 `IssueMergeRelation` 不会有结果**，会让全业务列表 / TopN / histogram 的 `issue_id` 过滤漏掉 active members（docstring 原文）。
- **被否决方案**：在各 Resource 层分别展开：否决理由 —— 需要覆盖 search / histogram / TopN 三条路径，分散展开易漏（docstring：「可一处覆盖所有经 AlertQueryHandler 的查询路径」）
- **已知代价**：合并关系查询失败时静默退化为「不展开」（只记 warning），表现为按主 Issue 查不到被并入告警。
- **重新评估触发条件**：`IssueMergeRelation` 查询方式变化；或需要把展开失败暴露给调用方
- **关联代码**：`AlertQueryHandler._expand_merged_issue_conditions` @ handlers/alert.py；`IssueMergeResolver` @ bkmonitor/issue_merge/
- **证据来源**：`_expand_merged_issue_conditions` 方法 docstring（含「biz 维度用已解析的 authorized_bizs 而非原始 bk_biz_ids」「直接用 [-1] 查 IssueMergeRelation 无结果会让全业务列表漏掉 active members」「fail-open：关系层异常或无合并关系时保持原条件」）；C0 已知坑 3；commit bd7c598464

### 决策 9：兼容处理-`assign_tags` 回退：`event.ip` / `event.bk_cloud_id` 自动 OR 展开嵌套查询
- **分类**：兼容处理
- **动机**：一致性（传统主机告警与 K8s 告警的 IP 字段位置不同，用户用同一个字段搜索应都能命中）
- **决策**：`AlertQueryTransformer.ASSIGN_TAGS_FALLBACK_FIELDS` 声明 `event.ip → ip`、`event.bk_cloud_id → bk_cloud_id`；`_expand_assign_tags_fallback` 把 `event.ip:"x"` 改写为 `(event.ip:"x") OR nested(assign_tags, key="ip" AND value.raw:"x")`。
- **背景约束**：传统主机告警的 `event.ip` 有值；K8s 告警只有 `assign_tags` 中的 `ip` 有值。两者并存，单一字段查询会漏掉其中一类。
- **被否决方案**：只查 `event.ip` 或只查 `assign_tags`：否决理由 —— 会漏掉另一类告警（docstring：「这样传统主机告警和 K8s 告警都能被搜到」）
- **已知代价**：改写后的查询是 nested + OR 组合，DSL 更复杂、开销更高；**必须靠 `context["assign_tags_expanded"]` 标记防重入**——`generic_visit → clone_children → visit_iter` 会递归遍历替换后节点的子节点，其中包含原始 `SearchField("event.ip", ...)`，不加防护会**无限递归**（docstring 原文）。
- **重新评估触发条件**：新增需要回退的字段（需同步 `ASSIGN_TAGS_FALLBACK_FIELDS` 与防重入逻辑）；或告警文档统一 IP 字段位置
- **关联代码**：`AlertQueryTransformer.ASSIGN_TAGS_FALLBACK_FIELDS` / `_expand_assign_tags_fallback` / `visit_search_field` @ handlers/alert.py；`NESTED_KV_FIELDS` @ handlers/base.py
- **证据来源**：`_expand_assign_tags_fallback` docstring（含扩展示例、两类告警并存说明、无限递归警告）；`NESTED_KV_FIELDS` 注释（「对标签进行特殊处理，(tags.a : b) => (tags.key : a AND tags.value : b)」）

### 决策 10：兼容处理-枚举展示值与原始值双向翻译，裸词仅整词相等、中文改短语查询
- **分类**：兼容处理
- **动机**：一致性（用户按界面看到的中文/展示值搜索，而 ES 存的是原始 ID/数值）
- **决策**：三层机制——
  - `VALUE_TRANSLATE_FIELDS`（severity / status / target_type / data_type）：指定字段时把展示值转回原始值（如 `severity:致命 → severity:1`）
  - `build_enum_display_term_query`：裸词精确匹配枚举中文显示名时补 term 查询，**仅做整词相等、不做子串**，避免短词误伤
  - `_quote_translated_query_string`：把翻译生成的原始中文词改为**短语查询**（加引号），避免中文分词误命中
- **背景约束**：旧 query_string 语义是「致命 => 致命 OR severity:1」，需保持兼容；中文分词会把「致命」拆开导致误命中。
- **被否决方案**：裸词对枚举值做子串匹配：否决理由 —— docstring 明写「避免短词误伤」
- **已知代价**：展示值变更（如重命名状态）需要同步维护枚举映射；裸词补齐的 term 查询只在整词相等时生效，输入「致」不会命中。
- **重新评估触发条件**：枚举展示值国际化改造；或枚举项重命名
- **关联代码**：`AlertQueryTransformer.VALUE_TRANSLATE_FIELDS` / `_process_value_translate_fields` / `_process_not_search_field_name` @ handlers/alert.py；`build_enum_display_term_query` / `build_bare_fulltext_query` @ handlers/fulltext.py；`_quote_translated_query_string` @ handlers/incident.py

### 决策 11：性能取舍-告警详情 CMDB 关联查询：≤500 个主机 ID 时合并为单次请求
- **分类**：性能取舍
- **动机**：优化（告警详情按主机 ID 查 CMDB 时存在额外计数请求与重复调用）
- **决策**：精确主机 ID **不超过 500 个**时单次查询 CMDB，避免额外计数请求；空主机 ID 列表直接返回；单页结果不完整时回退原分页逻辑；告警详情只请求拓扑富化需要的**五个主机字段**。
- **背景约束**：告警详情的关联信息展示是高频路径，CMDB 调用次数与字段量直接影响响应。
- **被否决方案**：统一走分页/批量请求：否决理由 —— 小批量场景下计数请求是纯浪费；commit 明确「超过 500 个唯一主机 ID 时保留原分页路径」（即不搞一刀切）
- **已知代价**：500 是硬阈值，超过后行为回退（优化不覆盖大结果集）；通用 `batch_request` 未改动，其他调用方不受益。
- **重新评估触发条件**：CMDB 接口支持更大的单次批量；或出现 500 边界附近的性能差异反馈
- **关联代码**：告警详情关联信息 / 主机信息查询 @ resources.py（或 handlers/alert.py）
- **证据来源**：commit 458460c006（body「变更内容」三条、「变更边界」三条、48 passed 测试）；commit 85cc50592f（「优化告警详情关联信息的无效 CMDB 调用」）

### 决策 12：架构设计-可组合查询管线 + `query_fields` 白名单：新增可查询字段必须注册
- **分类**：架构设计
- **动机**：可维护性（新增查询维度不需要改管线，只改声明式配置）
- **决策**：查询管线固定为 `get_search_object → add_conditions → add_query_string → add_ordering → add_pagination →（可选）add_overview / add_aggs → execute`；所有可搜索字段必须在 `AlertQueryTransformer.query_fields` 中用 `QueryField` 声明（`field` 展示名 / `display` 中文名 / `es_field` / `agg_field` / `is_char` / `searchable` / `alias_func`）。
- **背景约束**：`add_conditions` / `add_query_string` 的字段映射全部来自该白名单；它是 `AlertQueryTransformer` 的翻译中心。
- **被否决方案**：按 ES 字段直接查询（不做映射）：否决理由 —— 展示字段名与 ES 字段名不一致（如 `ip` ↔ `event.ip`），且无聚合字段与值翻译能力
- **已知代价**：**新增可查询字段必须同时维护 `query_fields`**，否则前端字段查不到（实现层技术债已列）；`searchable=False` 的纯计算字段不进 ES，需走 `alias_func`。
- **重新评估触发条件**：字段映射改为从元数据自动生成（可移除手工注册）
- **关联代码**：`query_fields` / `AlertQueryTransformer` @ handlers/alert.py；`QueryField` / `BaseQueryTransformer` / `build_query_string_q` / `add_conditions` @ handlers/base.py
- **证据来源**：代码注释（base.py「可供查询的ES字段配置」、`NESTED_KV_FIELDS`「例如 "tags.": "event.tags"」）；实现层 02-实现.md「新增可查询字段必须在此注册」「查询管线高度可组合，新增查询维度通常只需扩展 query_fields 与 conditions 支持，无需改动管线本身」
