## 决策清单

### 决策 1：架构设计-内置视图用「读时差集同步」保证幂等存在
- **分类**：架构设计
- **动机**：避坑（内置视图定义随版本演进而业务侧无对应视图行 → 页面空白）；降本（免去为每个环境执行迁移脚本）
- **决策**：每次视图列表/详情读取前先执行 `create_default_views`，把「JSON 骨架定义的视图」与「DB 已存在视图」对齐；对齐策略由各场景 Processor 自行实现，实际分四类：
  - ① **双向差集（新增 + 删除）**：`NormalProcessorMixin`（alert 场景）、`HostBuiltinProcessor`（仅 `view_type == "detail"` 才执行，overview 直接 return）、`KubernetesBuiltinProcessor`、`ApmBuiltinProcessor`（删除时只按 `bk_biz_id + scene_id` 过滤，**未按 type 收敛**，删除面比其它实现更宽）
  - ② **仅首次补齐、已有视图即跳过（从不删除）**：`CollectBuiltinProcessor` 及其子类 `CustomEventBuiltinProcessor` / `CustomMetricBuiltinProcessor` / `ObservationSceneBuiltinProcessor`、`UptimeCheckBuiltinProcessor`
  - ③ **完全不建默认视图**：`CustomMetricV2BuiltinProcessor`（默认视图为自由视图，方法直接 return）
- **背景约束**：① 内置视图定义随版本演进会增删改；② 视图按 `bk_biz_id + scene_id + type` 逐业务逐类型落库；③ 模块无独立迁移/任务入口（`tasks.py` 为空占位）。
- **被否决方案**：无（未找到相关记录）
- **已知代价**：删除分支只存在于第 ① 类场景——这些场景下 JSON 骨架文件临时缺失或改名，即**物理删除** DB 视图行（详见 C0 已知问题）；APM 场景的删除还跨 `type` 生效。第 ②③ 类场景无删除风险，但代价是内置视图的增删改不会自动同步到 DB。
- **重新评估触发条件**：出现「用户自建视图被内置同步删除」的线上工单；或单场景内置视图数 > 50 且列表接口 P95 > 500ms
- **关联代码**：`NormalProcessorMixin.create_default_views` @ scene_view/builtin/__init__.py；各 Processor 覆写的 `create_default_views` @ scene_view/builtin/{host,kubernetes,apm,collect,uptime_check,custom_metric_v2}.py；调用点 `GetSceneViewResource.perform_request` / `GetSceneViewListResource.get_view_list` @ scene_view/resources/view.py
- **证据来源**：各 Processor 的 `create_default_views` 实现（bulk_create + 差集 delete / `if existed_views: return` / `return` 三种分支）；commit 58d27694cc（该机制同文件的线上事故修复）

### 决策 2：架构设计-模块级默认视图配置必须深拷贝返回（防跨业务污染）
- **分类**：架构设计
- **动机**：避坑（模块级常量 `DEFAULT_HOST_ORDER` 被原地 `append` 业务指标 → 上一业务看到的面板泄漏到下一业务的请求）
- **决策**：`get_default_order` 对 `DEFAULT_HOST_ORDER` / `DEFAULT_PROCESS_ORDER` 先 `deepcopy` 再加工返回；调用方 `get_order_config` 不再自行 copy，由被调方保证返回副本。
- **背景约束**：默认排序是模块级常量，而「已上报指标」需按 `bk_biz_id` 查 `MetricListCache` 动态追加，两者混合加工必须写副本而非原地修改。
- **被否决方案**：无（未找到相关记录）
- **重新评估触发条件**：新增任何「按业务动态追加面板/排序」的加工点时，须检查是否对模块级常量做 `deepcopy`（验证方式：跨业务并发请求对比返回的面板 id 集合是否互相串扰）
- **关联代码**：`get_default_order` / `get_order_config` @ scene_view/builtin/host.py
- **证据来源**：commit 58d27694cc（diff 明确把 `DEFAULT_HOST_ORDER` 改为 `deepcopy` 后加工，并修复 `metrics.filter(...)` 未回赋值的失效调用）

### 决策 3：性能取舍-内置视图 JSON 进程内缓存 + 双重检查锁加载
- **分类**：性能取舍
- **动机**：优化（APM 场景 34 个 JSON 骨架文件，每次请求读盘 + 递归国际化翻译成本高）
- **决策**：`ApmBuiltinProcessor` / `HostBuiltinProcessor` 在类属性 `builtin_views` 为空时加载一次并缓存，后续复用；APM 用 `threading.Lock` + 双重检查，一次性赋值保证原子性。`NormalProcessorMixin.load_builtin_views` 仍每次重新加载（未纳入缓存）。
- **背景约束**：① Web 进程多线程并发，首次加载需避免重复读盘；② 国际化需按请求语言在运行期执行，因此缓存的是「未翻译骨架」，翻译仍在取配置阶段完成。
- **被否决方案**：
  - 每次请求重新读盘（`NormalProcessorMixin` 现状）：否决理由 —— 文件数多的场景重复 IO 与递归翻译开销大（注释：「等待锁期间可能已经有其他线程『完成』初始化，返回以减少重复读取文件」）
  - 模块级 `_BUILTIN_VIEWS` 全局缓存：否决理由 —— 变量已声明但从未启用，缓存粒度与失效时机未定（C0 已知问题）
- **已知代价**：缓存无失效机制，改 JSON 骨架需重启进程才生效。
- **重新评估触发条件**：内置视图 JSON 需要不停机热更新；或缓存导致的「改了 JSON 不生效」反馈累计 ≥ 2 次
- **关联代码**：`ApmBuiltinProcessor.load_builtin_views` @ scene_view/builtin/apm.py；`HostBuiltinProcessor.load_builtin_views` @ scene_view/builtin/host.py
- **证据来源**：代码注释（apm.py `load_builtin_views`：「双重检查，等待锁期间可能已经有其他线程『完成』初始化，返回以减少重复读取文件」「一次性赋值以确保原子性」）；`_BUILTIN_VIEWS` 声明未使用 @ scene_view/builtin/__init__.py

### 决策 4：接口契约-进程维度以 CMDB 进程名 display_name 分组，而非 CMDB 进程 ID / 单 PID
- **分类**：接口契约
- **动机**：避坑（以 CMDB 进程 ID 作为列表 id → 前端拿该 ID 去过滤 `display_name` 维度 → 图表查询无数据）
- **决策**：进程列表以 `process.name`（display_name）作为稳定 row key 与图表查询变量；同名进程的多个 CMDB 配置合并为一组，组内保留全部端口绑定 `portBindings`，单值字段（protocol/bindIp/port/user）取「排序最小的代表配置」；CPU/内存按同名进程组汇总，`uptime` 固定取 MAX。
- **背景约束**：① TSDB 进程指标以 `display_name` 为维度上报，无 PID 维度时无法按单实例区分；② CMDB 同名进程可存在多条配置（多端口绑定、不同启动命令）。
- **被否决方案**：
  - 以 CMDB 进程 ID 作为列表 id：否决理由 —— 与 TSDB 的 `display_name` 维度不匹配，过滤后图表无数据（commit aa68990ea2 记录的线上故障）
  - 按单 PID 查看进程组指标：否决理由 —— commit 4ca8b24a00 明确列为边界外：「本次保持按 CMDB 进程名 display_name 查看进程组指标，不改为按单 PID 查看」
- **已知代价**：同名进程组的 CPU/内存为合计值；单值字段只代表组内一条 CMDB 配置；`uptime` 只展示组内最大值。
- **重新评估触发条件**：TSDB 进程指标稳定带上 PID 维度且产品要求按实例下钻；或出现「同名进程不同配置需独立展示」的需求
- **关联代码**：`group_process_configs` @ scene_view/process_group.py；`GetHostProcessListResource.perform_request` @ scene_view/resources/host.py；`get_metric_panel`（`group_by=["display_name"]`）@ scene_view/builtin/host.py
- **证据来源**：commit aa68990ea2、08d008d995、4ca8b24a00（PR 描述「边界」段）；代码注释（host.py「分组后继续使用进程名作为稳定 row key」「代表端口及其他单值字段均来自同一条确定的 CMDB 配置」）

### 决策 5：接口契约-端口状态统一取 system.proc_port 的 port_health，三态简化为二态
- **分类**：接口契约
- **动机**：避坑（PromQL 指标 `system:proc_port:proc_exists` 查询恒无数据 → 端口状态图表始终为空）
- **决策**：`GetHostProcessPortStatusResource` 改用 `resource.cc.get_process_port_health`，与 `GetHostProcessListResource` 同数据源；状态映射只保留 `0 正常 / 1 异常`（不再区分 nonlisten）；时间范围改为可传 `start_time`/`end_time`（秒级），不传时保持「最近 5 分钟」默认行为。
- **背景约束**：端口健康是**进程级**指标，图表按同名 CMDB 进程的端口展开，端口共享该进程的健康状态。
- **被否决方案**：
  - 继续用 PromQL `system:proc_port:proc_exists`：否决理由 —— 实测该指标查询无数据，图表恒空（commit 8eb7d38599 body）
  - 保留三态（含 nonlisten）：否决理由 —— 数据源只提供 0/1 健康值，无第三态数据支撑
- **已知代价**：无 listen/nonlisten 区分；查询窗口被收敛为最长 5 分钟（`start_time` 取 `max(传入值, end_time - 300)`）。
- **重新评估触发条件**：`system:proc_port:proc_exists` 恢复上报且产品要求区分 nonlisten；或需要查询超过 5 分钟窗口的端口状态趋势
- **关联代码**：`GetHostProcessPortStatusResource.perform_request` @ scene_view/resources/host.py
- **证据来源**：commit 8eb7d38599（body：「实际测试该指标查询均无数据返回…因此改用 get_process_port_health 统一数据源」+「端口状态从三态简化为二态（注释 nonlisten）」）；代码注释（host.py「端口健康是进程级指标；图表按同名 CMDB 进程的端口展开，端口共享该进程的健康状态」）

### 决策 6：接口契约-进程指标单位与精度约定（比值 0~1、绝对值不 round）
- **分类**：接口契约
- **动机**：避坑（前端把 `fdUsageRate` 当百分数展示 → 数值被放大 100 倍）；一致性（与 `unify_query` 的 data_format 格式化逻辑对齐）
- **决策**：`cpuUsage` / `memUsage` / `fdUsageRate` 返回 **0~1 比值**，前端展示 % 需自行 ×100；`memRss`（字节）/ `uptime`（秒）/ `fdNum`（计数）为绝对值，**不做** round 精度限制；百分比/比值类的 round 精度统一为 `settings.POINT_PRECISION`。
- **背景约束**：① 与 `unify_query.GraphUnifyQueryResource.data_format` 的格式化逻辑需保持一致；② 主机列表的同名字段 `mem_usage` 是 percent(0-100)，与进程侧 percentunit(0-1) 语义不同。
- **被否决方案**：
  - `fdUsageRate` 计算中保留 ×100：否决理由 —— 与「返回比值」约定冲突，前端会二次放大（commit 152775dc1a 移除该 ×100）
  - 对所有运行时指标统一 `round(value, POINT_PRECISION)`：否决理由 —— 绝对值（字节/秒/计数）无需精度限制且会损失整数精度（commit 2819712f98 收敛为只对比值/百分比类生效）
- **已知代价**：与主机列表接口的 `mem_usage` 语义（percent）不一致，跨接口复用易误判（C0 已知问题）。
- **重新评估触发条件**：前端统一改为接收百分数；或 `settings.POINT_PRECISION` 调整
- **关联代码**：`GetHostProcessListResource.perform_request`（`_round_metric`、`runtime_metric_map`、`fdUsageRate` 计算）@ scene_view/resources/host.py
- **证据来源**：commit 1974f50749、152775dc1a（body：「cpuUsage/memUsage/fdUsageRate 返回 0~1 的比值，前端展示为 % 时需自行 *100」）、2819712f98（body：「memRss（字节）、uptime（秒）、fdNum（计数）为绝对值，无需 round 精度限制」）；代码注释（host.py「fdUsageRate = fdNum / fdLimit，返回比值（0~1），前端展示 % 时需自行 *100」）

### 决策 7：性能取舍-进程指标取「选中时点快照」，4 路 TSDB 查询并发
- **分类**：性能取舍
- **动机**：优化（4 路查询串行会叠加网络 IO 延迟）；一致性（进程列表是「当前状态」视图，区间聚合与即时语义冲突）
- **决策**：`GetHostProcessListResource` 用 `ThreadPool` 并发执行 4 路查询（端口健康 / 运行时指标 / 启动时间 / 实例数）；时间参数可选，不传时取默认回溯窗口（进程列表 3 分钟、端口状态 5 分钟、启动时间 180 秒），并以 `instant` 方式取结束时刻快照。
- **背景约束**：① 进程列表展示所选结束时刻的即时状态；② 各 TSDB 查询函数内部已有 `try/except` 返回 `{}`，单路失败不影响整体。
- **被否决方案**：
  - 区间聚合（AVG/MAX over 区间）：否决理由 —— 与「当前状态」语义冲突；commit 4ca8b24a00 明确「进程列表指标仍是所选结束时刻的即时快照」
  - 串行执行 4 路查询：否决理由 —— 每路均有网络 IO 延迟，串行累加（代码注释「四次 TSDB 查询并发执行，缩短接口延迟」）
- **已知代价**：不反映历史 CMDB 快照与依赖异常态（commit 4ca8b24a00 列为边界外）。
- **重新评估触发条件**：产品要求列表展示区间趋势/同环比；或单主机进程数 > 100 时 4 路并发成为瓶颈（可观测判据：接口 P95 > 1s）
- **关联代码**：`GetHostProcessListResource.perform_request`（ThreadPool 4 路）@ scene_view/resources/host.py；`GetHostProcessUptimeResource.perform_request`（`instant=True`）@ 同文件
- **证据来源**：commit 4ca8b24a00（「进程列表指标仍是所选结束时刻的即时快照，历史 CMDB 快照和依赖异常态不在本 PR 范围」）；代码注释（host.py「四次 TSDB 查询并发执行，缩短接口延迟」「取选中时点的进程组快照；前端传秒，UQ 查询使用毫秒」）

### 决策 8：性能取舍-视图列表 panel_count 分级计算（轻量占位 + 未覆盖场景返回 0）
- **分类**：性能取舍
- **动机**：避坑（collect 场景 SceneView 列表慢查询）；避坑（`custom_event_*` / `custom_metric_*` 未兜底导致 `GetSceneViewList` 直接报错）
- **决策**：`CollectBuiltinProcessor.get_view_config` 在 `params.only_simple_info=true` 时返回 N 个 `{"type": "graph"}` 占位面板（N 来自 `get_simple_panel_count`），跳过完整面板渲染与 `MetricListCache` 查询；`get_simple_panel_count` 仅对 `collect_*` / `plugin_*` 精确计数，其他场景返回 0。
- **背景约束**：① 列表接口只需要「有哪些视图 + 大致面板数」；② 完整渲染需查 `MetricListCache` 并按业务拼装 panels，成本高。
- **被否决方案**：
  - 所有场景统一走完整渲染计算 panel_count：否决理由 —— collect 场景已出现列表慢查询（commit 7eada2ad26）
  - 未覆盖场景抛异常：否决理由 —— `custom_event_*` / `custom_metric_*` 会导致整个列表接口报错（commit 5b8992aff9）
- **已知代价**：非 `collect_*` / `plugin_*` 场景列表的 `panel_count` 恒为 0，前端需接受「无面板数」展示。
- **重新评估触发条件**：产品要求 `custom_metric_*` / `custom_event_*` 也展示 panel_count；或出现新的列表慢查询场景
- **关联代码**：`get_simple_panel_count`、`CollectBuiltinProcessor.get_view_config` @ scene_view/builtin/collect.py
- **证据来源**：commit 7eada2ad26、5b8992aff9；docstring（collect.py `get_simple_panel_count`：「用于 SceneViewList 仅请求基础信息时，避免为计算 panel_count 触发完整面板渲染和 MetricListCache 查询」「其他场景类型（如 custom_event_*、custom_metric_* 等）不展示 panel_count，直接返回 0」）

### 决策 9：接口契约-APM 场景不区分视图 type（overview/detail）
- **分类**：接口契约
- **动机**：一致性（APM 视图集合按应用/服务/组件维度组织，无 overview/detail 分层）
- **决策**：`validate_scene_type` 对 `apm_application` / `apm_service` / `kubernetes` / `alert` 场景把 `type` 强制置空；`ApmBuiltinProcessor.get_view_config` 不读 `view.type`，改由 `params` 中的 `app_name` / `service_name` 判断视图形态。
- **背景约束**：这些场景的 view_id 自带层级语义（如 `apm_service-service-default-overview`），无需再用 `type` 字段区分。
- **被否决方案**：无（未找到相关记录）
- **已知代价**：调用方传入 `type` 会被静默忽略（C0 已知问题）。
- **重新评估触发条件**：APM / K8s / alert 场景引入 overview/detail 分层视图
- **关联代码**：`validate_scene_type` @ scene_view/resources/view.py；`ApmBuiltinProcessor.get_view_config` @ scene_view/builtin/apm.py
- **证据来源**：代码注释（apm.py `get_view_config` docstring：「APM下不需要区分视图的type类型(overview/detail)」）

### 决策 10：[推测] 技术选型-内置视图国际化用单一 JSON 骨架 + 运行期递归翻译
- **分类**：技术选型
- **动机**：降本（10 类场景 × 数十个视图，为每种语言维护 JSON 副本成本高）
- **决策**：`view_configs/*.json` 只维护一份，需要翻译的字符串写成 `"_(文本)"` 形式，由 `_translate_config` 递归替换为翻译结果（只翻译 `_(...)` 包裹的字符串）。
- **背景约束**：视图配置是嵌套 JSON（panels / targets / options 多层），翻译点分散在任意层级。
- **被否决方案**：无（未找到相关记录）
- **已知代价**：约定隐式，新增 JSON 字段忘加 `_(...)` 包裹即不翻译（C0 已知问题）。
- **重新评估触发条件**：「新增内置视图字段未国际化」反馈累计 ≥ 2 次；或需要支持运行期切换语言（当前骨架缓存与翻译时机耦合）
- **关联代码**：`BuiltinProcessor._translate_config` @ scene_view/builtin/__init__.py
- **证据来源**：无直接证据，基于 `_translate_config` 仅处理 `_(` 前缀 + `)` 后缀字符串的实现结构，及 C0 已知问题条目推断
