## 简介
`performance` 模块是蓝鲸监控「主机性能 / 拓扑 / 进程」场景的**后端聚合层**：以 Django DRF Resource 形式对外暴露 6 个接口，内部通过线程池并行聚合 CMDB、Agent 状态、TSDB 性能指标、告警计数等多源数据。**自身不含持久化**，`models.py` 已迁空（注释「迁移至 monitor_api 中的 model」）。
章节来源：[resources.py](file://bkmonitor/packages/monitor_web/performance/resources.py#L1-L472) · [models.py](file://bkmonitor/packages/monitor_web/performance/models.py#L11-L13)

## 项目结构
```
bkmonitor/packages/monitor_web/performance/
├── __init__.py            # 版权声明（空逻辑）
├── models.py              # 空（模型已迁移至 monitor_api）
├── resources.py           # 8 个 Resource 类（聚合逻辑核心）
├── host_metric_stats.py   # 卡片统计表达式构造与解释（2026-09 新增，94 行）
├── urls.py                # ResourceRouter 自动注册
└── views.py               # 7 个 ViewSet，绑定 Resource 路由 + IAM 权限
```
各文件职责：`urls.py` 通过 `ResourceRouter.register_module(performance_views)` 注册路由；`views.py` 定义 7 个 ViewSet + `PermissionMixin`（统一 `VIEW_HOST` 权限）；`resources.py` 承载全部聚合业务逻辑；`host_metric_stats.py` 只负责「构造统计用 UQ 表达式 + 解释四量结果」，被 `SearchHostMetricStatsResource` 调用（**纯函数模块，不依赖 DRF**）。

> 增量说明（2026-09-22，PR #12574）：本模块的页级加载还依赖 `bkmonitor/api/cmdb/*` 的四项新能力（`GetHostPage` / `GetHostIdentities` / `GetTopoTreeResource(raw)` / `GetProcess(bk_host_ids)`）与 `TopoTree.module_links_from_raw`，产权属外部 API 集成专题，此处只记消费关系。
章节来源：[urls.py](file://bkmonitor/packages/monitor_web/performance/urls.py#L17-L22) · [views.py](file://bkmonitor/packages/monitor_web/performance/views.py#L25-L74)

## 组件详细分析
### HostPerformanceResource（主机列表，最重接口）
- 设计要点：继承 `CacheResource`，`cache_type = CacheType.HOST`，缓存整份主机列表降低 CMDB/TSDB 压力。
- 关键流程：`api.cmdb.get_host_by_topo_node` 拉全量主机 → 构造 `host_dict` 默认值（指标/状态/进程/告警均为 `None`/`[]`/`UNKNOWN`）→ `ThreadPool` 并行 4 路填充（`get_agent_status` / `get_performance_data` / `get_process_status` / `get_alarm_count`）→ 返回 `{hosts, update_time}`。
- 错误处理：各 fetch 静态方法对 `data` 中缺失 `bk_host_id` 做 `continue` 跳过，单主机缺失不影响整体聚合。
章节来源：[resources.py](file://bkmonitor/packages/monitor_web/performance/resources.py#L43-L127)

### SearchHostMetricResource（指定主机实时指标）
- 设计要点：与 `HostPerformanceResource` 同构，但按 `bk_host_ids` 精确查询、**无缓存**，支持 `start_time`/`end_time` 时间范围。
- 关键流程：`ThreadPool` 并行 4 路（`get_agent_status` / `get_performance_data` / `get_process_status` / `get_alarm_count`），`get_alarm_count` 包裹 `try/except` 降级。
- 错误处理：`get_alarm_count` 捕获所有异常并 `logger.exception` 降级为空列表，不影响其他指标返回。
章节来源：[resources.py](file://bkmonitor/packages/monitor_web/performance/resources.py#L343-L472)

### SearchHostInfoResource 页级模式（2026-09 新增）
- 设计要点：**同一个 Resource 承载「全量」与「按页」两种形态**，靠 `page`/`page_size` 是否成对传参分流——这既避免了新增接口造成的契约分裂，也让老前端继续拿到数组。
- 关键流程（带 `page` 时）：`ThreadPool(2)` 并发发起 ① `api.cmdb.get_host_page`（CMDB 端过滤 + 分页）与 ② `api.cmdb.get_topo_tree(raw=True)`（原始拓扑 dict）；返回后取本页模块 ID 集合，用 `TopoTree.module_links_from_raw(raw_tree, module_ids)` **只为目标模块**构造自底向上路径，再逐主机组装 `module` 字段（`module_cache` 保证同一模块只构造一次展示信息）。
- 错误处理：`page`/`page_size` 不成对、`bk_obj_id`/`bk_inst_id` 不成对、`biz` 根跨业务均抛 `InvalidParamsError`；拓扑或主机查询异常照常抛出（前端按整表错误态处理）。
- 章节来源：`resources.py`（PR #12574 的 `SearchHostInfoResource` 与 `get_module_info`）· [define.py](file://bkmonitor/api/cmdb/define.py#L375)

### SearchHostMetricStatsResource + host_metric_stats（卡片统计，2026-09 新增）
- 设计要点：把「三张卡片各一次 instant 查询」做成**纯表达式聚合**——不在 Python 侧按主机循环，也不允许调用方传任意查询语句（`category` 是 ChoiceField 白名单）。
- 关键流程：`perform_request` → `api.cmdb.get_host_identities`（取身份 + `has_duplicate_ip`）→ `query_host_metric_stats` → `build_host_stats_query` 拼四个量 → `query.query_data(instant=True, 180s 窗口)` → 逐项校验（`is_partial` / 非有限值 / 字段缺失）→ 身份歧义判定 → 返回 `{value, complete, reason}`。
- 错误处理：空 hosts 直接返回 0；其余异常**不吞不重试**，按标准路径上抛，由前端单卡重试。
- 章节来源：`host_metric_stats.py`（PR #12574 新增文件）

### HostTopoNodeDetailResource（拓扑节点详情）
- 设计要点：聚合拓扑节点信息 + 下属主机数 + 告警数 + 策略数 + 负责人。
- 关键流程：`api.cmdb.get_topo_tree().get_all_nodes_with_relation()` 查节点 → `api.cmdb.get_host_by_topo_node` 查下属主机 → `resource.cc.get_topo_strategy_count` 查策略 → `get_alarm_count` 静态方法统计告警。
- 注意：`child_count` 在 `bk_obj_id == "module"` 时取 `len(hosts)`，否则取 `len(node.child)`。
章节来源：[resources.py](file://bkmonitor/packages/monitor_web/performance/resources.py#L181-L245)

### SearchHostInfoResource.get_module_info（跨类复用）
- 设计要点：静态方法 `get_module_info` 被 `HostPerformanceResource` **跨类直接调用**（`SearchHostInfoResource.get_module_info`），构造模块到拓扑根的路径链。
- 关键流程：按 `bk_module_ids` 在 `topo_links` 中查找，输出 `topo_link`（`bk_obj_id|bk_inst_id` 列表）和 `topo_link_display`（节点名列表），均 `reversed` 使根节点在前。
章节来源：[resources.py](file://bkmonitor/packages/monitor_web/performance/resources.py#L286-L310)

## 依赖关系分析
- **内部依赖**（`resource.cc.*`，实现在 `cc/resources/cmdb.py`）：
  - `get_process_info` — 进程信息
  - `get_agent_status` — Agent 状态
  - `get_host_performance_data` — TSDB 性能指标
  - `get_host_alarm_count` — 告警计数
  - `get_topo_strategy_count` — 拓扑节点策略数
- **内部依赖**（`api.cmdb.*`）：
  - `get_host_by_topo_node` — 按拓扑节点拉主机
  - `get_topo_tree` — 拓扑树（含 `convert_to_topo_link` / `get_all_nodes_with_relation`）
  - `get_host_by_id` — 按 ID 拉主机
  - `get_business` — 业务信息
  - `get_service_instance_by_topo_node` — 服务实例（进程）
  - `get_module` — 模块详情（含负责人）
  - `get_host_page` — CMDB 端过滤 + 分页（页级加载，2026-09 新增）
  - `get_host_identities` — 统计所需身份白名单 + `has_duplicate_ip`（复用业务主机预热缓存）
  - `get_topo_tree(raw=True)` — 原始拓扑 dict（跳过 `TopoTree` 构造）
  - `get_process(bk_host_ids=...)` — **构造 Process 之前**按主机过滤服务实例
- **框架依赖**：`core.drf_resource`（Resource / CacheResource / ResourceRouter / ResourceRoute / ViewSet）、`bkmonitor.utils.thread_backend.ThreadPool`、`bkmonitor.utils.cache.CacheType`、`bkmonitor.utils.time_tools`、`bkm_space.validate.validate_bk_biz_id`、`monitor_web.constants.AGENT_STATUS`、`bkmonitor.iam`（权限）；**统计路径额外依赖 `bkmonitor.data_source.UnifyQuery` + `load_data_source`**（直连统一查询，不经 `resource.cc`）
- **跨模块契约依赖**：`bkmonitor/share/handler.py` 的 `HostApiAuthChecker`（分享场景的范围校验与后代节点放行，2026-09 起把本模块两个列表接口登记为 `HOST_LIST_ACTIONS`）；`bkmonitor/models/token.py` 的 `AuthType` 白名单（新增 `SearchHostMetricStatsViewSet.create`）
- **被依赖**：前端主机场景页（主机列表/详情/拓扑树/进程）；`scene_view` 模块间接消费主机拓扑信息

## 结论
模块是纯聚合层、**无 DB**；扩展返回字段需同步改 `host_dict` 默认值 + 新增 fetch 静态方法 + `ThreadPool` 注册。列表接口走 `HOST` 缓存，详情/指标接口实时查询——新增实时字段需评估缓存一致性。2026-09 起新增第三条主线：**页级加载（`GetHostPage` + 本页指标 + 本页拓扑路径）与卡片统计（单次 instant UQ 表达式）**，把「首屏」与「全量」解耦；代价是同一 Resource 出现两种响应结构、页级与全量两套口径需要前端对拍验证。主要风险仍是 `ThreadPool` 并行无超时熔断（单源慢拖慢整体）、两处 `get_process_status` 代码重复，以及页级模式对 `api/cmdb` 新增能力的强耦合（`get_host_page` / `get_host_identities` 任一行为变化会直接影响首屏与卡片统计）。
