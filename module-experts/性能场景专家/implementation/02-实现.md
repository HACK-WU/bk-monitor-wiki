## 简介
实现层围绕两条主线：一是「主机列表/指标的多源并行聚合」，由 `HostPerformanceResource` 和 `SearchHostMetricResource` 通过 `ThreadPool` 4 路并发拉取 Agent 状态、性能指标、进程、告警；二是「拓扑/详情的同步聚合」，由 `HostTopoNodeDetailResource` 和 `HostPerformanceDetailResource` 串行调用 CMDB API 组装完整信息。
**2026-09 新增第三条主线：页级加载与卡片统计**（PR #12574）——`SearchHostInfoResource` 的 `page` 模式把过滤/分页下推给 CMDB 并只为本页构造拓扑路径；`SearchHostMetricStatsResource` + `host_metric_stats.py` 用单次 instant 表达式算出卡片数值与身份完整性。
章节来源：[resources.py](file://bkmonitor/packages/monitor_web/performance/resources.py#L43-L472) · [resources.py](file://bkmonitor/packages/monitor_web/performance/resources.py#L313-L435)

## 核心流程
```mermaid
flowchart TD
  A[perform_request 入参] --> B[api.cmdb.get_host_by_topo_node 拉全量主机]
  B --> C[api.cmdb.get_topo_tree 拓扑链]
  C --> D[构造 host_dict 默认值\n指标=None/状态=UNKNOWN/进程=[]]
  D --> E[ThreadPool 4 路并行]
  E --> E1[get_agent_status\n→ data.status]
  E --> E2[get_performance_data\n→ data.cpu_usage/mem_usage/...]
  E --> E3[get_process_status\n→ data.component]
  E --> E4[get_alarm_count\n→ data.alarm_count]
  E1 & E2 & E3 & E4 --> F[pool.join 汇合]
  F --> G[返回 hosts + update_time]
```
`SearchHostMetricResource` 流程类似，区别：按 `bk_host_ids` 精确查 `api.cmdb.get_host_by_id`，无缓存，`get_alarm_count` 有 `try/except` 降级，支持 `start_time`/`end_time` 时间范围。

页级与统计流程（2026-09 新增，前端一次 `loadData()` 并发三条链，后端只负责其中两次请求）：
```mermaid
flowchart TD
  L[前端 loadData] --> P1[页链: search_host_info page=N]
  L --> P2[全量链: search_host_info 无 page + search_host_metric]
  L --> P3[卡片链: search_host_metric_stats x3]
  P1 --> A1[ThreadPool(2): get_host_page ∥ get_topo_tree raw]
  A1 --> A2[module_links_from_raw 只建本页模块路径]
  A2 --> A3[本页指标: search_host_metric 带本页 IDs]
  P2 --> B1[Worker INIT_BASE / MERGE_METRICS / COMPUTE]
  B1 --> B2[全量就绪: 表格与统计同轮接替\n页级与单卡响应全部失效]
  P3 --> C1[get_host_identities 预热缓存身份]
  C1 --> C2[单次 instant UQ: value/id_count/ip_count/duplicates]
  C2 --> C3[complete=false 时显示未知]
```

## 热点路径
- **`HostPerformanceResource.perform_request`**：拉全量主机 + 拓扑树 + 4 路并行聚合，是主机列表页的核心热点。`HOST` 缓存缓解了大部分请求压力，但缓存失效后的首次请求仍会全量拉取。
- **`get_host_by_topo_node` + `get_topo_tree`**：两个 CMDB 调用串行执行，拓扑树构建有一定开销（`convert_to_topo_link` 遍历全树）。
- **`SearchHostMetricResource`**：无缓存，每次请求都 4 路并发查 TSDB；`get_alarm_count` 的异常降级意味着告警数据可能静默缺失。
- **`HostTopoNodeDetailResource.get_alarm_count`**：遍历所有主机的告警计数再求和，主机数多时是 O(N×级别) 累加。
- **`SearchHostInfoResource` 页级路径**（2026-09 新增）：首次全量仍是最慢路径（本页请求与之并发，互不阻塞）；页级自身的开销集中在 `get_host_page`（下推给 CMDB）与本页指标一次 `search_host_metric`。
- **`TopoTree.module_links_from_raw`**：1 万模块、目标 50 模块的场景下，拓扑实例构造由 10 101 → 0、目标路径仅 150 次，中位耗时 177.8 → 3.1 ms（PR 自测数据，不含网络）。
- **`get_process_info` + `GetProcess(bk_host_ids)`**：5 000 主机 × 4 进程、目标 50 台的场景下，Process 构造由 20 000 → 200，中位耗时 153.4 → 4.8 ms（PR 自测数据）。
- **`host_metric_stats`**：命中预热缓存后仍需**全量解码 + 白名单处理**；表达式本身是单次 instant 查询，冷启动并发回源未消除（PR 明确「本次不引入新的查询框架」）。

## 技术债
- **`get_process_status` 代码重复**：`HostPerformanceResource` 和 `SearchHostMetricResource` 各有一份 `get_process_status` 静态方法，逻辑近乎相同（字段略有差异），未抽取公共方法。
- **`HostPerformanceResource.get_alarm_count` 无降级**：与 `SearchHostMetricResource.get_alarm_count` 不同，`HostPerformanceResource` 版本无 `try/except`，异常会中断整个 `ThreadPool.join`。
- **`ThreadPool` 无超时熔断**：4 路并行任一路慢（如 TSDB 超时）会拖慢整体响应，无独立超时控制。
- ~~**`SearchHostInfoViewSet` 权限缺失**~~（2026-08-31 核对：**已修复，条目过期**）：2026-08-12 的 commit 24f090ed5e 已补齐，当前 6 个 ViewSet 全部继承 `PermissionMixin`；分享场景另有 `SearchHostMetricResource.validate_scope_host_ids` 做 `bk_host_ids` 越权校验。详见 `C5-关键决策.md` 决策 10。
- **`TopoNodeProcessStatusResource` 硬编码置灰**：所有进程 `status` 直接置 `AGENT_STATUS.UNKNOWN`，`ports`/`protocol` 留空，不查实时状态。
- **`HostTopoNodeDetailResource` 串行调用**：拓扑树 + 主机列表 + 策略数 + 负责人 4 步串行，无并行优化。
- **`node` 为 None 的潜在 AttributeError**：`HostTopoNodeDetailResource.perform_request` 中 `node = topo_nodes.get(f"{bk_obj_id}_{bk_inst_id}")` 可能返回 None，非 module 类型时 `len(node.child)` 会抛 `AttributeError`。
- **同一接口双形态的认知成本**（2026-09 新增）：`SearchHostInfoResource` 带不带 `page` 返回结构不同，消费方与测试都需双分支覆盖；未来所有消费方升级后应收敛为对象响应。
- **页级与全量口径一致性无服务端保证**（2026-09 新增）：CMDB 分页结果与全量结果、两套身份（`bk_host_id` vs IP+云区域）的统计口径都靠前端对拍与自动化测试保证，服务端不做一致性校验。
- **统计冷启动回源未优化**（2026-09 新增）：`GetHostIdentities` 复用预热缓存，但缓存 miss 时仍会全量回源并解码；`has_duplicate_ip` 依赖全业务 IP 计数（O(N) 遍历）。
- **前端 Worker 单线程 + 全量重算**（2026-09 新增）：全量首次计算比原实现慢约 5.6%、堆内存 +7.1 MiB，代价转移到了 Worker 侧（三级缓存让后续翻页几乎零成本）。
- **完整测试基线缺失**（2026-09 新增）：PR 自述「完整 Django 测试因缺 `ai_agent` 依赖尚未运行」，且 TS 全库仍有 1 327 项存量诊断未通过（本次无新增）。

## 结论
实现以「ThreadPool 并行聚合 + CacheResource 缓存」为核心模式，适合多源数据聚合场景。扩展返回字段的标准路径：在 `host_dict` 加默认值 → 新增/修改 fetch 静态方法 → 在 `ThreadPool` 注册。2026-09 新增的页级与统计主线把「首屏」从「全量等待」中解耦：页级靠 `page` 参数分流 + CMDB 端分页 + 目标模块路径构造，统计靠单次 instant 表达式聚合 + 身份完整性判定。主要风险在无超时的并行调用、`HostPerformanceResource.get_alarm_count` 的无降级设计、以及页级/全量两套口径的一致性只能靠测试与前端对拍保证；`get_process_status` 代码重复仍是主要可优化点。
