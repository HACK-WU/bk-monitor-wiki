# 数据源查询构造 能力契约

## 1. `load_data_source` 工厂函数

**用途**：通过 `(data_source_label, data_type_label)` 二元组获取对应的 `DataSource` 子类。

**参数**：

| 参数 | 枚举类 | 常用取值 |
|------|--------|----------|
| `data_source_label` | `DataSourceLabel` | `BK_MONITOR_COLLECTOR`、`CUSTOM`、`BK_DATA`、`BK_LOG_SEARCH`、`BK_FTA`、`BK_APM`、`PROMETHEUS` |
| `data_type_label` | `DataTypeLabel` | `TIME_SERIES`、`LOG`、`EVENT`、`ALERT` |

**返回值**：`DataSource` 子**类**（非实例）

## 3. 路径决策机制

### 3.1 UnifyQueryDataSources（硬编码，恒走 unify-query）

```
(BK_MONITOR_COLLECTOR, TIME_SERIES)  # 监控采集指标
(CUSTOM, TIME_SERIES)                 # 自定义指标
```

### 3.2 GrayUnifyQueryDataSources（灰度，条件判定）

```
(BK_APM, LOG)              # APM Trace → 按黑名单判定
(CUSTOM, EVENT)            # 自定义事件 → 按白名单判定
(BK_DATA, TIME_SERIES)     # 计算平台 → 按灰度业务列表判定
(BK_MONITOR_COLLECTOR, LOG) # 监控日志 → 按白名单判定
(BK_LOG_SEARCH, LOG)       # 日志关键字 → 按白名单判定
(BK_LOG_SEARCH, TIME_SERIES) # 日志平台指标 → 按白名单判定
```

灰度判定逻辑：各数据源类实现各自的 `switch_unify_query(bk_biz_id)` 方法，通过 DB/Redis 中的白名单或黑名单决定是否走 unify-query。

### 3.3 原生路径（永不走 unify-query）

不在以上两个列表的组合，`use_unify_query()` 直接返回 `False`，通过 `_query_data_using_datasource` → `DataQueryHandler` 路由到存储后端：
- FTA 事件/告警 → **直连 ES**
- 系统事件/告警 → **直连 ES**
- APM 时序指标 → metadata/ES
- Prometheus → PromQL 直查

## 4. 查询描述对象构造规范

### 4.1 `data_source_class(...)` 参数

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `bk_biz_id` | int | 是 | 业务 ID，用于租户空间解析 |
| `interval` | int | 否 | 聚合窗口（秒），如 `180` = 3 分钟；不传则默认 `1h` |
| `metrics` | list[dict] | 是 | 指标列表，每项 `{field, method, alias}` |
| `table` | str | 是 | 结果表 ID，如 `"system.proc"`、`"system.cpu_summary"` |
| `group_by` | list[str] | 否 | 维度字段列表，分组聚合依据 |

### 4.2 `metrics` 字段详解

| 字段 | 类型 | 说明 |
|------|------|------|
| `field` | str | 真实指标名，来自 `ResultTableField` 中 `tag="metric"` 的字段（如 `cpu_usage_pct`、`load5`） |
| `method` | str | 聚合方法：`AVG`/`SUM`/`COUNT`/`MAX`/`MIN` 或 `*_without_time` 变体 |
| `alias` | str | 在后续 `expression` 中的引用名（如 `"A"`），用于关联计算 |

**多指标示例**（一个 data_source 查询多个指标）：
```python
metrics = [
    {"field": "cpu_usage_pct", "method": "AVG", "alias": "A0"},
    {"field": "mem_res",       "method": "AVG", "alias": "A1"},
    {"field": "uptime",        "method": "AVG", "alias": "A2"},
]
```

约束：多 metrics 会被平铺为 `query_list` 多条目（各自独立 `reference_name=a0~aN`），适合需要关联计算（如 `a0/a1`）的场景，不是批量独立查询。

### 4.3 `group_by` 规范

- 来自 `ResultTableField` 中 `tag="dimension"` 的字段
- 定义分组边界：不同 group 互相隔离，聚合在组内进行
- 常用维度字段：`bk_host_id`、`bk_target_ip`、`bk_target_cloud_id`、`display_name`、`pid`、`username`

---

## 5. 表名与字段来源

查询中的 `table` 和 `metrics[].field` / `group_by` 都来自元数据：

**表名来源**：
- `ResultTable` 模型 → `table_id` 字段
- 命名规则 `DB.TABLE_NAME`：DB = 监控范围（`system`/`docker`），TABLE_NAME = 指标集合（`cpu`/`mem`/`proc`）
- 初始化数据：`init_resulttable.json`

**字段来源**：
- `ResultTableField` 模型 → `field_name` + `tag`（`metric`=指标、`dimension`=维度、`timestamp`=时间）
- 指标字段带 `unit`（如 `%`、`MB`），可聚合；维度字段是描述性字符串

**DataSource → ResultTable 关系**：
- `DataSource` 模型：`bk_data_id` 定义采集通道
- `DataSourceResultTable` 关系表：一对多（一个数据源可对应多个结果表）
- 如 `snapshot`(bk_data_id=1001) 对应 `system.cpu_summary`、`system.io`、`system.disk`、`system.mem` 等多表

## 6. 典型使用示例

### 时序指标查询（最常用，UNIFY 硬编码）
```python
data_source_class = load_data_source(DataSourceLabel.BK_MONITOR_COLLECTOR, DataTypeLabel.TIME_SERIES)
data_source = data_source_class(
    bk_biz_id=bk_biz_id,
    interval=180,
    metrics=[{"field": "proc_exists", "method": "AVG", "alias": "A"}],
    table="system.proc_port",
    group_by=["bk_host_id", "bk_target_ip", "bk_target_cloud_id", "display_name"],
)
```

### 单指标、不同方法
```python
data_source = data_source_class(
    bk_biz_id=bk_biz_id,
    interval=180,
    metrics=[{"field": metric["metric_field"], "method": "MAX", "alias": "A"}],
    table=metric["result_table_id"],
    group_by=["bk_host_id", "bk_target_ip", "bk_target_cloud_id"],
)
```

### 自定义事件查询（GRAY 灰度）
```python
data_source_class = load_data_source(DataSourceLabel.CUSTOM, DataTypeLabel.EVENT)
data_source = data_source_class(bk_biz_id=bk_biz_id, table=..., metrics=...)
```
