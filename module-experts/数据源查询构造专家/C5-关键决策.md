## 决策清单

### 决策 1：架构设计-数据源注册表用「显式类列表 + 每次调用重建映射」，未注册组合直接抛 `KeyError`
- **分类**：架构设计
- **动机**：可维护性（组合数量可控，显式列表一眼可查全部数据源）
- **决策**：`load_data_source(data_source_label, data_type_label)` 在函数体内硬编码数据源子类列表，每次调用都用字典推导重建 `(label, type) → 类` 映射后取键；组合未注册时**直接抛 `KeyError`**，无兜底类、无降级、无业务异常封装。
- **背景约束**：① 组合数量可控（当前 16 个类）；② 调用方（告警策略、图表、APM 检索等）几乎都从元数据拿 `(data_source_label, data_type_label)`，理论上不会出现未注册组合。
- **被否决方案**：无（未找到相关记录）
- **已知代价**：新增数据源必须改这个列表，漏改即运行时 `KeyError`；每次调用重建映射（微小开销）；调用方拿到的是 `KeyError` 而非可读的业务异常（C0 已知问题 1）。
- **重新评估触发条件**：注册组合数 > 30；或需要插件化/装饰器自动注册（如第三方数据源动态接入）
- **关联代码**：`load_data_source` @ data_source/data_source/__init__.py
- **证据来源**：代码实现（函数内列表 + 字典推导 + 直接下标取值）

### 决策 2：接口契约-日志类数据源切换机制三阶段演进：白名单灰度 → 支持全量灰度 → 黑名单豁免
- **分类**：接口契约
- **动机**：降本（切换完成后白名单需为每个新业务手动放行，维护成本高）；止损（黑名单可一键切回）
- **决策**：日志类数据源（日志平台 LOG / TIME_SERIES、监控日志、自定义事件、APM 日志）是否走统一查询的判定机制经历过三次演进，当前形态是**黑名单语义**：
  - 阶段①（2025-11 ~ 12）白名单灰度：走 UnifyQuery 需显式加入白名单（commit 30f43e4adc、563176c124）
  - 阶段②（2025-12）灰度能力补强：支持 `*` 全局禁用（commit 95859b3d96）；期间出现过 `switch_unify_query` 恒返回 `False` 的临时关停（commit 2fdbb026ce）
  - 阶段③（2026-06 ~ 07）支持配置全量灰度（commit ea568bf0f4），随后**正式转为黑名单机制**（commit 35c429eaf7）——默认走统一查询，命中黑名单的业务才切回原生
  - 当前三类黑名单配置：`APM_UNIFY_QUERY_BLACK_BIZ_LIST`（DB 全局配置）、`EVENT_UNIFY_QUERY_BLACK_BIZ_LIST`（DB 全局配置）、`LOG_UNIFY_QUERY_BLACK_BIZ_LIST`（环境变量，逗号分隔业务 ID）
- **背景约束**：切换完成后默认应走统一查询，只有例外业务需要豁免；黑名单可在不动代码的前提下止损。
- **被否决方案**：维持白名单：否决理由 —— commit 35c429eaf7 标题直述「日志数据源切换转为黑名单机制」，切换完成后逐个放行的维护成本高于例外豁免
- **已知代价**：黑名单命中即整业务降级，粒度粗；新业务自动走统一查询，若踩到未知问题只能事后加黑名单；APM/事件黑名单走 DB 全局配置、日志黑名单走环境变量，三类配置**来源不一致**，排查时需分别确认。
- **重新评估触发条件**：三类黑名单长期为空且统一查询稳定 → 可移除切换逻辑、直接恒走统一查询；或出现「需要按场景（而非按业务）豁免」的需求
- **关联代码**：`BaseBkMonitorLogDataSource.switch_unify_query` / `BaseBkMonitorLogDataSource._fetch_black_list` / `BkMonitorLogDataSource._fetch_black_list` / `LogSearchTimeSeriesDataSource._fetch_black_list` @ data_source/data_source/__init__.py；黑名单配置 @ config/default.py、define/global_config.py
- **证据来源**：commit 30f43e4adc、563176c124、95859b3d96、2fdbb026ce、ea568bf0f4、35c429eaf7；代码注释（「如果业务在黑名单中，则不使用 UnifyQuery」「* 在黑名单中，则不使用 UnifyQuery」）；配置注释（global_config.py「APM UnifyQuery 查询业务黑名单，在此列表内的业务，检索能力不切换到 UnifyQuery」，config/default.py「日志 UnifyQuery 查询业务黑名单（环境变量，逗号分隔业务 ID）」）

### 决策 3：兼容处理-提供对账命令，用类成员临时黑名单做切换前后一致性比对
- **分类**：兼容处理
- **动机**：避坑（切换统一查询后口径变化不易察觉，需要可复现的 A/B 比对手段）
- **决策**：新增管理命令 `reconcile_log_strategy`，通过**临时改写** `LogSearchTimeSeriesDataSource.LOG_UNIFY_QUERY_BLACK_BIZ_LIST` 类成员变量，分别在「强制日志平台数据源」与「强制 UnifyQuery」下执行同一策略的查询并比对结果；比对时移除最后一个时间点的数据（注释：「因为日志平台数据源可能存在最后一个时间点数据不稳定的情况」）。
- **背景约束**：线上黑名单来自环境变量/DB 全局配置，不便为对账临时修改；类成员变量优先级高于环境变量，可在进程内临时覆盖。
- **被否决方案**：无（未找到相关记录）
- **已知代价**：类成员变量是**进程级全局状态**，对账过程中若并发执行真实查询会受影响；命令内以 `finally` 恢复为 `None`，但异常中断仍有残留风险。
- **重新评估触发条件**：对账完成、日志数据源切换全量稳定后可移除该命令与 `LOG_UNIFY_QUERY_BLACK_BIZ_LIST` 类成员
- **关联代码**：`LogSearchTimeSeriesDataSource.LOG_UNIFY_QUERY_BLACK_BIZ_LIST` / `_fetch_black_list` @ data_source/data_source/__init__.py；`reconcile_log_strategy` 命令 @ management/commands/reconcile_log_strategy.py
- **证据来源**：命令 docstring（「本命令用于验证日志平台数据源切换到 unify-query 前后查询结果的一致性。通过临时黑名单分别强制使用日志平台数据源和 UnifyQuery，比较两种查询方式的结果是否一致」）；代码注释（「用于灰度对账的临时黑名单列表（类成员变量），对账完成后会清空此列表以恢复正常逻辑」「仅用于命令行对账，线上环境恒定为 None」「移除最后一个时间点的数据（如果存在），因为日志平台数据源可能存在最后一个时间点数据不稳定的情况」）

### 决策 4：接口契约-日志聚类场景统一走统一查询，不受黑名单影响
- **分类**：接口契约
- **动机**：一致性（聚类结果只在统一查询侧存在，原生路径查不到）
- **决策**：`LogSearchTimeSeriesDataSource.switch_unify_query` 中，若结果表名以 `_clustered` 结尾（由 `_get_unify_query_table_suffix` 从条件中解析），**直接返回 `True`**，短路后续黑名单判定。
- **背景约束**：日志聚类产生的结果表结构与原始索引不同，只有统一查询后端支持。
- **被否决方案**：无（未找到相关记录）
- **已知代价**：黑名单无法对聚类场景止损——业务命中黑名单时，普通日志查询走原生，聚类查询仍走统一查询。
- **重新评估触发条件**：原生路径支持聚类结果表查询；或聚类场景出现需要按业务豁免的故障
- **关联代码**：`LogSearchTimeSeriesDataSource.switch_unify_query` / `_get_unify_query_table_suffix` @ data_source/data_source/__init__.py
- **证据来源**：commit 3bef9aeffb（「日志聚类场景统一通过 UnifyQuery 查询」）；代码实现（`_clustered` 后缀短路分支）

### 决策 5：兼容处理-切换前后保持原始日志结构一致（`_meta` 字段归集）
- **分类**：兼容处理
- **动机**：避坑（切换查询后端导致上层依赖的日志字段结构变化 → 前端/告警展示异常）
- **决策**：`process_unify_query_log` 统一把 `__data_label` / `__doc_id` / `__index` / `__result_table` / `__parse_failure` 归集到记录的 `_meta` 下，并把内置时间字段 `_time` 移到 `_meta._time_`；注释明确「仅将内置时间字段移动到 _meta 下，无需统一时间格式」（时间字段可能是字符串或各种单位的事件戳）。
- **背景约束**：日志数据源切换期间，同一份上层代码会分别消费「原生路径」与「统一查询路径」的返回，两者结构必须一致。
- **被否决方案**：无（未找到相关记录）
- **已知代价**：`_meta` 归集逻辑需随后端元字段增减同步维护；时间字段不做统一格式化，下游需自行处理多种时间表示。
- **重新评估触发条件**：统一查询后端直接返回符合约定的 `_meta` 结构（可移除该层转换）
- **关联代码**：`UnifyQuery.process_unify_query_log` @ data_source/unify_query/query.py
- **证据来源**：commit eabea6737e（「日志数据源切换前后保持原始日志结构一致」）；代码注释（「可能是字符串或事件戳（各种时间单位都有可能），这里仅将内置时间字段移动到 _meta 下，无需统一时间格式」）

### 决策 6：兼容处理-cmdb 层级表查询走 bk_sql 直查计算平台（注释标注为临时方案）
- **分类**：兼容处理
- **动机**：一致性（与统一查询侧的 cmdb 层级判定保持一致）
- **决策**：数据源构造阶段，若 `table` 含 `_cmdb_level` 后缀，则剥离该后缀并调用 `to_bk_data_rt_id(raw_table, settings.BK_DATA_CMDB_SPLIT_TABLE_SUFFIX)` 转成计算平台结果表，**用 bk_sql 直查**；与此同时 `UnifyQuery.use_unify_query` 对「cmdb 层级查询 + 表名命中 `settings.BKDATA_CMDB_LEVEL_TABLES` 白名单」的组合直接返回 `False` 走原生路径，两条路径的判定逻辑刻意保持一致。
- **背景约束**：cmdb 层级聚合表由计算平台（bkdata）侧维护，统一查询当前不支持该查询形态。
- **被否决方案**：无（未找到相关记录）
- **已知代价**：这是**被代码注释标注为临时的方案**——注释写明「后续此逻辑去掉，直接将结果表传递给 unify-query 即可」；当前需要维护 `BKDATA_CMDB_LEVEL_TABLES` 白名单与表名后缀约定。
- **重新评估触发条件**：统一查询支持直接查询 cmdb 层级结果表（即注释所述「后续此逻辑去掉」的时机）；届时需同步移除 `use_unify_query` 中的豁免分支
- **关联代码**：`BkdataTimeSeriesDataSource`（表名转换分支）@ data_source/data_source/__init__.py；`UnifyQuery.use_unify_query`（cmdb 层级豁免分支）@ data_source/unify_query/query.py；`BKDATA_CMDB_LEVEL_TABLES` @ config/default.py
- **证据来源**：代码注释（「通过 is_cmdb_level_query 判定是否查询 cmdb 层级表（和 unify-query）判定逻辑保持一致」「如果是层级表查询，则转到计算平台查询」「后续次逻辑去掉。直接将结果表传递给 unify-query 即可」「在 UnifyQuery.use_unify_query 判定中，如果是 cmdb-level 查询，并且在白名单(settings.BKDATA_CMDB_LEVEL_TABLES)里会走到这个逻辑」）；config 注释（「强制使用数据平台查询的 cmdb 层级表」）；commit 79f2823bac（「docs: 补齐cmdb层级查询判定逻辑注释」）

### 决策 7：架构设计-注册表演进：RUM 两个组合新增，当前实际 16 个组合（资产原记 14 已过期）
- **分类**：架构设计
- **动机**：可维护性（RUM 复用 APM Trace 的检索链路，不重复实现）

### 决策 8：兼容处理-未切换统一查询的场景，复刻日志平台的 `query_string` 处理逻辑
- **分类**：兼容处理
- **动机**：一致性（切换前后检索语法行为一致，避免切回原生后检索结果变化）
- **决策**：`_get_unify_query_string` 对未走统一查询的场景，复刻 bklog 日志平台的 `query_string` 构造规则：先 `html.unescape`，空串返回通配符 `*`；命中 `QUERY_SPECIAL_REGEX`（`[+\-=&|><!(){}\[\]^\"~*?:/]` 或 `AND|OR|TO|NOT`）则原样返回；否则两端包通配符（`*关键词*`）。
- **背景约束**：日志平台对 `query_string` 有自己的 DSL 处理规则（含 ES 语法特殊字符判定），原生路径直调其 API，必须在 SaaS 侧还原同样的处理，否则检索语义不一致。
- **被否决方案**：无（未找到相关记录）
- **已知代价**：需跟随日志平台的实现演进维护（注释中给出 Ref 链接指向 bklog 的 `query_string_builder.py`）；SaaS 侧与日志平台侧存在隐式的行为耦合。
- **重新评估触发条件**：全部业务切换至统一查询（该兼容分支可移除）；或日志平台调整 `query_string` 处理规则
- **关联代码**：`LogSearchTimeSeriesDataSource._get_unify_query_string` / `QUERY_SPECIAL_REGEX` / `WILDCARD_PATTERN` @ data_source/data_source/__init__.py
- **证据来源**：代码注释（「背景：没有切换 UnifyQuery 的场景直调日志平台 API，此处对其日志平台对 query_string 的处理逻辑。Ref：https://github.com/TencentBlueKing/bk-monitor/blob/master/bklog/apps/log_esquery/esquery/builder/query_string_builder.py#L46」）；commit ca2a2e841e（「优化告警详情日志查询，对 query string 中的特殊字符进行转义」）、18ada779fc（「修复 SQLCompiler 中对 query_string 转义报错问题」）

### 决策 9：接口契约-ES 排序支持 `-time` 降序简写
- **分类**：接口契约
- **动机**：一致性（与 Django ORM / 本模块其它查询入口的 `-字段` 降序写法保持统一）
- **决策**：ES compiler 的 `_parser_order_by` 支持三种排序写法：`-time`（单字段带前导 `-`）解析为 `{"time": "desc"}`；单字段无前缀为 `asc`；带空格的 `"field desc"` 形式按空格拆分。
- **背景约束**：调用方（尤其从 ORM 侧迁移过来的代码）习惯用 `-字段名` 表示降序。
- **被否决方案**：无（未找到相关记录）
- **已知代价**：字段名本身含前导 `-` 的边缘场景会被误判为降序（实践中字段名不含 `-`）。
- **重新评估触发条件**：出现字段名含 `-` 的排序需求
- **关联代码**：`_parser_order_by` @ data_source/backends/elastic_search/compiler.py；`process_sort_fields` @ data_source/utils/query.py
- **证据来源**：commit d66983ce0c（「ESDataQuery支持order_by的'-time'格式」）；代码注释（compiler.py「支持: "-time" → {"time": "desc"}」；utils/query.py docstring「原始排序字段列表，如 ["-time", "name"] → ["time desc", "name"]」）

### 决策 10：[推测] 架构设计-7 个组合恒走原生路径，未纳入统一查询灰度
- **分类**：架构设计（本条为推测，查询侧请降级使用）
- **动机**：可维护性（这些后端与统一查询的查询模型差异大，接入成本高）
- **决策**：以下 **7 个**组合既不在 `UnifyQueryDataSources` 也不在 `GrayUnifyQueryDataSources`，`use_unify_query()` 恒返回 `False`，直连各自后端：`(PROMETHEUS, TIME_SERIES)`（PromQL 直查）、`(BK_MONITOR_COLLECTOR, EVENT)` / `(BK_MONITOR_COLLECTOR, ALERT)`（直连 ES）、`(BK_FTA, EVENT)` / `(BK_FTA, ALERT)`（直连 ES）、`(BK_APM, TIME_SERIES)` / `(BK_RUM, TIME_SERIES)`（metadata/ES）。注意 APM 与 RUM 的**日志**组合已灰度接入，但两者**时序**组合均未接入。
- **背景约束**：无直接证据说明未接入的原因；从查询形态看，PromQL 直查与事件/告警的文档模型与统一查询的时序/日志查询模型差异较大。
