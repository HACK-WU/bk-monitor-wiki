【专题记忆｜IP 选择器拓扑树】POST /rest/v2/commons/ip_chooser_topo/trees/ 性能画像与瓶颈
- 入口链路：IpChooserTopoViewSet.trees（bkm_ipchooser/views.py:107，list_route，URL_BASE_NAME=ipchooser_topo，路由 urls.py:15）→ TopoHandler.trees（handlers/topo_handler.py:60）→ TopoTool.get_topo_tree_with_count（tools/topo_tool.py:66）→ ResourceQueryHelper（query/resource.py）→ BkApi 抽象（settings.BKM_IPCHOOSER_BKAPI_CLASS = api.cmdb.ipchooser.IpChooserApi）→ api/cmdb/client.py
- 两条统计分支由请求参数 count_instance_type 决定：host 走主机-模块关系；service_instance 走 BkApi.list_service_instance_detail

service_instance 分支的实测事实（APM trace，业务 100864，2026-10-21）：
- 端到端 8.37s，应用内 7.26s（占 86.7%）
- 服务实例全量分页拉取约 6.9~7.2s（占 83~86%），是唯一主瓶颈
- 拓扑树 2 次 CMDB 调用（get_biz_internal_module + search_biz_inst_topo，resource.py:32/59 串行）合计不超过 5%
- 外层差额 1.11s（HTTP、权限、序列化），trace 中未分离
- 请求形态：api.cmdb.client.ListServiceInstanceDetail 约 145~155 个 span，单次 1.2~2.3s，每个下挂一个 HTTP POST 且耗时基本等同父 span（说明耗时在 CMDB 侧与传输，不在本地）
- 推算规模：约 149 页，每页 200 条，约 2.9 万服务实例
- 分页实现：bkm_ipchooser/tools/batch_request.py:63-94，先以 limit=1 探测 count，再按 limit=200 切片，ThreadPool(20) 并发，页数等于 count 除以 200

根因在设计层而非实现层：
- 拓扑树只需要每个模块的实例数量，即 len(ids)，却拉取了完整明细
- 该 CMDB 接口每条明细内嵌 process_instances（process、relation、bind_info 三层嵌套），单页响应体积被放大约两个数量级
- 本地等价结构实测（2.9 万对象）：仅 id 的索引 {module_id: [id]} 为 0.23MB、json.loads 2.2ms；含 process_instances 的明细为 30.45MB、580.7ms，体积差 132 倍、反序列化差 267 倍
- 反证：同一接口 GetServiceInstanceByID（api/cmdb/default.py:781-799）带 service_instance_ids 过滤时 count 等于 len(ids)，通常一页即可，并不慢；慢的是无过滤条件的全业务扫描加全字段返回

既有范式（平台已有两条成熟用法，T1 不是新设计）：
- 纯 ID 下推不查详情：parse_topo_target（packages/monitor_web/cc/resources/cmdb.py:1059-1132）用 get_service_instance_ids_by_topo_node 拿 ID 后直接拼查询条件；GetServiceInstanceIdsByTemplate（api/cmdb/default.py:1027）同理
- 按 id 反查详情：GetServiceInstanceByID（api/cmdb/default.py:781-799）；IpChooserServiceInstanceViewSet.details（bkm_ipchooser/views.py:213-221，IP 选择器选中后按 service_instance_id_list 反查）；另有 alert_events/frontend_resource.py:834,1644、data_explorer/resources.py:510、grafana/time_series.py:911、grafana/unify_query.py:1148、fta_web/alert/resources.py:1077

服务实例 ID 索引（T1 的落点）：
- 定义与读写：ServiceInstanceModuleIndex（api/cmdb/default.py:183-220）。CACHE_KEY 为 web_cache:cc_cache_always:service_instance_module_index:v2:{tenant}:{biz}，INDEX_FIELD 为 module_to_service_instance_ids；build 把 bk_module_id 转 str 作 key、服务实例 id 作 value；set 带 write_id 回读校验
- 写入触发：get_service_instance_by_biz（api/cmdb/default.py:223-234），内部 batch_request 全量拉明细后写索引
- 刷新调度：cache_cmdb_resource（alarm_backends/core/api_cache/library.py:112-137），API_CRONTAB 每分钟触发（:177-181），但按 biz_is_ready 哈希分片（:169-174），单个业务实际间隔等于 RING_NODES 分钟（默认 10，业务数超过 100 时为 20，1000 以上为 30，见 :60-64 与 :184）
- 覆盖范围限制：active_biz_ids 取自 StrategyModel.objects.all().values(bk_biz_id).distinct()（:50-57），只覆盖配过告警策略的业务；无策略的业务索引永远不会被刷新
- TTL 3600s 只是兜底，不是刷新周期
- 缓存介质：cache 是 django.core.cache.cache（api/cmdb/default.py:20），CACHES.default 等于 CACHES.db 等于 DatabaseCache（config/role/web.py:218、config/role/api.py:32），实际是 MySQL 表 django_cache，不是 Redis
- 现成消费方：GetServiceInstanceIdsByTopoNode（api/cmdb/default.py:758-778），索引缺失时抛 CustomError 服务实例拓扑索引尚未就绪

不改功能的优化项与收益：
- T1 拓扑树改读索引：服务实例段 6.9~7.2s 降到 0.05~0.15s，端到端 8.37s 降到约 1.2s（-86%，上限），P95 约 1.5s（-82%）。三个实现陷阱：索引 key 是 str 必须转 int 否则所有 count 变 0；索引缺失必须回退不能抛错；fill_host_count_to_tree 的递归聚合不能改成节点自身 len，父节点是子树 ID 并集
- T2 limit 200 改 500：页数 149 降到约 60，端到端 8.37s 降到 3.8~8s（乐观上界；全量分页的单页体积不能类比按 id 过滤的 500）
- T3 加锁防击穿：缓存未命中无保护，N 个并发各拉一次；优先用 caches.redis 的 add，未配 DJANGO_REDIS_HOST 则退回 default cache
- T5 拓扑树 2 次 CMDB 并行化：省 0.1~0.3s
- T6 ThreadPool(20) 抽成配置、future.get 加 timeout、单页降级：以稳定性收益为主；batch_request 被 13 个文件引用（api/cmdb、api/metadata、api/job、api/node_man、api/bk_login、apm_web 等），提并发是全局抬压
- T7 给 ServiceInstanceModuleIndex.get 加 locmem 一级缓存：省掉每次请求一次 MySQL SELECT

已排除方向：
- 提高并发度：149 页除以 20 为 8 批，服务实例段 6.9s，平均每批约 0.86s；提到 40 乐观省 3.4s、悲观 0.9s，且 T1 落地后该段归零
- gevent worker：greenlet 在 CPU 密集段不会让出，2.9 万条嵌套 dict 反序列化会阻塞同 worker 内所有并发请求；且项目 web 实际是 gunicorn sync（gunicorn_config.py:29-32 未设 worker_class；settings.py:34 的 monkey.patch_all 是自研模块替换，patches 目录下为 json、re、shutil、furl，不是 gevent）
- asyncio：core/drf_resource/contrib/api.py:125 使用同步 requests.session，改异步需把 CMDB、metadata、gse、apigw 全部 API 调用层换成 httpx.AsyncClient

其他发现：
- 前端并发双请求放大：打开 IP 选择器时除 trees 外还会调 service_instance_count（monitor-ip-selector.tsx:513），两者共用缓存 key all_service_instance_detail:{biz} 且都无锁，冷缓存下可能双份全量拉取
- 两套并行机制：all_service_instance_detail（300s，完整明细）与 service_instance_module_index（10~30 分钟，仅 id）互不复用
