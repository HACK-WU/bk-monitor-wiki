kernel_api 异常处理与错误码：api_exception_handler 统一渲染 {code, result, message, data}，HTTP 状态码恒 200，业务错误靠 body.code 表达；data 仅白名单透传 error_code/next_actions 防泄露。web 端需识别 body.code 而非 HTTP 状态码。

## 关键函数
- 符号: `api_exception_handler(exc, context)`
- 位置: `bkmonitor/kernel_api/exceptions.py`
- 实现: ① `ValidationError` 跳过日志，其余 `logger.exception(exc)` ② `json_data = failed(six.text_type(exc))` 生成 {result:false, message, data:{}} ③ `code = getattr(exc, "code", 500)`；DRF 异常补 `detail` 键并取 `status_code` 作为 code ④ data 白名单：仅当 `exc.data` 为 dict 时透传 `error_code`/`next_actions` ⑤ `Response(json_data, content_type="application/json")` 不带 status，HTTP 恒 200

## 设计意图
- `failed()` 默认清空 data：整体透出 `exc.data` 会让 `BKAPIError` 把上游原始响应体泄露到所有 API 角色端点
- HTTP 恒 200 + body.code：前端/web 网关识别业务错误必须认 `body.code`，不要依赖 HTTP 状态码

## web 端识别模式
```python
# web 端 packages/xxx/resources.py
class RenameIssueResource(APIResource):
    def perform_request(self, validated_request_data):
        try:
            return api.issue.rename(validated_request_data)   # 走 kernel_api 网关
        except BKAPIError as e:
            if e.data.get("code") == 3327001:                 # kernel_api 透传的 body.code
                raise IssueRenameConflictError()
            raise
```

## 错误码约定
- `3` 开头统一为蓝鲸平台错误（3301xxx=外部API、3300xxx=业务逻辑）
- kernel_api 侧专有错误码需避免与 `core/errors/upgrade.py` 3318001 等已占用段冲突
- issue 用 3327xxx 段；新增错误码前先 grep `code = 33` 全局占用，选未占用段

## 踩坑点
- 前端看到 HTTP 500 而非真实业务错误码：web 端经 `APIResource` 调 kernel_api，kernel_api 恒 200，web 网关 `BKAPIError` 默认包装为 500 → 前端认 body.code；要 4xx 需在 web 端 Resource 捕获 `BKAPIError` 按 `e.data.code` 重抛专有错误
- kernel_api 层 data 字段丢失：`api_exception_handler` 只白名单透传 `error_code`/`next_actions`，需透传结构化字段时用这两个键
