ShieldCacheManager 是引擎面读取屏蔽配置的唯一入口，避免每条告警都查 MySQL。通过 Celery 定时任务 refresh 将 DB 中生效的屏蔽配置全量同步到 Redis。

- 符号: `ShieldCacheManager.refresh`、`get_shields_by_biz_id`、`publish_failure`、`get_last_failure_end`
- 位置: `bkmonitor/alarm_backends/core/cache/shield.py`

缓存结构:
- Key: CACHE_KEY_PREFIX.shield.biz_{bk_biz_id}
- Value: 该业务下所有生效屏蔽配置的 JSON 列表（extended_json.dumps 序列化）
- TTL: CACHE_TIMEOUT（继承 CacheManager 基类）
- 故障事件: Redis Hash，key=shield.failure.{module}，field=target，value=expected_end_timestamp

刷新逻辑 refresh():
- 拉取所有业务中 begin_time <= now+10min 且 end_time >= now 且 is_enabled=True 的屏蔽配置
- 多预取 10 分钟：让即将生效的屏蔽配置提前进入缓存
- 按业务分组写入 Redis pipeline
- 无屏蔽的业务删除对应 Key
- 序列化用 extended_json（支持 datetime 等自定义类型）

读取路径 get_shields_by_biz_id():
- 从 Redis 读取 JSON 字符串
- extended_json.loads 反序列化为 dict 列表
- 遍历每条配置，将 begin_time/end_time/failure_time 补充 UTC tzinfo
- 缓存不存在时返回空列表 []

匹配快照缓存 ALERT_SHIELD_SNAPSHOT:
- Key: strategy_id + alert_id 组合（无策略的第三方告警不缓存）
- Value: 匹配到的屏蔽配置 ID 列表（JSON 字符串）
- 写入时机: 首次匹配完成后写入，带 TTL 过期
- 作用: 避免每轮检测都重新遍历所有屏蔽配置
