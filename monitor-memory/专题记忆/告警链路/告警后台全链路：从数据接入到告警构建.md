# 告警后台全链路：从数据接入到告警构建

## 四级收敛模型

告警后台（alarm_backends）是一条四级收敛流水线，横跨 access / detect / trigger / alert-builder 四个子系统：

| 层级 | 形态 | 由谁产出 | 关键标识 |
|---|---|---|---|
| 数据点 DataPoint | `{"value": 1.38, "dimensions": {...}}` | `AccessDataProcess` | `record_id = {dimensions_md5}.{timestamp}` |
| 异常点 AnomalyDataPoint | 带 ANOMALY 标记的检测结果 | `DetectProcess` | 写入 `CHECK_RESULT_CACHE_KEY` |
| 事件 Event | 自愈标准格式 | `TriggerProcess` / 事件旁路 | `event_id = anomaly_id` |
| 告警 Alert | 有状态有生命周期 | `AlertBuilder` + `AlertManager` | `dedupe_md5` + UID |

**核心认知**：告警不是"检测到的"，是"构建出来的"。检测只回答"这个点越界了吗"，真正的告警在最后一级按身份去重、合并、赋予状态后才存在。

## 关键源码事实（2026-09-15 实证）

### 接入层 access

- **调度周期** = `min(58, 组内最小 agg_interval)`（`service/access/handler.py:43/172`）。58 是**上限非默认值**，压到 60 秒以内保证 1 分钟周期策略不漏拉
- **QoS** = 周期放大 3 倍（`QOS_INTERVAL_EXPAND` 默认 3，`handler.py:96`）+ 独立队列。**独立队列还需环境变量 `QOS_QUEUE_ENABLE`**（`handler.py:48`），不开则只降频不隔离
- **熔断早拦截**：`AccessDataCircuitBreakingManager` 在刷新阶段就跳过，被熔断的策略组连调度条目都不生成（`handler.py:138-166`）
- **查询时间范围**（`service/access/data/processor.py:565`）：
  - checkpoint 对齐周期边界 `// agg_interval * agg_interval`
  - `from = checkpoint - NUM_OF_COUNT_FREQ_ACCESS * agg_interval`（应对入库延迟）
  - `until = (now - time_delay) // agg_interval * agg_interval`（**SUM 等聚合最后一点不准**，这是告警天然延迟的根本原因；日志/BK_LOG_SEARCH +60s、AIOps SDK +60s）
- **去重**：`filter_duplicates`（`processor.py:718`），TTL = `max_agg_interval * 10`；**延迟到 push() 后刷新**（`processor.py:790` 注释），防止被时间点限制丢弃的数据永久丢失；`max_queried_data_time` 记录含重复数据的最大值，防 checkpoint 死循环
- **`is_partial` 一致性原则**：查询不完整时，**只有配了 `DOUBLE_CHECK_SUM_STRATEGY_IDS` 的策略才整批丢弃**（`processor.py:489-502`）；没配的只打日志照常处理
- **维度补充** `TopoNodeFuller`（`data/fullers.py:20`）补集群/模块；**过滤** `ExpireFilter`/`RangeFilter`/`HostStatusFilter`（`data/filters.py:25/41/77`）按 item 独立记录，`is_retains[item_id]` 用 `and` 叠加

### 检测层 detect

- 主干 `DetectProcess.process()`（`service/detect/process.py:209`）：`service_lock` → `gen_strategy_snapshot()` → 逐 item `pull_data`/`handle_data`/`double_check` → `push_data`
- **策略快照**保证同一轮用同一套配置；快照 key 带到告警里 → **改阈值不影响历史告警显示**
- `pull_data`（`:41`）：队列**左进右出**，`lrange` 后必须 `reversed()` 才保序（`:79`）；单批上限 `SQL_MAX_LIMIT`，超限 `is_busy=True` 延迟而非丢弃
- **算法三分支**：`BasicAlgorithmsCollection`（静态阈值/ProcPort/PingUnreachable）、`RangeRatioAlgorithmsCollection`（同比/环比/振幅，**要拉历史点，是检测主要性能开销**）、`SDKPreDetectMixin`（AIOps）
- **输出**：`CHECK_RESULT_CACHE_KEY`（SortedSet，score=时间戳，异常记 `{timestamp}|ANOMALY`，常量 `ANOMALY_LABEL` 在 `core/detect_result/__init__.py:26`）+ `LAST_CHECKPOINTS_CACHE_KEY`。**两 key 模板耦合**，`core/cache/key.py:398/441` 有互相引用注释，改一个必须改另一个
- **二次确认默认关**：`double_check`（`:181`）白名单制，注释明说原因是性能考虑，留了"后续优化性能后默认开启"TODO

### 触发层 trigger

- `process()`（`service/trigger/processor.py:664`）：**`in_alarm_time()` 不过直接跳过**（`:666`，这是"告警不触发"排查第一检查点）
- `AnomalyChecker._check_anomaly_by_level`（`checker.py:168`）：`check_window_offset = check_window_size * check_window_unit - 1`，`zrangebyscore` 取窗口内记录，数 `ANOMALY` 后缀条目，`anomaly_times >= trigger_count` 即触发。**是窗口内累计，非严格连续**
- **级别从高到低遍历，高级别已触发则跳过低级别**（`:144`）→ 一条数据只出最高级别一个事件
- **无数据告警独立逻辑**：用 `get_no_data_configs`（单级别），补充判定要求"窗口内全异常 + 时间跨度 >= (trigger_count-1)*窗口单位"（`:210`）
- `MonitorEventAdapter.adapt()`（`core/alert/adapter.py:104`）输出自愈事件：`event_id = anomaly_id`；**`extra_info.origin_alarm` 保留完整原始数据**（data/trigger/anomaly/strategy_snapshot_key）——**是唯一可靠的溯源来源**；`dedupe_keys = [f"tags.{k}" for k in dimensions]`

### 构建层 alert.builder

- `handle()`（`builder/processor.py:174`）= `enrich_events` → `save_events` → `dedupe_events_to_alerts`
- **事件保存错误分类**（`:258`）：`409` = uid 重复（poller 拉取窗口重叠，**正常**）；其他 = 数据类型与 ES mapping 不符（真错误）。分开统计避免 409 噪声淹没真错误
- **去重 MD5**：`DEFAULT_DEDUPE_FIELDS = ["alert_name","strategy_id","target_type","target","bk_biz_id"]`（`constants.py:75`）；**有 `strategy_id` 时移除 `alert_name`**（`core/alert/event.py:167` 注释"这是监控特有逻辑"）→ **改策略名不炸开告警**；`cal_dedupe_md5`（`:205`）目标类型扩展兼容置空 target
- **锁粒度 = `dedupe_md5`**（`:112`）；**加锁失败 5 秒重试不丢弃**（`:139`）
- **build_alerts 四分支**（`:365`）：屏蔽接管(shield_end_close)→update / **级别升高→关旧建新**（`severity_source != AssignMode.BY_RULE` 才走）/ 级别降低→丢弃事件记 EVENT_DROP / 同级→update / 无告警+非异常→跳过
- `should_send_signal()`（`core/alert/alert.py:616`）= `_refresh_db and not is_blocked and not shield_end_close` → **被屏蔽的告警不发信号**
- **`enrich_alerts` 只富化新告警**（docstring 明写，富化有外部调用很慢）

### 养护层 alert.manager

- `INSTALLED_CHECKERS`（`manager/processor.py:31`）顺序固定：Next → Close → **Recover** → Shield → Ack → Upgrade → ActionHandle
- **加锁失败策略与 builder 不同**：builder 5 秒重试，manager 等下一轮。原因：builder 处理新事件（丢了就没了），manager 处理存量告警（下轮还会捞起）
- `alerts_finalized = True` 在落库后设置（`:180` 注释）：此后异常不会导致终态告警被下周期重新捞起重发 signal

### 事件旁路

`service/access/event/processorv2.py`（`AccessCustomEventGlobalProcessV2`）**跳过 detect 与 trigger 两级**，直接产出事件进 `alert.builder`。因为事件本身就是异常（agent 心跳丢失、自定义事件），无需算法判定与"连续 N 次"。**两条链路在 alert.builder 汇合**——所以 builder 的输入契约是"事件"而非"异常点"。

无数据告警走主链路，用 `NO_DATA_TAG_DIMENSION = "__NO_DATA_DIMENSION__"`（`constants.py:67`）标记，告警名自动加 `[无数据]` 前缀（`adapter.py:117`）。

## 排障要点

- **告警不触发**：先看 `in_alarm_time`（日志 `not in alarm time`）→ 触发条件（数 `CHECK_RESULT_CACHE_KEY` 里 ANOMALY 条目）→ 事件被 enrich 丢弃（日志 `dropped(N/M)`）→ 保存失败（日志 `save events ERROR`）→ **限流静默丢（只能看 `TRIGGER_EVENT_RATE_LIMIT_DROP` 指标）**
- **告警炸开**：查 `dedupe_md5` 是否变化（改维度/改目标/跨业务迁移）；改名不会炸开
- **告警延迟**：三个自带延迟 = time_delay + 58s 周期 + 队列积压；用 `access_time`/`detect_time`/`trigger_time`（都在 origin_alarm 里）定位卡点
- **告警不恢复**：`RecoverStatusChecker` 未跑 / 加锁一直失败 / shield_end_close / 无 strategy_id
