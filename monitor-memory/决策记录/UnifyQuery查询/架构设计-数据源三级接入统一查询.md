【决策记录｜UnifyQuery 数据源分三级接入统一查询（全量/灰度/未接入），不一次性切换】
- 分类：架构设计
- 动机：避坑（一次性全量切换的失败风险）、可维护性（各数据源能力不同需逐个验证）
- 决策：use_unify_query 按数据源 id 分三级：全量（UnifyQueryDataSources 三类，BK_MONITOR_COLLECTOR+TIME_SERIES、CUSTOM+TIME_SERIES、BK_APM+EVENT）恒走统一查询后端；灰度（GrayUnifyQueryDataSources 七类，APM日志、RUM日志、自定义事件、计算平台时序、主机采集日志、日志检索 LOG 与 TIME_SERIES）由各数据源 switch_unify_query(bk_biz_id) 决定；不在两列表中恒走数据源原生查询
- 背景约束：数据源逐批迁移（计算平台 2024-01 灰度、Trace 检索 2025-04 灰度、日志 2025-11 与 2026-03、枚举值 2026-08），各批次查询语义与后端能力不一致；灰度期同一份代码对不同业务可能走不同链路
- 被否决方案：一次性全量切换，否决理由为 commit e0900310e3 标题即标注灰度，其后 dc07f88329 与 c925aacf09 连续两次灰度 unify-query 查询失败修复，说明分阶段是踩坑后的选择；仅按数据源类型判定不做能力判定，否决理由为多数据源联合查询、表达式、查询函数、分位数等场景原生路径不支持
- 已知代价：切换状态耦合 settings（BKDATA_USE_UNIFY_QUERY_GRAY_BIZ_LIST、各类 UNIFY_QUERY_BLACK_BIZ_LIST、IS_ACCESS_BK_DATA）与 settings.ROLE，同一查询在不同环境或业务可能走不同链路，问题难复现
- 重新评估触发条件：灰度业务列表包含 0 业务（代码注释约定即为全量）后可移除灰度分支；或新增数据源类型接入
- 关联代码：UnifyQuery.use_unify_query @ unify_query/query.py；UnifyQueryDataSources 与 GrayUnifyQueryDataSources @ constants/data_source.py
- 证据来源：代码注释（use_unify_query 各判定分支：如果是多指标必然会走统一查询模块、灰度切换 unify-query 判定不灰度就全量放开）；commit e0900310e3、dc07f88329、c925aacf09、8e9217a8a3、485290b5a6、f0453a87d6
