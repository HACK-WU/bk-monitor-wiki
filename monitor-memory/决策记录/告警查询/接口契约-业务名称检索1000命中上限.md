【决策记录｜告警查询 全字段业务名称检索限制 1000 业务命中，超限直接报错而非截断】
- 分类：接口契约
- 动机：避坑（业务名称全字段检索在应用层把空间名转业务 ID 再生成 ES terms 分支，关键词过宽时会生成超大 DSL）
- 决策：最终去重业务 ID 命中数量上限 1000；第 1001 个不同业务 ID 命中时返回明确校验错误，不生成 ES DSL；多个全文检索值按合并去重后的业务集合统一计数；租户与显式业务范围过滤先于上限判断；1000 及以内保持现有 terms 与显式范围 match_all 语义
- 背景约束：无显式业务范围时，业务名称检索无法安全化简为 match_all 或补集查询，否则会扩大 Alert 与 Incident 的召回范围（越过权限边界）
- 被否决方案：化简为 match_all 或补集查询，否决理由为可能扩大 Alert 与 Incident 召回范围属越权风险；截断到前 N 个业务，否决理由为 commit 明写不截断，截断会让结果静默不完整；静默跳过业务名称分支，否决理由为 commit 明写不静默跳过，用户会误以为查全了
- 已知代价：命中 1001 个业务时整个查询失败（需用户收窄关键词或指定业务范围）；上限值 1000 是硬编码阈值
- 重新评估触发条件：出现业务数在 1000 附近、用户无法理解为何失败的反馈；或空间名称检索改为 ES 侧完成（可移除应用层展开）
- 关联代码：MAX_FULLTEXT_BIZ_MATCHES（等于 1000，模块级常量）@ packages/fta_web/alert/handlers/base.py；BaseBizQueryHandler.build_additional_fulltext_query 与 get_fulltext_biz_name_entries @ handlers/base.py
- 证据来源：commit e766fa4c79（body 的背景、修改、验证、Test plan 四段，含三条否决方案与本地 5 万空间模拟在第 1001 个业务处终止、不生成约 290KB DSL 实测数据）；代码 docstring（build_additional_fulltext_query：将业务名称子串命中转换为业务 ID 精确查询，不对 ES 执行名称通配）；代码注释（空间名称是全文检索的可降级分支，加载失败时降级为空不阻断主查询）
