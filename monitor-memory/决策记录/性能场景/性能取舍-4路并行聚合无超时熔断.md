【决策记录｜性能场景 4 路 ThreadPool 并行聚合，但不做独立超时熔断】
- 分类：性能取舍
- 动机：优化（CMDB、TSDB、Agent 状态、告警四路串行会叠加延迟）
- 决策：HostPerformanceResource 与 SearchHostMetricResource 均用 ThreadPool 并发执行 4 路填充，各路以原地回填 host_dict 的方式汇合（pool.close 后 join），不设独立超时控制，单路慢会拖慢整体响应
- 背景约束：各路数据源（CMDB API、UQ、ES）自身已有超时与重试机制，模块层不再重复实现
- 被否决方案：在模块层引入 per-future 超时（如 future.get 带 timeout）后降级，无相关记录；现状是依赖下游超时，代价是单源慢会拖慢整体（已列入实现层技术债）
- 已知代价：任一路慢（如 TSDB 超时）会拖慢整体；HostPerformanceResource 的告警路无 try 与 except，异常会中断整个聚合
- 重新评估触发条件：出现单路慢导致列表接口 P95 显著劣化（可观测判据：单路耗时大于整体 P95 的百分之八十）
- 关联代码：HostPerformanceResource.perform_request、SearchHostMetricResource.perform_request @ monitor_web/performance/resources.py
- 证据来源：代码实现（ThreadPool 4 路且无 timeout 参数）；C0 能力边界（不做超时熔断）与已知坑（并行无超时）；实现层 02-实现.md 技术债条目
