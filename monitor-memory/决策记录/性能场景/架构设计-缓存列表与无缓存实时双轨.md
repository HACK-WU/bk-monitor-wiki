【决策记录｜性能场景 缓存列表接口与无缓存实时接口双轨并存】
- 分类：架构设计
- 动机：优化（列表页高频访问、数据允许短暂滞后）、一致性（实时视图与时间范围查询必须拿最新数据）
- 决策：HostPerformanceResource 继承 CacheResource（缓存类型 HOST），缓存整份主机列表结果；SearchHostMetricResource 不走缓存，按 bk_host_ids 精确查询并支持 start_time 与 end_time 时间范围。两份实现各自持有一套 get_process_status 等静态方法（字段略有差异）
- 背景约束：主机列表是高频入口，每次全量拉 4 路成本过高；但告警与实时视图需要即时数据，缓存不可接受
- 被否决方案：单接口加可选缓存开关，无相关记录；现状是两套并行实现，代价是逻辑重复
- 已知代价：同一段聚合逻辑存在两份实现（get_process_status 在两处各写一遍且字段不同：HostPerformanceResource 版含 ports 与 protocol，SearchHostMetricResource 版不含），改一处必须同步另一处；HostPerformanceResource.get_alarm_count 无 try 与 except 降级，与另一份实现不一致
- 重新评估触发条件：两份实现的字段差异引发前端兼容问题；或重构合并为一份共享实现
- 关联代码：HostPerformanceResource（CacheResource 子类）、SearchHostMetricResource（ApiAuthResource 子类）@ monitor_web/performance/resources.py
- 证据来源：代码实现（两个类的继承差异）；C0 已知坑（缓存不实时、component 字段差异、get_process_status 代码重复）；commit ae0298af48（主机列表 cache 序列化问题处理）
