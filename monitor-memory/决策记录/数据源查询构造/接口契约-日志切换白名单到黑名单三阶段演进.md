【决策记录｜数据源查询构造 日志类数据源切换机制三阶段演进：白名单灰度到全量灰度到黑名单豁免】
- 分类：接口契约
- 动机：降本（切换完成后白名单需为每个新业务手动放行，维护成本高）、止损（黑名单可一键切回）
- 决策：阶段一 2025-11 至 12 白名单灰度，走 UnifyQuery 需显式加入白名单（commit 30f43e4adc、563176c124）；阶段二 2025-12 支持星号全局禁用（commit 95859b3d96），期间出现过 switch_unify_query 恒返回 False 的临时关停（commit 2fdbb026ce）；阶段三 2026-06 支持配置全量灰度（commit ea568bf0f4），2026-07 正式转为黑名单机制（commit 35c429eaf7），默认走统一查询，命中黑名单的业务才切回原生。当前三类黑名单：APM_UNIFY_QUERY_BLACK_BIZ_LIST 与 EVENT_UNIFY_QUERY_BLACK_BIZ_LIST 走 DB 全局配置，LOG_UNIFY_QUERY_BLACK_BIZ_LIST 走环境变量逗号分隔
- 背景约束：切换完成后默认应走统一查询，只有例外业务需要豁免；黑名单可在不动代码的前提下止损
- 被否决方案：维持白名单，否决理由为 commit 35c429eaf7 标题直述转为黑名单机制，切换完成后逐个放行成本高于例外豁免
- 已知代价：黑名单命中即整业务降级粒度粗；新业务自动走统一查询，踩到未知问题只能事后加黑名单；三类黑名单配置来源不一致（两类 DB 全局配置、一类环境变量），排查时需分别确认
- 重新评估触发条件：三类黑名单长期为空且统一查询稳定后可移除切换逻辑直接恒走统一查询；或出现需要按场景而非按业务豁免的需求
- 关联代码：BaseBkMonitorLogDataSource.switch_unify_query 与 _fetch_black_list、BkMonitorLogDataSource._fetch_black_list、LogSearchTimeSeriesDataSource._fetch_black_list @ data_source/data_source/__init__.py；黑名单配置 @ config/default.py 与 define/global_config.py
- 证据来源：commit 30f43e4adc、563176c124、95859b3d96、2fdbb026ce、ea568bf0f4、35c429eaf7；代码注释（如果业务在黑名单中则不使用 UnifyQuery、星号在黑名单中则不使用 UnifyQuery）；配置注释（APM UnifyQuery 查询业务黑名单，在此列表内的业务检索能力不切换到 UnifyQuery；日志 UnifyQuery 查询业务黑名单环境变量逗号分隔业务 ID）
