## 双回调安全机制：signed_state HMAC 验签 + Session state 机制

### B-03 应用态授权回调（signed_state HMAC 验签）

**问题背景**
- 用户点击「授权」→ 浏览器被重定向到 TAPD 安装页 → 点击「立即安装」→ TAPD 回调 PaaS
- 仅当 state 身份保证与点击「授权」的人一致时，才允许代表用户创建绑定关系
- `initiator`（创建者）从 `signed_state` Payload 提取，不支持透传；强身份约定由单一可信方（PaaS 侧）生成

**state 格式**
```
{ "bk_biz_id": 2, "bk_tenant_id": "default", "space_uid": "bkcc__2", "initiator": "admin", "exp": 1750691375 } + "_" + HMAC_SHA256("bk_biz_id=...", key=DJANGO_SECRET_KEY)[:16]
```

**验签流程**
1. 检查 `exp` 是否超期（15 分钟）
2. 重新计算 HMAC，对比末尾 16 位 hex
3. 通过后使用 Payload 中的 `initiator` 作为 `create_user` / `update_user`
4. 用得到的 `token` 调用 `GetGrantedWorkspacesResource`
5. 逐项检查 `workspace_id` 与请求人等字段，匹配则创建绑定关系

**为何恢复 HMAC（v2→v3）**？- v2 改为仅 JWT Sign 导致 `initiator` 透传不可信、跨浏览器/跨账号场景存在安全风险；- v3 恢复 HMAC，仅 PaaS 能生成有效签名，第三方无法伪造

### B-05 用户态授权回调（Session state 机制）

**state 格式**：`nonace:bk_biz_id`，其中 `nonce` = `{username}:{随机串}`

**安全机制**
1. 点击「去关联」时将 `{username}:{随机串}` 存入 Redis + Session
2. 回调时校验 state 是否与 Redis 中记录的 nonce 匹配
3. 同时校验回调 domain 白名单
4. code 一次性使用，用后即删

**对比**
| 维度 | B-03 signed_state | B-05 Session state |
|------|-------------------|-------------------|
| 鉴权强度 | 最高（HMAC + exp + 单点写入） | 高（Redis nonce + domain + 一次性） |
| 使用场景 | 应用态安装（管理员一次性全网同意） | 用户态 OAuth（逐用户同意） |
| 谁创建 | 后端生成 | 后端生成 |
| 存储位置 | 嵌入 URL（加密 + 签名） | Redis（TTL = 300s） |
| 审计优势 | `initiator` 可信，明确责任人 | 权限主体精确 |
