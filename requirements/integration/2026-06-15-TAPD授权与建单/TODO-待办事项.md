## ISSUE-001：`importable` 状态缺少「一键关联」接口

### 发现时间
2026-06-22

### 问题描述
当前 API 设计中，`importable` 状态表示：TAPD 侧已授权蓝鲸监控应用，但本地 `TapdWorkspaceBinding` 表中没有与当前 `bk_biz_id` 的绑定记录。

用户点击「一键关联」后，系统需要在本地数据库**创建绑定记录**，使状态从 `importable` → `bound`。

但当前接口清单中没有承担此职责的接口：
- B-01 `GET /user_workspace/`：只读查询
- B-07 `POST /workspace/`：只读查询 app 已授权列表
- B-03 / B-05：均为 TAPD 回调接口，不处理业务侧主动绑定

### 两个可选方案

| 维度 | 方案 A：新增「一键关联」接口（推荐） | 方案 B：合并到现有建单流程 |
|------|-----------------------------------|---------------------------|
| **端点** | `POST /fta/issue/tapd/workspace/bind/` | 复用现有建单接口（本次迭代范围外） |
| **核心行为** | 校验 workspace 在 TAPD 已授权列表 → 调用 GetWorkspaceInfoResource 补全信息 → INSERT TapdWorkspaceBinding | 建单时后端隐式检测 `importable` 并自动创建绑定 |
| **优点** | 职责清晰；错误透明；不侵入已有接口；用户可单独完成「关联」而不必立刻建单 | 少一个新接口 |
| **缺点** | 多一个接口 | 隐式行为，无法区分「关联失败」vs「建单失败」；修改已有建单接口有回归风险 |
| **对前端影响** | 明确：点击「一键关联」→ 调用新接口 → 成功后刷新列表 → 状态变 `bound` | 模糊：前端直接走建单流程，绑定行为对前端不可见 |

### 已受影响文档
- `frontend-guide/load-tapd-workspaces.md` 中 Q1 描述为「一期实现中，『一键关联』的绑定动作可合并进入建单接口处理」，该描述在当前缺乏接口支撑的情况下属于**假设性描述**，需在接口确定后修正。
- `frontend-guide/INDEX.md` 场景总览表中「一键关联」行为描述为「先完成绑定，再走建单流程」，但缺少绑定接口的实现细节。

### 建议决策
**采用方案 A**（新增绑定接口），理由：
1. 一期 TAPD 建单功能本身可能尚未开发完成，将绑定逻辑隐式合并到建单接口会导致两个未开发功能互相阻塞
2. 「一键关联」作为用户主动触发的操作，应有明确的 API 反馈（成功/失败）
3. 绑定和建单是不同粒度的操作，解耦更符合单一职责原则
