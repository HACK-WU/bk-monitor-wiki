# 需求挖掘报告：TAPD 手动解绑持久化与重新关联

## 1. 原始需求描述

基于现有 TAPD Issue 集成功能，提出以下两个需求：

1. **手动解绑持久化**：当前取消关联（Unbind）操作删除本地 `TapdWorkspaceBinding` 后，列表查询时 `try_bind_importable` 静默重新创建 binding，导致取消操作形同虚设。需要引入 tombstone 机制，支持持久化的"手动取消关联"状态。

2. **取消用户态授权接口**：提供显式删除 access_token 的入口。

## 2. 需求澄清

### 2.1 需求形态（真实需求 / 还原后的需求）

**两个均为真实需求**：
- 需求1是真实需求：解决解绑操作不可预期的问题
- 需求2是真实需求：补充授权生命周期管理中缺失的"撤销"环节

### 2.2 功能本质

- **需求1**：解绑操作的效果不可预期 —— 用户主动取消关联后，系统又在后台自动恢复。需要一个持久化的 tombstone 机制区分"从未关联"和"主动取消关联"两种 `!in_local` 状态，并支持一键重新关联。
- **需求2**：缺乏全局授权生命周期管理的"撤销"环节 —— 仅有授权（OAuth 获取 token），没有撤销入口。

### 2.3 使用场景与角色

| 场景 | 角色 | 触发条件 | 当前困境 | 期望结果 |
|------|------|----------|----------|----------|
| S1 手动解绑 | 普通用户 | 点击"取消关联"某 TAPD 项目 | 解绑后下次查询又自动绑回来了 | 取消后持久保持 unbound，不再自动重绑 |
| S2 重新关联 | 普通用户 | 之前手动解绑的项目想重新使用 | 只能再走一遍完整 OAuth 授权流程 | 点击"重新关联"直接恢复本地 binding，无需再走授权 |
| S3 区分 importable | 普通用户 | 查看 TAPD 项目列表 | 无法区分"从未关联"和"手动取消关联后再关联"的项目 | 列表状态清晰：bound / stale / importable / unbound / manually_unbound |
| S4 撤销授权 | 普通用户 | 想彻底断开 TAPD 连接 | 无主动撤销入口，只能等 token 过期 | 点击"取消授权"直接清除 access_token |

**场景关联性**：S1→S2 为依赖关系，必须先有取消关联才能演示重新关联；S4 为独立场景。

### 2.4 用户角色

蓝鲸监控平台普通用户（具有 Issue 模块操作权限的用户）。

### 2.5 核心痛点

1. **解绑无效**：取消关联后 `try_bind_importable` 静默恢复 binding，操作无效果感。
2. **重新关联成本高**：已授权项目重新关联需要走完整 OAuth 流程（5+ 步）。
3. **状态不可区分**：无法判断 TAPD app 授权还在但本地未关联的项目是"从未关联"还是"手动取消过"。
4. **授权无法撤销**：access_token 存储在 Redis 中，用户无法主动清除。

### 2.6 期望体验

- 解绑后列表不再自动恢复关联，该项目显示"已取消关联"状态
- 已取消关联但 TAPD 授权仍在的项目，支持一键重新关联（1 步完成）
- 列表状态一目了然，不混淆"可导入"和"已取消"
- 普通用户可随时彻底断开 TAPD 授权

### 2.7 深层动机

- 用户操作必须有确定性和可预期性
- 已授权的项目应该支持"软解绑"，保持 TAPD 侧授权但断开本地关联
- 降低重新关联的操作成本，提升用户体验
- 完善授权生命周期管理（授权→使用→撤销）

### 2.8 非功能性需求

- **性能**：tombstone 查询增加一次 DB 查询，需确保 N+1 问题不发生（批量查询时一次查出所有 tombstone）
- **安全**：重新关联接口需校验 TAPD app 授权仍然有效，防止授权过期后仍允许重新关联
- **可用性**：解绑操作即时生效，用户无需等待
- **兼容性**：不影响现有 B-01、B-04 接口的已有行为，仅对新增场景生效

### 2.9 关键假设与验证建议

| 假设 ID | 假设内容 | 验证难度 | 验证建议 |
|---------|----------|----------|----------|
| H-01 | 目标用户理解"取消关联"仅断开本地 binding，不影响 TAPD 侧授权 | 低 | 交互设计阶段确认前端提示文案 |
| H-02 | TAPD 侧授权在取消本地关联后不会被自动撤销 | 低 | 确认 TAPD `open_app_install` 授权是持久的（已确认） |
| H-03 | 重新关联时不需要重新走 OAuth 授权流程（因为 TAPD app 授权仍在） | 低 | 验证 B-03 回调后获取的 token 对所有已授权项目有效 |
| H-04 | 取消用户态授权后，binding 记录应保留（项目级关联不应被删除） | 低 | 与用户确认行为预期 |

## 3. 根本性分析

### 3.1 核心问题

**需求1**：`_mark_bind_status` 方法在 `in_app && !in_local` 场景下，无条件调用 `try_bind_importable()` 创建 binding，没有区分"从未关联"和"主动取消关联"两种 `!in_local` 状态。

**需求2**：token 管理只有`save`和`get`，缺少`delete`接口。

### 3.2 根因链

```
需求1 根因链：
用户点击"取消关联"
    → 删除 TapdWorkspaceBinding（B-04）
    → 下次 B-01 查询 → _mark_bind_status 发现 in_app && !in_local
    → 静默 try_bind_importable() → binding 重新创建
    → 用户看到的列表状态又回到 bound
    → 用户困惑："我明明取消了，怎么又关联了？"

根因：没有区分"从未关联"和"主动取消关联"两种 !in_local 状态。
```

### 3.3 方案评估

**你描述的功能**：新增 tombstone 表 + 显式重新关联接口 + 撤销授权接口

**我的判断**：**情况 A（方案对症）**

**理由**：
- tombstone 直接从根源上解决了状态混淆问题，阻止 `try_bind_importable` 的自动恢复
- 显式重新关联接口解决了已授权项目的高成本重绑问题
- 撤销授权接口补全了 token 生命周期管理
- 方案触及根因，不是症状处理

### 3.4 预期效果分析

- **核心场景覆盖度**：高 —— 覆盖解绑、查询、重绑、撤销全链路
- **痛点解决程度**：高 —— 解绑即时生效、重绑一键完成、状态清晰可区分
- **用户体验提升**：解绑操作不再"反弹"；重绑从 5+ 步 OAuth 流程缩减到 1 步点击；列表状态语义明确
- **潜在副作用**：
  - tombstone 记录长期无清理 → 建议按项目需求决定是否增加定期清理
  - 状态从四态变为五态 → 前端需适配新状态展示

### 3.5 建议

- **短期**：按方案实现 tombstone + 显式重绑 + 撤销授权
- **长期**：无额外需要 — 该方案已经触及根因
- **如果坚持简化方案**：若不引入 tombstone，只能将"取消关联"改为同时撤销 TAPD app 授权，但这会导致重新关联必须走完整 OAuth，用户体验更差，不推荐。

### 4.6 非功能性约束

- 新增 tombstone 查询不能引入 N+1 问题（批量查询时应一次获取全部）

- 解绑操作应保证原子性（binding 删除 + tombstone 写入在同一事务中）
- 不能影响已有 B-01/B-04 接口的已有行为，仅对新增场景生效

## 5. 潜在风险与注意事项

1. **tombstone 数据膨胀**：手动取消关联的记录长期不清理。建议暂不处理，后续视数据量决定是否增加定时清理。
2. **状态展示变更**：前端需适配新增的 `manually_unbound` 状态，展示文案和按钮逻辑需要调整。
3. **B-01 计算逻辑变更**：`_mark_bind_status` 是 B-01（列表查询）的核心方法，修改需确保不会影响性能（批量 tombstone 查询）。
4. **重新关联的并发安全**：多个请求同时重新关联同一条 tombstone 时，需确保幂等（`get_or_create` binding + `delete` tombstone 的顺序）。
5. **撤销授权与 binding 的关系**：REQ-05 仅删除 access_token，不触碰 binding 记录。用户重新授权后，之前绑定的项目仍然可用，这是预期行为，但需要在前端交互中明确提示。
