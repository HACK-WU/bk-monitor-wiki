# 需求文档：Issue 拆分支持批量操作

- **需求 ID**：REQ-20260901-001
- **TAPD 需求**：1010158081136938380（蓝鲸监控项目，提单人 @触发用户）
- **创建时间**：2026-09-01
- **状态**：草案（待需求确认）
- **分类**：integration

## 背景与目标

**背景**：错误日志合并明细界面中，大量同类错误（如 `context deadline exceeded`、`snetcd 选举 Keepalive 失败`、`sn.dtm.delay_worker 调用 tcaplus 失败` 等）目前只能逐一点击"拆分为新 Issue"，操作重复、效率低，影响问题跟进与处理速度。

**目标**：支持批量拆分操作，一次性将多条错误日志合并明细拆分为独立 Issue，减少重复手动操作。

## 需求描述

合并明细界面支持勾选多条错误日志合并明细，一键触发"批量拆分"；每条明细的拆分行为与现有单条"拆分为新 Issue"保持一致；拆分后各 Issue 独立可追踪。

**现状界面**（见 TAPD 截图）：合并明细列表右上角为"批量拆分"规划入口，列表中每条明细当前仅有独立的"拆分为新 Issue"按钮，无多选能力。

## 使用场景

- 场景 1（主场景）：用户在合并明细列表中勾选多条同类错误明细（如十余条 `context deadline exceeded`），点击"批量拆分"，系统逐条拆分为独立 Issue，操作一次完成。
- 场景 2（部分失败）：批量拆分中个别明细因状态变化（如已被他人拆分、主 Issue 状态变化）失败，期望仅该明细失败并明确反馈，不阻塞其余明细。

场景关联性：场景 2 是场景 1 的异常分支，同属一个交互流程。

## 核心痛点

同类错误在合并 Issue 下积压数十条时，逐条点击"拆分为新 Issue"需重复操作 N 次，每次均有界面等待与确认成本。

## 非功能性约束

- 权限：与现有单条"拆分为新 Issue"权限要求一致
- 性能：批量条数上限待定（建议评估前端交互与后端耗时后设定，如单次 ≤ 50 条）
- 兼容：不改变单条拆分入口与行为，老用法不受影响

## 潜在风险与注意事项

1. **事务边界**：批量拆分建议逐条独立事务（部分成功可接受），避免整体事务回滚导致全部失败；需在设计中明确。
2. **与合并/改挂的交互**：拆分对象是合并 Issue 的成员明细，需确认拆分后 `main_issue` 聚合状态、成员关系（含 PR #12234 引入的改挂字段 `via_issue_id` / `reparented_members`）的一致性维护。
3. **并发冲突**：同一明细被多端同时拆分（单条按钮与批量勾选并发）的幂等防护。
4. **主 Issue 终态**：若批量拆分后成员全部迁出，主 Issue 状态如何收敛，需在技术设计时确认。

## 待确认问题（需求挖掘遗留）

2. 部分失败时，用户期望的反馈形式（逐条列表 / 汇总提示）？
3. 是否需要在拆分前对已拆分/不可拆分状态的明细做前置置灰过滤？
