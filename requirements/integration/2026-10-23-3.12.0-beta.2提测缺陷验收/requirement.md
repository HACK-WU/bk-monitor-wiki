**验收要点**：

### #1（SOPS 接口报错）根因方向

结合 `bkmonitor/api/sops/default.py` 的 `SopsBaseResource`：

- `base_url` 在 `use_apigw` 为真时取 `settings.BK_COMPONENT_API_URL}/api/bk-sops/prod/`，否则取 `api/c/compapi/v2/sops/`
- `use_apigw` 由 `settings.BKSOPS_API_BASE_URL` 或 `settings.ENABLE_MULTI_TENANT_MODE` 决定

若提测环境开启多租户，链路会切到 apigw，此时 app_code / 鉴权头不匹配即直接返回服务不可用，与缺陷现象吻合。验收前应先确认该环境的 `ENABLE_MULTI_TENANT_MODE` 取值与 apigw 侧授权。

### 检索踩坑记录

- **本地为浅克隆**：`.git/shallow` 边界为 `648dae91e7`（2026-09-21），`--all` 只能覆盖已 fetch 的引用。判断「有无修复提交」前必须先 `git fetch` 目标远端，否则会漏检新分支
- **多远端易混淆**：本仓库配置了 `gf` / `origin` / `upstream` / `tang` / `zx` 五个远端，同一提交可能只存在于其中之一，`--all` 的覆盖范围取决于 fetch 历史

### 修复完成后回填约定

每条缺陷修复后，按以下三步回填，三者缺一不可：

1. **提交信息带缺陷号**：`fix: <描述> --bug=<缺陷号>`（如 `--bug=165607340`），保证 `git log --grep=<缺陷号>` 可检索
2. **登记到本需求**：`req update REQ-20261023-001 --commit <git_hash> --changelog "修复 #<缺陷号>"`
3. **同步上表**「修复提交」列为 commit hash，并在 TAPD 将该缺陷流转至已修复

> 回填后须用 `req list --id REQ-20261023-001` 验证 `关联提交` 数已递增，且用 `git log --grep=<缺陷号>` 能反查到提交，避免只改文档不落代码。
