# 排障速查手册

> 用法：按现象查表 → 定位到层 → 看验证手段。**所有行号均经源码核实**。

## 一、按现象速查

| 现象 | 最可能的原因 | 定位到 | 验证手段 |
|---|---|---|---|
| 完全没告警 | `in_alarm_time` 不在生效时间 | [trigger/processor.py:666](/root/bk-monitor/bkmonitor/alarm_backends/service/trigger/processor.py) | 日志 `not in alarm time` |
| 有异常无告警 | 触发条件未满足（N周期M次） | [checker.py:208](/root/bk-monitor/bkmonitor/alarm_backends/service/trigger/checker.py) | 数 `CHECK_RESULT_CACHE_KEY` 里 `ANOMALY` 条目 |
| 事件被吞 | 黑白名单过滤 | [builder/processor.py:217](/root/bk-monitor/bkmonitor/alarm_backends/service/alert/builder/processor.py) | 日志 `dropped(N/M)` |
| 告警炸开 | `dedupe_md5` 变化 | [event.py:205](/root/bk-monitor/bkmonitor/alarm_backends/core/alert/event.py) | 对比新旧事件维度 |
| 告警不恢复 | `AlertManager` 未跑/加锁失败 | [manager/processor.py:143](/root/bk-monitor/bkmonitor/alarm_backends/service/alert/manager/processor.py) | 日志 `get lock error` |
| 告警延迟大 | `time_delay` + 58s 周期 + 队列积压 | [processor.py:591](/root/bk-monitor/bkmonitor/alarm_backends/service/access/data/processor.py) | 算 `detect_time - access_time` |
| 数据重复告警 | 去重缓存 TTL 不足 | [processor.py:721](/root/bk-monitor/bkmonitor/alarm_backends/service/access/data/processor.py) | TTL = `max_agg_interval * 10` |
| 无数据告警不触发 | 无数据补充判定未满足 | [checker.py:210](/root/bk-monitor/bkmonitor/alarm_backends/service/trigger/checker.py) | 需"全异常 + 时间跨度够" |
| 被屏蔽还通知 | `should_send_signal` 判断 | [alert.py:616](/root/bk-monitor/bkmonitor/alarm_backends/core/alert/alert.py) | 三条件全满足才发 |

## 二、关键日志关键字

| 关键字 | 含义 | 严重度 |
|---|---|---|
| `not in alarm time` | 不在告警生效时间，跳过 | 信息 |
| `暂无待检测数据` | 队列空 | 信息 |
| `待检测数据量达到配置值` | 达到 `SQL_MAX_LIMIT`，部分数据延迟 | 警告 |
| `发现非期望格式的待检测数据` | 脏数据，已跳过 | 错误 |
| `[access to detect]big latency` | 接入→检测延迟 >60s | 警告 |
| `[detect to trigger]big latency` | 检测→触发延迟 >60s | 警告 |
| `二次确认时发生异常，不影响告警主流程` | 二次确认失败，已忽略 | 异常 |
| `is partial` | 查询返回不完整结果 | 信息 |
| `is partial: skip query results` | 残缺数据整批丢弃（配了二次确认） | 警告 |
| `dropped(N/M)` | 事件富化时被丢弃 | 信息 |
| `save events ERROR` | 事件保存失败（非 409） | **错误** |
| `alerts is locked, retry in 5s` | 加锁失败，5 秒重试 | 信息 |
| `get lock error` | manager 加锁失败，等下一轮 | 信息 |

## 三、关键指标名

| 指标 | 含义 | 关注阈值 |
|---|---|---|
| `ACCESS_DATA_PROCESS_TIME` | 接入处理耗时 | 持续升高 = 数据源慢 |
| `DETECT_PROCESS_DATA_COUNT` | 检测拉/推数据量 | pull >> push = 正常（大部分不异常） |
| `DETECT_PROCESS_LATENCY` | 检测延迟 | >60s 要查 |
| `TRIGGER_EVENT_RATE_LIMIT_DROP` | **限流丢弃事件数** | >0 就要关注（静默丢） |
| `PROCESS_OVER_FLOW` | 单批超 1000 条 | 说明该策略数据量异常 |
| `ALERT_PROCESS_LATENCY` | 触发→构建延迟 | >60s 要查 |
| `PROCESS_BIG_LATENCY` | 段间大延迟（带 module 标签） | 按 module 定位卡点 |

| Key | 定义位置 | 用途 | 排查时能看什么 |
|---|---|---|---|
| `DATA_LIST_KEY` | core/cache/key.py | 接入产出的数据队列 | 队列长度 = 积压量 |
| `CHECK_RESULT_CACHE_KEY` | key.py:436 | 检测判定结果 SortedSet | **数 `ANOMALY` 条目判断是否该触发** |
| `LAST_CHECKPOINTS_CACHE_KEY` | key.py:390 | 各维度最后检测时间 | 判断某维度是否还在被检测 |
| `ANOMALY_LIST_KEY` | key.py:240 | 异常详情 | |
| `ANOMALY_SIGNAL_KEY` | key.py:260 | 异常信号（轻） | 哪组有异常 |
| `ALERT_UPDATE_LOCK` | - | 告警更新锁 | 长时间持有 = 任务卡死 |

## 五、配置速查

| 配置 | 默认/位置 | 作用 | 调优建议 |
|---|---|---|---|
| `max_access_data_period` | 58（handler.py:43） | 调度周期上限 | 一般不动 |
| `REFRESH_INTERVAL` | 90（handler.py:37） | 排班表刷新周期 | 一般不动 |
| `QOS_INTERVAL_EXPAND` | 3（settings） | QoS 数据源周期放大倍数 | 慢数据源可加大 |
| `QOS_QUEUE_ENABLE` | **环境变量，默认 False** | QoS 独立队列开关 | **不开则只降频不隔离** |
| `NUM_OF_COUNT_FREQ_ACCESS` | settings | 往前多拉几个周期 | 数据源延迟大则加大 |
| `ACCESS_DATA_TIME_DELAY` | settings | 上界往前推的秒数 | 影响告警及时性 |
| `SQL_MAX_LIMIT` | settings | 单批处理上限 | 积压时可调大 |
| `DOUBLE_CHECK_SUM_STRATEGY_IDS` | settings | 二次确认白名单 | 配了会因 partial 丢数据 |
| `DEFAULT_DEDUPE_FIELDS` | constants.py:75 | 默认去重字段 | 不改 |

## 六、常见误解澄清

| 误解 | 实际 |
|---|---|
| "连续 3 次" = 严格连续 | **窗口内累计 3 次**，不要求紧挨 |
| 58 秒是默认周期 | 是**上限**，实际是 `min(58, 组内最小 agg_interval)` |
| 改策略阈值会影响历史告警 | 不会，历史告警显示**快照**里的阈值 |
| 改策略名会炸开告警 | 不会，有 `strategy_id` 时会**移除** `alert_name` 出重字段 |
| 检测出异常就会告警 | 不一定，还要过 `in_alarm_time` + 触发条件 |
| 加锁失败会丢事件 | builder 不会（5s 重试），manager 也不丢（下轮捞） |
| 事件保存 409 是错误 | **不是**，是 uid 重复（poller 窗口重叠），正常 |
| 限流会打日志 | **不会**，静默丢，只能看 `TRIGGER_EVENT_RATE_LIMIT_DROP` 指标 |
