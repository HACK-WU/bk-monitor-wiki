# 实战经验与场景解法库

## 一、实战经验（踩坑清单）

> 这些是源码里**明确写出但容易忽略**的设计，读懂能少踩很多坑。

### 经验 1：QoS 配了不等于隔离

**坑**：配了 `QOS_DATASOURCE_LABELS` 以为慢数据源被隔离了，其实没有。

**源码**：[handler.py:48](/root/bk-monitor/bkmonitor/alarm_backends/service/access/handler.py)

```python
self.enable_qos_queue = os.getenv("QOS_QUEUE_ENABLE", False)
```

周期放大（`min_interval *= 3`）**总是生效**，但独立队列**还要看环境变量**。

**正确做法**：配 `QOS_DATASOURCE_LABELS` **且**设 `QOS_QUEUE_ENABLE`，两者缺一不可。

---

### 经验 2：配了二次确认反而会丢告警

**坑**：给策略配二次确认想降噪，结果数据源一抖动告警全没了。

**源码**：[processor.py:489-502](/root/bk-monitor/bkmonitor/alarm_backends/service/access/data/processor.py)

```python
if first_item.query.is_partial:
    ...
    if protected_strategy_ids:
        logger.warning("... is partial: skip query results")
        points = []
```

**只有配了二次确认的策略**会在 `is_partial` 时丢弃整批。没配的只打日志照常处理。

**正确做法**：数据源不稳定时**别配**二次确认。二次确认的前提是数据源可靠。

---

### 经验 3：`reversed()` 不是可有可无

**坑**：改动 `pull_data` 时删掉了 `reversed(records)`，环比类算法结果全乱。

**源码**：[detect/process.py:79](/root/bk-monitor/bkmonitor/alarm_backends/service/detect/process.py)

```python
# 队列左进右出，lrange 取出时需要做一次倒序才能保证先进先出
for record in reversed(records):
```

**正确做法**：这行不能删。队列是"左进右出"，不反转就逆序处理。

---

### 经验 4：去重缓存刷新时机不能提前

**坑**：把 `dup_obj.refresh_cache()` 挪回 `filter_duplicates` 里，导致部分数据永久丢失。

**源码**：[processor.py:790-793](/root/bk-monitor/bkmonitor/alarm_backends/service/access/data/processor.py)

```python
# 修改：不在这里刷新缓存，而是在 push() 中，时间点限制之后刷新
# 这样可以确保只有被处理的数据才会被标记为"已见过"
# dup_obj.refresh_cache()
```

**原因**：后面还有时间点限制可能丢数据。提前标记"已见过"，被丢的数据下次不再拉，就真丢了。

---

### 经验 5：改 `CHECK_RESULT_CACHE_KEY` 模板要同步改另一个 key

**坑**：只改了 `CHECK_RESULT_CACHE_KEY` 的 key 模板，触发阶段取不到检测结果，告警全不触发。

**源码**：[core/cache/key.py:398 与 :441](/root/bk-monitor/bkmonitor/alarm_backends/core/cache/key.py)

```python
# 这里的field_tpl需要保持和CHECK_RESULT_CACHE_KEY的key_tpl一致
# 这里的key_tpl修改后，需要同步修改LAST_CHECKPOINTS_CACHE_KEY的field_tpl
```

**正确做法**：这两个 key 模板**必须同时改**。源码用两处互相引用的注释标出了这个隐式契约。

---

### 经验 6：`max_queried_data_time` 是防死循环的关键

**坑**：去重后 `record_list` 为空就不更新 checkpoint，导致无限重拉同一批数据。

**源码**：[processor.py:744-746](/root/bk-monitor/bkmonitor/alarm_backends/service/access/data/processor.py)

```python
# 记录所有数据的最大时间点（包括重复数据）
# 用于在去重后 record_list 为空时，仍然能够更新 checkpoint，避免死循环
```

**正确做法**：checkpoint 推进要用 `max_queried_data_time`（含重复数据的最大值），不能用去重后的最大值。

---

### 经验 7：告警快照让"改配置"不影响"历史告警"

**现象**：改了策略阈值，历史告警详情显示的还是旧阈值。

**源码**：[detect/process.py:213](/root/bk-monitor/bkmonitor/alarm_backends/service/detect/process.py)

```python
self.strategy.gen_strategy_snapshot()
```

**这不是 bug**：快照保证同一轮检测用同一套配置，且快照 key 带到告警里供溯源。

**正确认知**：告警详情显示的是**触发时**的配置，不是当前配置。

## 二、场景解法库

> 格式：场景 → 解法 → 涉及改动点 → 风险

### 解法 1：慢数据源拖慢整体

**场景**：某数据源查询要 30 秒，把 Celery 队列堵住。

**解法**：
1. 把该数据源标签加入 `QOS_DATASOURCE_LABELS`
2. 设环境变量 `QOS_QUEUE_ENABLE=True`
3. 观察 `qos_interval_expand`（默认 3）是否够，可加大

**涉及改动**：配置层，不改代码

**风险**：周期放大 3 倍意味着该数据源的告警延迟增加。需与业务确认可接受。

---

### 解法 2：数据源入库延迟大，告警漏数据

**场景**：数据源延迟 5 分钟入库，按当前配置拉不到。

**解法**：
1. 调大 `NUM_OF_COUNT_FREQ_ACCESS`（往前多拉几个周期）
2. **同步检查**去重缓存 TTL = `max_agg_interval * 10` 是否覆盖得住

**涉及改动**：配置层

**风险**：多拉的周期数超过去重 TTL 会造成**重复告警**。两者必须配套调整。

---

### 解法 3：告警抖动严重（毛刺误告）

**场景**：数据偶尔一个尖峰就告警，希望降噪。

**解法**（按代价从低到高）：
1. **调大触发条件**：增加 `check_window_size` 或 `trigger_count`（最推荐，零成本）
2. **用同比/环比替代静态阈值**（能识别周期规律，但要拉历史点，有性能成本）
3. **配二次确认**（代价最大，会因 `is_partial` 丢数据，**数据源不稳时别用**）

**涉及改动**：策略配置层

**风险**：选项 3 在数据源抖动时会丢告警；选项 2 增加检测耗时。

---

### 解法 4：告警数量爆炸

**场景**：一次故障产生几百条告警，通知被打爆。

**解法**（不同层，可叠加）：
- **构建层**：检查 `dedupe_keys` 是否包含了高基数维度（如把 `request_id` 当维度会导致每条一个告警）
- **收敛层**：告警收敛/合并（Issue 聚合，超出本课范围）
- **通知层**：屏蔽规则

**涉及改动**：维度配置是根因，先从这查

**风险**：改维度配置会让历史告警与新告警 md5 不一致，可能炸开。

---

### 解法 5：需要接入事件型告警（无时序数据）

**场景**：业务方直接上报"订单失败"事件，没有指标数据。

**解法**：走**事件旁路**（[access/event/processorv2.py](/root/bk-monitor/bkmonitor/alarm_backends/service/access/event/processorv2.py)），跳过 detect 与 trigger 两级，直接产出事件进 `alert.builder`。

**涉及改动**：Kafka 数据源 + 事件类型注册

**风险**：旁路没有"连续 N 次"保护，**一条原始事件一条告警**。业务侧要自己做降噪，否则会被打爆。

---

### 解法 6：无数据告警不触发

**场景**：agent 挂了，期望产生无数据告警，但没有。

**解法**：检查无数据的补充判定（[checker.py:210-218](/root/bk-monitor/bkmonitor/alarm_backends/service/trigger/checker.py)）：

```python
always_nodata = anomaly_times == len(check_results)
is_triggered = always_nodata and (
    (end - start) >= (trigger_config["trigger_count"] - 1) * self.check_window_unit
)
```

两个条件：① 窗口内**全部**是异常点（不是部分）② 首末异常点时间跨度够。

**涉及改动**：无数据配置（`get_no_data_configs`）独立于普通触发配置

**风险**：无数据告警**只有一个级别**（`trigger_configs` 是单元素字典），不能配多级别。

---
