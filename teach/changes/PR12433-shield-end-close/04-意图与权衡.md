## 二、推断意图（结构推演，附依据）

| # | 意图 | 推断依据 |
|---|---|---|
| 1 | 为什么"接管"而不是"结束时扫描窗口内产生的告警" | 若不接管，屏蔽结束时需回答"哪些告警是期间产生的"——只能按 begin_time + 维度重匹配全量告警，重匹配成本高且维度匹配语义在结束时已过期（告警 dimensions 可能被收敛改写）。接管方案把判定前置到 builder 阶段（告警维度最完整时），结束时只按 owner shield_id 判活，O(1) 查配置即可。快照 window_begin/window_end 写进 extra_info 也支持这个推断——记录的是"接管那一刻的判定依据" |
| 2 | 为什么独立任务而不是复用 manager check 链 | manager 的 handle 阶段跑 7 个 checker（[processor.py:31-40](file://bkmonitor/alarm_backends/service/alert/manager/processor.py#L31-L40)：NextStatus/CloseStatus/RecoverStatus/ShieldStatus/Ack/Upgrade/ActionHandle），其中 ShieldStatusChecker 会对告警重刷屏蔽状态、ActionHandleChecker 触发套餐——托管告警进这条链等于重新暴露"要关闭的能力"。独立任务天然物理隔离：独立 ES filter、独立锁复核路径、独立关闭语义（set_end_status(CLOSED) + 专用描述文案），不用在 7 个 checker 里各加 if |
| 3 | 为什么候选选择"结束最晚优先、ID 小优先" | 多条 close 屏蔽同时覆盖时，选 end 最大=告警被托管到最晚，最不易出现"屏蔽 A 还在但告警已被 B（更早结束）释放后又被 A 重新接管"的抖动；ID 小作 tie-breaker 保证确定性（同 end 时结果可复现，便于测试与排障） |
| 4 | why (end, -shield_id) 元组直接 max | Python 元组比较逐元素——第一键 end 大者胜，同 end 时 -id 大（即 id 小）者胜，一行实现两级排序 |
| 5 | 为什么 RECOVERED 事件也不终结托管告警 | 需求语义"屏蔽结束时系统将这些告警关闭"——集合边界由"期间产生"定义；若恢复即终结，同一策略恢复后再触发会开新去重线，新告警若仍在窗口内会被接管、不在则不接管，集合成员随恢复/再触发漂移。保持身份直到统一关闭，集合边界稳定（与显式意图 1 同源） |
| 6 | 为什么 end_policy 创建后不可修改 | 托管告警 extra_info 冻结了接管时的 shield_end_close_config 快照；若允许 notify_once↔close 互改，存量托管告警的处置语义与配置背离（改成 notify_once 后这些告警"无人认领"——既不被关闭也不再补发）。拒绝修改是最小正确实现 |
| 7 | 为什么 window.py 不复用 TimeMatchByWeek 的原 is_week_match | 原实现用构造时刻 worker 本地时区算周几；混合时区集群（worker 分布多时区）下同一配置在不同 worker 解析出不同窗口。_BusinessCalendar 用 time_tools.localtime（业务时区）统一判定，代价是每次 is_match 多一次时区换算 |
| 8 | 为什么 close.py 在 _match 里先补 StrategySnapshotEnricher | is_match 的维度匹配依赖 alert.get_dimension(alert)——部分维度（策略相关）来自 strategy 快照；若告警尚未 enrich，维度不全会导致匹配漏判。先补齐再匹配，保证判定的维度集合与后续 enrich 链一致 |

## 三、被否决的备选方案（从代码结构反推）

| 决策点 | 实际选择 | 可推见的备选 | 备选为何被否（推断） |
|---|---|---|---|
| 关闭判定时机 | builder 接管 + 独立任务判活 | 屏蔽结束时全量扫描窗口内产生的告警 | 全量重匹配维度语义过期、成本 O(告警数×屏蔽数)；接管方案 O(1) 判活 |
| 托管告警状态管理 | 独立 shield_tasks.py | 复用 manager check 链 + 7 checker 各加分支 | 链内分支散布 7 处、ShieldStatusChecker 语义冲突（见推断 2） |
| 时区处理 | timezone.override 包裹解析与判活 | 全链统一 UTC 比较 | 周期窗口的"周几/几点"本质是业务本地概念，UTC 直比会把周一 00:30 窗口算到周日；override 侵入面最小（只包判定段） |
| 告警标记 | ES 布尔字段 shield_end_close | 复用 is_shielded/is_blocked | 普通屏蔽也写 is_shielded；托管需要独立标记支撑独立扫描 filter（term 查询）与 7 个隔离点的判定条件 |
| 通知抑制 | should_send_signal + send_signal + composite 三道过滤 | 只在通知发送端一处过滤 | 告警副作用不止通知：套餐执行、分派、状态检查都是副作用；单点过滤漏套餐执行。7 隔离点=按副作用入口逐一封堵 |
| 缓存一致性 | 先 ES 后缓存 + BulkIndexError 剔除失败 ID | 先缓存后 ES 或全失败整批放弃 | 缓存可由快照/ES 回读重建（RRedis 丢数据不致命），ES 是事实源；部分成功继续比整批放弃更能推进（下轮补扫失败项） |

## 四、代价与适用边界

- **代价 1（写放大）**：接管告警每分钟被独立任务扫一遍（ES search_after + Alert.mget + 锁），大业务托管告警量大时有周期负载。缓解：分批 200 + 锁内快速过滤 + 判活后 active dict 全批复用（每批一次配置查询）。
- **代价 2（7 个隔离点的维护成本）**：后续任何新增"告警副作用入口"都必须记得加 shield_end_close 过滤——散布式防御，漏一处就漏一条副作用。这是接管方案的固有税。
- **代价 3（快照与实时配置可能背离）**：接管冻结 window 快照，判活只看当前配置——设计上已选择"当前配置优先"（显式意图 5），但快照失去判定作用后仍保留（溯源用途），存在"两个真相源"的阅读困惑。
- **适用边界**：本方案只覆盖"屏蔽期间产生的告警"；屏蔽开始前已存在的告警不受影响（需求原文明示）——因为接管只发生在 builder 新告警/存量再触发路径，begin_time 在屏蔽窗口外的告警 is_match 不命中（begin_time 落窗判定）。

## 五、何时该改选

- 若业务反馈"托管告警量×分钟扫描"造成 ES 压力：可把 check_shield_end_close_alert 改为事件驱动（屏蔽 end_time 近似对齐触发）而非固定 cron。
- 若隔离点漏防成为高频 bug 源：可考虑收敛为"告警状态机层"单一闸门（update 入口统一判定），替代 7 点散布——但那是架构级重构。
- 若需要支持"编辑屏蔽窗口后按新窗口判活"：快照需参与判活（当前被有意绕过，显式意图 5），需重设计快照语义。
