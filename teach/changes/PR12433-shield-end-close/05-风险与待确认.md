## 一、风险点清单（按触发链路分组）

### R1 · 发布顺序依赖（置信度：高）

`shield_end_close` ES term 查询（[manager/tasks.py:144/177](file://bkmonitor/alarm_backends/service/alert/manager/tasks.py#L144)、[shield_tasks.py:36](file://bkmonitor/alarm_backends/service/alert/manager/shield_tasks.py#L36)）依赖索引 mapping 含该字段。**事实**：field.Boolean() 声明在 [documents/alert.py:83](file://bkmonitor/bkmonitor/documents/alert.py#L83)，新索引按模板自动含；存量索引是否动态映射加字段未在本 PR 内处理。**风险**：若存量索引 strict mapping 或模板未更新，写入带新字段的文档可能失败、或 term 查询静默漏命中。**待确认**：索引模板/rolling 更新机制是否自动带新字段（需查 ES 索引模板配置与滚动策略，超出 diff 范围）。

### R2 · 接管粘滞与屏蔽编辑的交互未定义（置信度：高，来自 code review P1）

**事实链**：① take_over 首行粘滞（已托管不重选，[close.py:23](file://bkmonitor/alarm_backends/service/converge/shield/close.py#L23)）；② end_policy 创建后不可修改（serializers 校验），**但时间窗口可编辑**（EditShieldResource 仅拒 end_policy 变更，begin_time/end_time/cycle_config 可改）；③ 判活只看当前配置（shield_is_active，显式意图 5）。**行为组合**：屏蔽 A 接管告警后，用户把 A 的窗口大幅缩短/延长——告警仍粘滞于 A，判活按新窗口，extra_info 快照与实际不一致。**后果**：功能上自洽（最终总会被关闭或保留），但快照信息失真，且"延长窗口"场景告警的释放时间与用户预期（按编辑后的窗口）一致、快照显示旧窗口——排障时会困惑。**是否缺陷待作者确认**（也可能被有意接受：快照仅溯源）。

### R3 · 屏蔽期间告警恢复后的"体验空窗"（置信度：中）

**事实**：托管告警 RECOVERED 事件不终结（alert.update 托管分支），告警保持 ABNORMAL 直到屏蔽结束统一关闭。**后果**：实际已恢复的故障在屏蔽期内"未恢复告警"列表持续显示为未恢复——符合需求"结束时统一关闭"的字面语义，但若屏蔽周期很长（如每月窗口），用户在 UI 看到的恢复状态失真持续整月。**描述**：这是需求语义的直接实现，非实现偏差；是否可接受属产品决策。

### R4 · manager 既有任务与独立任务的锁竞争窗口（置信度：低）

**事实**：两者共用 ALERT_UPDATE_LOCK（同 dedupe_md5 键）。托管告警被既有任务 filter 排除（ES filter + 锁内复核双保险），理论上不会同时被两链处理。**残余窗口**：check_blocked_alert_finished 锁内复核加了 `not alert.shield_end_close`（[tasks.py:227](file://bkmonitor/alarm_backends/service/alert/manager/tasks.py#L227)），check_abnormal 链的 filter_alerts 也排除——但告警在"被接管前的瞬间"（builder 已写缓存、独立任务未扫到）若恰好被既有任务捞起，ES filter 此时查的是旧文档（无 shield_end_close 标记），会进 filter_alerts——此时缓存/快照已带标记（close.py 的 alert.set 写的是内存对象，save_alerts 后才落 ES），filter_alerts 的三重判定（缓存命中项 + mget 快照回读）能拦住。**结论**：锁+缓存双通道判定下竞争窗口收敛到毫秒级且大概率被拦，但无法从静态阅读证明 100% 无漏——依赖发布后观察。

### R5 · 周期屏蔽跨天窗口的边界语义（置信度：中）

**事实**：matching_window 对跨天窗口（start>end）用 matcher.is_match 校验凌晨边界日，未命中则截断到 23:59:59（[window.py:63-68](file://bkmonitor/alarm_backends/service/converge/shield/window.py#L63-L68)，test_weekly_overnight_respects_existing_day_filter 实证：周三 23:00-周四 01:00 窗口、week_list=[3] 时 end 截断为周三 23:59:59）。**后果**：周过滤屏蔽的跨天部分只覆盖到过滤日当天午夜——符合"周过滤日"的字面语义，但用户配置"周三 23:00-01:00"时可能预期覆盖周四凌晨。**描述**：与既有 TimeMatchByWeek 的判定语义一致（匹配日在周三才算命中），非新引入偏差；属产品语义确认项。

### R6 · take_over 异常吞掉的观测性（置信度：低）

**事实**：take_over 整体 try/except，异常仅 logger.exception（[close.py:25-28](file://bkmonitor/alarm_backends/service/converge/shield/close.py#L25-L28)），无指标上报。**后果**：接管持续失败（如缓存配置脏数据）时告警静默走普通链路（会发通知），无 metric 可告警。**描述**：与模块既有风格一致（fail-safe toward alerting——宁可多通知不误吞），但缺主动发现手段。

## 二、需向作者/评审确认的清单

1. ES 存量索引对 `shield_end_close` 的 mapping 就绪机制（R1）——发布顺序是否有依赖文档？
