## 一句话概括

给"屏蔽"加一个正交维度 `end_policy`：选 `close` 时，屏蔽期间产生的告警被 builder 批内接管（标记 `shield_end_close`），全程不通知、不执行套餐、不被恢复事件终结，屏蔽结束（到期或解除）后由独立周期任务统一静默关闭；默认 `notify_once` 保持现行为。

## 三个最值得记住的设计

**1. 接管前置而非事后回溯。** "屏蔽期间产生了哪些告警"若在结束时回答，需按 begin_time+维度重匹配全量告警——维度可能已被收敛改写、语义过期。本方案在 builder 阶段（维度最完整时）判定并冻结快照，结束时只按 owner shield_id 查配置判活，O(1)。

**2. 托管告警是第三种告警形态。** 普通/屏蔽中（is_shielded）/托管（shield_end_close）三者生命周期不同：托管告警 RECOVERED 不终结、不进任何 checker 链、由专用任务统一关闭。为支撑独立扫描，7 个副作用入口逐一封堵（这是方案的固有维护税：未来新增告警副作用必须记得加过滤）。

**3. 全链 fail-safe toward alerting。** 接管匹配失败→告警照常走普通链路（会通知）；判活时配置读不到/SQL 异常/owner 缺失→保留告警不关闭；部分写失败→只更成功项下轮补扫。与告警屏蔽模块既有保守原则一致。

## 风险与待确认（摘要，全表见 05）

- R1 发布顺序：ES 存量索引 mapping 对 shield_end_close 的就绪机制待确认。
- R2 接管粘滞 + 窗口可编辑：快照失真但行为自洽（判活只看当前配置），需作者确认是否有意。
- R3 屏蔽期内已恢复告警 UI 持续显示未恢复（需求语义直接实现，产品确认项）。
- code review 双 P1 的后续实证：P1-a（is_match 语义改写影响面）经全仓构造点核查收敛——通知链路不调 is_match；P1-b（粘滞+编辑）保留为 R2。
