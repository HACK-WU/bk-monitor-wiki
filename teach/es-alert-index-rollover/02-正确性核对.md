## 二、有误项（已修正）

### ❌ E1：reindex 的搬运范围——"每天搬运全部活跃告警"表述不精确

**原结论**（Phase 1 第四节沿用了项目内既有说法）：
> ABNORMAL 告警每天被 reindex 搬运到当天索引。

**代码事实**（`ilm.py:759-762`）：

```python
current_datetime_object = datetime.datetime.strptime(current_datetime_str, self.date_format)
start_ts = int(arrow.get(current_datetime_object).timestamp)

search = Search().from_dict(self.reindex_query or {}).filter("range", create_time={"gte": start_ts})
```

搬运条件 = `REINDEX_QUERY`（`status=ABNORMAL`）**AND** `create_time >= 新索引日期零点`。

**为什么这两者不等价**：
- 若一条告警 `create_time` 是 3 天前、至今仍 ABNORMAL，则它在今天创建新索引时**不满足** `create_time >= 今天零点`，**不会被搬运**。
- 只有当该告警的 `create_time` 落在新索引当天（或之后）时才会被搬。

**`create_time` 是否会被刷新？** 取证结论：**不会**。
- `Alert.from_event()` 首次创建时一次性赋值（`core/alert/alert.py:781-786`），`create_time` 与 `update_time` 同值。
- `init_uid()`（`core/alert/alert.py:753-766`）在 `id` 不存在时用 `create_time` 生成 UID，并把**解析回的时间戳**写回 `create_time`，此后不再改动。
- 全仓 grep `self.data["create_time"]` 的写入点仅此二处（`core/alert/alert.py:765` 与 `:785`）；`add_log` 里的 `create_time`（`:446`）写的是**日志文档**的字段，与告警文档无关。
- `set_end_status`（`:707-740`）只改 `status` / `end_time` / `update_time`，**不动 `create_time`**。

**修正后的结论**：

> **reindex 实际搬运的是「状态为 ABNORMAL 且 create_time 落在新索引日期之后」的文档。**
> 对 `create_time` 与新索引同日的新增告警，效果等价于"搬到当天索引"；对 `create_time` 更早的长期存活告警，**它不会被继续搬运**，会停留在 `create_time` 所在那天的索引。

**这个修正改变了什么**：项目内四处材料（`alert.py:156-160` 注释、`test_alert_document.py` 文件 docstring、`ai-docs/.../alert文档存储与查询行为.md` §2.3、ki `项目踩坑点/通用`）统一表述为"活跃告警每天被搬运到当天索引、doc 永远在今天的索引"。按代码实际行为，这个表述**只在告警 `create_time` 与当天一致时成立**。

**但要强调：这不影响现有代码的正确性。** `AlertDocument.get` / `mget` 把上界设为 `now`、下界设为 `begin_time`，覆盖 `[begin_time, now]` 全区间，无论文档是"被搬到今天"还是"停在 create_time 那天"都能命中。**上界恒 now 这条不变量依然成立且必要**——只是它的必要性来源不止"活跃告警被搬到今天"，还包括"RESOLVED 告警停在状态切换那天（可能远晚于 begin_time）"。

**判定**：修正是**表述精度**问题，不是代码 bug。已在 `01-代码wiki.md` §6.1 以"代码事实 + 存疑标注"方式呈现，未擅自改写项目内既有文档的结论。

**建议（不在本技能职责内，仅记录）**：若要彻底确认，可在测试环境对一条 3 天前创建、至今 ABNORMAL 的告警执行一轮轮转，观察其索引位置是否变化。此项列为 `05-数据流.md` 的"待确认"。
