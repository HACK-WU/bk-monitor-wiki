# 04 · 应用场景与待解决问题

> 回答：这套机制在什么场景下成立、什么场景下不成立、有哪些已知局限与技术债

---

## 一、它解决的核心痛点

[专用] 回到开场：告警数据的三个特征——**写多读少、按时间访问、总量无上限**。这套 ILM 机制逐个击破：

| 痛点 | 解法 | 效果 |
|---|---|---|
| 单索引无限膨胀 | 按天切片 + 按大小再分裂 | 单个索引的体积上界可控（默认 50 GB） |
| 历史数据清理成本高 | 整个索引删除而非 `delete_by_query` | 删文件 vs 删文档，成本差几个数量级 |
| 查询要扫全量分片 | 读别名按时间窗裁剪 | 查"最近 7 天"只扫 7 个索引 |
| 告警是长生命周期可变实体 | reindex 搬运活跃文档 | 让"活跃数据"与"当前时间"保持亲近 |
| 字段演进需要重建索引 | 模板 + 切新索引 | 改模型无需停机迁移，新索引自动带新字段 |

---

## 二、适用场景（什么时候该用它）

[专用] 这套机制在本项目内被 10 个 Document 共用，适用于：

| 场景 | 为什么适合 |
|---|---|
| **告警 / 故障 / 处理记录**（有状态机、长期存活） | reindex 搬运让活跃实体跟着时间走，查询收敛 |
| **事件 / 日志 / 操作流水**（一次写入、只按时间查） | 关掉 reindex，纯切片即可，零搬运开销 |
| **需要长期保留但访问集中在近期** | 时间切片天然支持按窗裁剪 |
| **字段结构会演进** | 模板 + 切索引，无需数据迁移 |

[通用] 抽象出来，这套"时间切片 + 别名路由 + 条件搬运"的组合适合：
- 数据有**天然时间维度**且查询以时间窗为主
- 数据**总量增长无上限**，需要过期策略
- 存在**少量长期存活且状态会变**的实体（这类实体才需要搬运）

---

## 三、不适用场景（什么时候不该用它）

[专用] 明确边界比罗列优点更有价值：

| 场景 | 为什么不适合 | 替代方案 |
|---|---|---|
| **需要跨全量历史做精确聚合** | 时间切片让"全量"变成几百个索引，聚合开销大 | 预聚合 / 离线数仓 |
| **数据没有时间维度**（如配置、字典表） | 切片毫无意义，反而增加复杂度 | 单索引 + 别名 |
| **文档会被高频随机更新且分布均匀** | reindex 搬运只对"活跃且 create_time 新"的文档有效，均匀分布的更新无法收敛 | 重新评估 `REINDEX_QUERY` 条件 |
| **要求强一致的删除语义** | 清理是按索引粒度，无法删单条历史数据 | `delete_by_query` |
| **ES 7.9+ 且无状态搬运需求** | ES 原生 Data Stream / ILM 更省心 | 原生能力 |

> [专用] **一个具体的反例**：`IssueDocument` 就**没有**启用 reindex（`issue.py:47`）。原因写在 `base.py:258-262`：Issue 要按 `impact_scope` 做影响范围过滤，该字段是后加的；关闭搬运意味着"历史数据留在旧索引、不参与新字段过滤"——**这是有意接受的语义**，即老 Issue 不参与新维度过滤。如果给 Issue 开了 reindex，反而会把不含新字段的旧文档搬到新索引，污染过滤结果。

## 四、已知局限与技术债

[专用] 按严重程度排列，全部有代码证据：

### 4.1 高优先级

| # | 问题 | 证据 | 影响 |
|---|---|---|---|
| **L1** | **过期清理未启用**：`clear_expired_indices` 无 crontab 注册 | 全仓 grep 仅命中定义处 `documents/tasks.py:38` | `retention=365` 是死配置；索引无限增长；`current_index_info` 的 O(M) 扫描持续劣化 |
| **L2** | **reindex 搬运范围与文档表述不一致**：代码是 `status=ABNORMAL AND create_time>=新索引日期`，四处材料表述为"活跃告警每天搬到当天" | `ilm.py:759-762` vs `alert.py:156-160` / `test_alert_document.py` docstring / ai-docs §2.3 / ki 记忆 | 长期存活的旧告警可能不被搬运；虽不影响查询正确性（上界恒 now），但运维预期与实际行为不符 |

### 4.2 中优先级

| # | 问题 | 证据 | 影响 |
|---|---|---|---|
| **L3** | `AlertDocument.get()` 无双副本防护，`mget()` 有 | `alert.py:161-164` vs `:205-215` | reindex 过渡期 `get` 可能返回陈旧副本 |
| **L4** | 轮转失败只有日志，无指标无重试 | `tasks.py:33-37` 仅 `logger.exception` | 索引未创建时写入会失败，但无人被告警 |
| **L5** | `current_index_info` 每次全量扫描所有索引 | `ilm.py:105-127` | 索引数增长后轮转任务自身变慢 |

### 4.3 低优先级 / 设计取舍

| # | 问题 | 证据 | 说明 |
|---|---|---|---|
| **L6** | 冷热分层在告警域未启用 | `base.py:198-211` 未传 `warm_phase_days` | 可能是有意的（告警域数据量不及时序数据），也可能未规划 |
| **L7** | `create_or_update_aliases` 即使无需变更也执行 | `ilm.py:246` | 幂等写，每 24 分钟 × 10 Document 一次，开销可接受但有优化空间 |

## 五、踩坑案例（本项目的真实教训）

[专用] 这些是已经被踩过、并被沉淀下来的坑。读它们比读代码更快建立直觉：

### 5.1 「查 7 天查不到，查 30 天能查到」

- **现象**：同一条告警，用户选 7 天时间窗查不到，选 30 天反而能查到（反直觉！）
- **根因**：用户输入的时间窗 → `build_index_name_by_time` → 索引列表。该告警已恢复，文档停在**恢复那天**的索引；7 天窗不含那一天，30 天窗含。
- **出处**：`ai-docs/bk-monitor/docs/告警后台(alarm_backends)/modules/alert/alert文档存储与查询行为.md` §4.1（2026-05-18 trace `8be317b143d4` 复盘）

### 5.2 「未恢复告警计数为 0」

- **现象**：`get_host_alarm_count` 传历史 `end_time` 时，未恢复告警计数恒为 0
- **根因**：`end_time` 被透传给 `AlertDocument.search()` 收窄了索引窗口上界，导致不含"今天"的索引
- **正确写法**：`AlertDocument.search(days=days)` 上界恒 now，`end_time` 仅做文档级 `begin_time lte` 过滤
- **出处**：ki `项目踩坑点/通用`；代码 `packages/monitor_web/cc/resources/cmdb.py`

> **两个坑的同构性**：都是"**用户时间窗 ≠ 文档实际索引位置**"。记忆口诀：**索引窗口管"扫哪些索引"，查询条件管"过滤哪些文档"，两者不可混用。**

### 5.3 「高并发 mget 打爆 scroll context」

- **现象**：`alert.manager` 成功率告警
- **根因**：`AlertDocument.mget` 原用 `scan()`（scroll API），高并发下积压突破 `max_open_scroll_context=500`
- **修复**：改为"按 ID 分批普通 search + 一次 execute 取完"（PR #11068，2026-06-15）

## 七、扩展点

[专用] 如果要在这套机制上加能力，自然的切入点：

| 需求 | 切入点 | 风险 |
|---|---|---|
| 新增一个需要轮转的 Document | 加到 `ALL_DOCUMENTS`（`documents/__init__.py`），按需设 `REINDEX_ENABLED` / `REINDEX_QUERY` | 低 |
| 修改切片粒度（按小时） | 改 `INDEX_TIME_FORMAT` 与 `slice_gap` | **高**：会影响索引名格式、别名正则、清理判定，历史索引不兼容 |
| 启用冷热分层 | `get_lifecycle_manager` 传入 `warm_phase_days` / `warm_phase_settings` | 中：需 ES 集群已配置节点属性 |
| 启用过期清理 | 在 crontab 注册 `clear_expired_indices` | 中：**会真实删除数据**，需先确认 retention 与备份策略 |
| 给 `get()` 补双副本防护 | 参照 `mget` 加 `.sort("-update_time")` | 低 |
