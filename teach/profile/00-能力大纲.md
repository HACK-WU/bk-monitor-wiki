## 一句话本质

> 把"程序运行时每一刻在忙什么"的原始记录，变成一张**哪里最耗时、一眼就能看出来**的图。
>
> 换句话说：**把一堆密密麻麻的流水账，折叠成一张能直接指出"时间花在哪儿"的地图。**

## 这份代码为什么存在

**处境对照**：剖析数据本身是"谁在什么时候占用了多少时间"的海量采样记录，一条条摊开看，人眼根本抓不住重点——这就是下面这张图左边的状态。

| | 不这么做（只有原始数据） | 这么做（建树 + 出图） |
|---|---|---|
| 看一次要花多久 | 逐条扫，几十万行起步，基本靠猜 | 打开就看到最宽的那块，直接定位 |
| 怎么比出"哪个更慢" | 记不住上一次的形状，没法比 | 两份图并排，宽窄差值直接标出来 |
| 想给同事复现 | 得把原始数据整个打包发过去 | 导出一个标准格式文件，对方本地打开即可 |
| 换一种图还要重写吗 | 每种图各解析一遍原始数据 | 只建一次树，六种图共用 |

![同样的记录，换个摆法重点自己浮出来](./assets/intuition-photo-stack.svg)

**图表来源**（本图为纯直觉类比，不对应具体代码；其表达的机制对应下列实现）
- [diagrams/base.py](file://bkmonitor/packages/apm_web/profile/diagrams/base.py#L29-L133)（调用栈树与节点值——"叠起来"的结构载体）
- [diagrams/tree_converter.py](file://bkmonitor/packages/apm_web/profile/diagrams/tree_converter.py#L23-L161)（从原始行直接建树——"换摆法"这一步）
- [views.py](file://bkmonitor/packages/apm_web/profile/views.py#L112-L880)（按 `diagram_types` 出图——选看哪种摆法）

**看图**：左边是同一批记录一条条摊开——看得全，但谁多谁少得一条条数；右边是按去处叠在一起，越宽的一块就是待得越久的那个，不用数，重点自己跳出来。本模块做的，就是右边这件事。

## 这套写法的特性

| # | 特性 | 换来什么 | 代价是什么 |
|---|---|---|---|
| 1 | [通用] 先建一棵调用栈树，再出图 | 火焰图 / 调用图 / 表格 / 趋势图共用同一份树，新增一种图不用重新解析 | 树建错则所有图一起错；树的结构约束会限制图的表达自由度 |
| 2 | [专用] 页面主链路绕开 pprof 中间格式 | 少一次序列化 + 反序列化，查询链路更短 | 页面链路与上传 / 导出链路走两套代码路径，改一处要确认是否两边都动 |
| 3 | [专用] 解析器与图表都用注册表 | 新增一种文件格式 / 一种图 = 新增一个文件 + 一行注册 | 调用关系在代码里看不出来（注册表间接引用），新人容易找不到实现在哪 |
| 4 | [通用] 节点值支持多种合成口径（AVG/SUM/LAST） | 同一棵树能回答"平均多慢""总共多慢""最后一刻多慢" | 口径靠查表匹配，查不中就静默退回某一种——结果可能不是你以为的那个 |
| 5 | [专用] 上传的文件回灌进采集链路 | 手工上传的数据和自动采集的数据走同一条存储与查询通路 | 上传链路依赖外部采集端可用，它挂了上传就失败 |

## 职责边界

**做什么** `[专用]`：本模块是蓝鲸 APM「性能分析（Profiling）」功能的 Web 侧实现，负责**把"已经采集上来的剖析数据"变成"页面上能看的火焰图 / 调用图 / 表格 / 趋势图"**，并提供文件上传与导出能力。它挂在 `apm_web/urls.py` 的 `profile_api/` 前缀下。

具体四件事：
1. **查**：从 Doris（经 bkdata 统一查询接口）拉回 sample 原始数据，转成前端要的图形结构；
2. **画**：把调用栈树渲染成火焰图、调用图（DOT）、表格、趋势图，并支持两份 profile 对比（diff）；
3. **传**：接收用户手工上传的 pprof / perf_script 文件，解析后回灌到内置数据源（走 bk-collector 的 pyroscope ingest 端点）；
4. **导**：把查询结果按 pprof 二进制格式导出，供本地 `go tool pprof` 等工具二次分析。

> ⚠️ **接手第一件事：本模块有两条并行数据管线**（[专用]，易混淆，见下文关键抽象）：
> - **Tree 管线（页面主链路）**：`query/samples` 固定用 `ConverterType.Tree`（`views.py#L430`、`views.py#L548`），由 `TreeConverter` 把 Doris 原始行**直接**建成 `FunctionTree` 再出图，**不经过 pprof**；
> - **Profile 管线（上传 / 导出）**：文件上传解析（`file_handler.py#L64`）与导出（`views.py#L818`）才把数据转成 pprof 的 `Profile` 对象。
>
> 因此 `Profile` 只是 Profile 管线与导出功能的中间格式，**不是页面主链路的中间格式**——按"全模块统一中间格式"去找页面调用链会扑空。

**不做什么** `[专用]`：
- 不负责**采集**（应用侧探针由 Pyroscope SDK / OpenTelemetry 承担——外部系统，非本模块代码；eBPF 场景由 DeepFlow 提供数据，见 `resources.py#L221-L224`）；
- 不负责**数据清洗入库**（由 bk-collector + BkData 清洗链路完成，本模块只调 `api.bkdata.query_profile_data` 查询）；
- 不做采样控制、不生成告警（无告警逻辑与定时任务写入，唯一的异步任务是上传文件解析）。
- ⚠️ **文档组织方式说明**：本模块共 **29 个 `.py` 文件**，目录层级 ≥ 3 且子目录间互相引用（`diagrams/` 内部依赖 `base.py`+`diff.py`；`views` 依赖 `doris/`+`diagrams/`；`pprof/`、`perf/` 经注册表由 `file_handler` 间接使用）。为避免产出 5×N 份碎片档案，本轮**按子模块组织章节、统一产出在 `.teach/profile/`**，不生成独立 `sub-modules/` 目录；如需对某个子模块单独深入，见末尾接力提示词。

### 术语对标

> 本模块混用 pprof 官方术语与项目自造命名，且**同一个词在不同链路指的不是一回事**，接手时极易混淆。下表给出业界叫法与出处，"代价 / 注意事项"列的是最容易踩的那个点。

| 项目叫法（人话） | 业界标准叫法 | 代码位置 | 代价 / 注意事项 |
|---|---|---|---|
| `Profile` 对象 | pprof 协议的数据模型（Google pprof 标准） | [models.py](file://bkmonitor/packages/apm_web/profile/models.py#L21-L196) | **本模块最大的坑**：它只是上传 / 导出链路的中间格式，**页面主链路不用它**——按"统一中间格式"去找页面调用链会扑空 |
| 建树 / `FunctionTree` | 调用栈树（Call Tree）；火焰图语境下即火焰图的底层结构 | [diagrams/base.py](file://bkmonitor/packages/apm_web/profile/diagrams/base.py#L29-L133) | 树一旦建好，六种图共用；建错了所有图一起错 |
| `value` / `self_value` | Total time（含子调用） / Self time（不含子调用） | [diagrams/base.py](file://bkmonitor/packages/apm_web/profile/diagrams/base.py#L29-L133) | 看图时认错这两个值，会把"自己慢"误判成"子调用慢" |
| `ConverterType.Tree` | 本项目特有（跳过标准中间格式、直建目标结构的一条取巧路径） | [views.py](file://bkmonitor/packages/apm_web/profile/views.py#L430-L548) | 换来查询链路更短；代价是页面链路与上传 / 导出链路**两套代码路径**，改一处要确认两边 |
| 聚合方法 `AVG/SUM/LAST` | 业界对同一棵树的时间合成本就有多种口径，无统一专有名词；本项目实现为可查表替换的计算策略 | [diagrams/base.py](file://bkmonitor/packages/apm_web/profile/diagrams/base.py#L135-L199) | 口径靠**查表匹配**，查不中就静默退回某一种——结果可能不是你以为的那个，且不报错 |
| `Diagrammer` + 注册表 | 插件注册表 / Registry 模式（与 Django signal 的"导入即注册"同型） | [diagrams/__init__.py](file://bkmonitor/packages/apm_web/profile/diagrams/__init__.py#L24-L62) | 新增一种图只改一处；代价是调用关系在代码里看不出来，新人找不到实现在哪 |
| pyroscope 回灌 | Pyroscope 的 ingest 协议（本模块以 agent 姿态调用其端点） | [collector.py](file://bkmonitor/packages/apm_web/profile/collector.py#L53-L133) | 上传的数据能复用采集侧的存储与查询通路；代价是依赖外部采集端可用 |
| `perf_script` 解析器 | Linux `perf script` 的文本输出格式 | [perf/converter.py](file://bkmonitor/packages/apm_web/profile/perf/converter.py#L27-L158) | 格式随内核版本有差异，解析规则硬编码，换版本可能失配 |

**全局注册表机制** `[通用]`：本模块用「模块导入即注册」的注册表模式（类似 Django signal / 插件注册表），在 `apps.py` 的 `ready()` 里把三个解析器注册进 `_profile_converters`，图表同理在 `diagrams/__init__.py` 里 `register_diagrammer_cls`。新增一种格式/图表只需新增文件 + 一行注册，无需改动调用方。
