## 不适用场景

| 场景 | 为什么不合适 | 范围 |
|---|---|---|
| 定位**单次慢请求** | Profiling 是**采样聚合**视角，看不到单次请求的完整耗时；应改用 Trace（本项目的 `apm_web.trace` 模块） | [通用] |
| 极短促的瞬时抖动（秒级以下） | 采样密度有限，短抖动可能完全没被采到 | [通用] |
| 要求精确到行号/变量的根因 | 符号信息依赖上报侧是否带齐（`has_line_numbers` / `has_inline_frames`），缺失时只能到函数级 | [专用] |
| 上传 JFR 文件 | `file_type` 选项里有 `jfr`，但**没有注册对应的解析器**，必然解析失败（详见待解决问题） | [专用] |
| 调用图做对比 | `CallGraphDiagrammer.diff()` 直接抛 `ValueError`（[callgraph.py#L370-L371](file://bkmonitor/packages/apm_web/profile/diagrams/callgraph.py#L370-L371)） | [专用] |

## 解决的核心问题

**在已经有 Trace / Metric 的前提下，Profiling 解决的是"知道哪个服务慢、但不知道为什么慢"的最后一公里。**

- Trace 回答"这次请求慢在哪一跳"——到接口/服务粒度就停了；
- Metric 回答"CPU 是不是高了"——只有总量，没有归因；
- **Profiling 回答"是哪个函数吃掉了这些 CPU/内存"**，把归因精确到函数级调用栈。

本项目把这能力做成"**查询 + 出图 + 上传 + 导出**"四项 Web 能力，并兼容 Pyroscope 生态（用户不必换探针）+ 支持 eBPF 无侵入采集（不必改代码）。

## 待解决问题与风险

> 以下为客观描述的事实性风险与技术债，不做"该不该改"的裁决（判定权在 `code-review`）。

| # | 问题 | 证据 | 影响 |
|---|---|---|---|
| 1 | **JFR 格式声明了但没有解析器**：`file_type` choices 含 `jfr`，`InputType` 枚举也有 `JFR`，但 `apps.ready()` 只注册了 DORIS / PERF_SCRIPT / PPROF 三个 | [models/profile.py#L31-L36](file://bkmonitor/packages/apm_web/models/profile.py#L31-L36)、[constants.py#L35-L43](file://bkmonitor/packages/apm_web/profile/constants.py#L35-L43)、[apps.py#L27-L29](file://bkmonitor/packages/apm_web/apps.py#L27-L29) | 上传 JFR 文件必然 `PARSING_FAILED`，且失败信息不直观 |
| 2 | **perf_script 解析器残留调试 `print`** | [perf/converter.py#L66-L69](file://bkmonitor/packages/apm_web/profile/perf/converter.py#L66-L69) | 污染标准输出；celery worker 日志噪音 |
| 3 | **服务柱状图按时间点放大查询**：每个时间点一次 label 查询，无点数量/并发度上限 | [resources.py#L283-L299](file://bkmonitor/packages/apm_web/profile/resources.py#L283-L299) | 长时间跨度（如 24h）会产生上千次下游请求 |

| 7 | **大应用判定缓存 1 小时** | [views.py#L566-L567](file://bkmonitor/packages/apm_web/profile/views.py#L566-L567) | 服务规模突变时，查询上限在 1 小时内不跟随 |
